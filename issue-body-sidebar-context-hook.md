Part of #1946 — Redux → React Query migration (Stage 1). Follow-up to #2111, which gave `SidebarContext` a `null` default and a `useSidebar()` hook but left the existing consumers and the raw `SidebarContext` export in place. A **wide** layer: many files, each touched lightly. Sequenced before #2087 (moved in review on 2026-09-24, so that layer lands on files already using the hook).

**Goal:** make `useSidebar()` the only way to read the sidebar context, stop exporting `SidebarContext` itself, and move the sidebar test suites off hand-rolled context values onto the real `SidebarProvider` — the convention the repo's other contexts (`ToastProvider`, `PluginOverridesProvider`, `CoursewareSearchProvider`, `TourProvider`) already follow in tests.

**Context.** After #2111, `courseware/course/sidebar/SidebarContext.ts` exports the context as its default export and `useSidebar()` beside it. Ten production files still read the context with `useContext(SidebarContext)`, which under the provider returns the same value as the hook and outside it returns `null` and throws on the destructure rather than with the hook's message. Some twenty test suites render the raw `SidebarContext.Provider` with a partial hand-rolled `value` (`mockData`, `defaultContextValue`, `buildContext(overrides)`), a convention from #1885/#1899 that predates the typed context; #2111's decision log (entry 15) records why that was left alone there and why the real-provider pattern is the target.

**Tasks**
- The ten `useContext(SidebarContext)` reads → `useSidebar()`: `sequence/lock-paywall/LockPaywall.jsx`, `sequence/sequence-navigation/hooks.js` (`useIsSidebarOpen`), `sidebar/Sidebar.jsx`, `sidebar/SidebarTriggers.jsx`, `sidebar/common/SidebarBase.jsx`, `sidebar/sidebars/course-outline/hooks.js`, `widgets/discussions/DiscussionsSidebar.jsx`, `widgets/discussions/DiscussionsTrigger.jsx`, `widgets/upgrade/src/UpgradePanel.jsx`, `widgets/upgrade/src/UpgradeTrigger.jsx`.
- Stop exporting `SidebarContext` from `SidebarContext.ts` and from `sidebar/index.js` (`export { default as SidebarContext }`); the module exports the hook and the types. `SidebarContextProvider.tsx` is the one remaining user of the context object.
- The test suites that render `SidebarContext.Provider value={…}` render the real `SidebarProvider` (with `courseId`/`unitId`, under a router, with the course query hooks mounted where the value depends on course data) and express the sidebar state they need through what the provider reads — viewport width, `sidebar` search param, localStorage — instead of a literal: `Sequence`, `LockPaywall`, `SequenceNavigation`, `SequenceNavigationTabs`, `Sidebar`, `SidebarTriggers`, `SidebarBase`, `CourseOutlineTray`, `CourseOutlineTrigger`, `SidebarSection`, `SidebarSequence`, `SidebarUnit`, `DiscussionsSidebar`, `DiscussionsTrigger`, `UpgradePanel`, `UpgradeTrigger`.
- The two suites that test components the provider itself mounts — `DiscussionsProvider.test.tsx`, `UpgradeWidgetContext.test.jsx` — cannot render the provider without circularity; give them a way to supply the context without it (a test-only export from `SidebarContext.ts`, or a small helper in `src/tests/`), decided in the plan.
- `sidebar/README.md`: the consumer examples already use the hook (#2111); remove any remaining mention of importing `SidebarContext` directly.

**Not in scope:** the provider's own logic, the widget contract types, and the `useModel` reads in the widget components (#2087, #2089).

**Verify:** `git grep "useContext(SidebarContext)" src` and `git grep "SidebarContext.Provider" src` return only `SidebarContextProvider.tsx` (and the agreed test-only seam); every suite that previously faked the context passes under the real provider; the trigger strip, paywall and navigation behave as before on tutor dev; `npm run types`, `npm run lint` and the full suite green.

**Findings that shape the task list**

- **The export and the test convention are coupled.** Tests can fake the context only because `SidebarContext` is exported; removing the export forces the suites onto the real provider, which is why the two changes are one layer rather than two. Doing the consumer swap alone would leave the export in place for the tests and change nothing an author sees.
- **The real provider mounts every enabled widget's `Provider`.** Under `SidebarProvider`, `UpgradeWidgetProvider` reads localStorage and `DiscussionsProvider` observes the topics query when the course-home metadata has a discussion tab. A suite whose metadata fixture has that tab will see the two discussion requests go to its adapter; it mocks them (the widget suites already do) or accepts the 404-and-log `Course.test.jsx` already lives with. Nothing renders a trigger or panel unless the suite renders `SidebarTriggers` / `Sidebar`.
- **"Nothing open" is the provider's own answer in jsdom.** With empty storage and the default jsdom viewport (below the extra-large breakpoint), `initialSidebar` and `currentSidebar` are `null` and `availableSidebarIds` follows each widget's `isAvailable`; the hand-rolled `{ currentSidebar: null, availableSidebarIds: [] }` values were asserting what the provider computes anyway. Suites that need a panel open set `sidebar.{courseId}` in localStorage or widen `global.innerWidth`, the way `Course.test.jsx`'s *sidebar behavior* cases do.
- **`SidebarContextProvider.test.jsx` is unaffected.** It renders the provider already.
