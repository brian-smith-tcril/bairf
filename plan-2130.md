# Plan: #2130 — type the course-home API module on the functions that produce its results

Sibling of #2129, from its plan's sweep of everything that reshapes an API
response. Layer of the running stack #2141 above #2148's bug-fix layer, which sits
above #2146 (`bsmith/declarative-courseware-redirects`, #2135). Slotted here because its
issue body names this slot: after #2089 (on the stack) and before #1999, which
is the next work to touch `tab-page/` and `CourseHomeMeta`.

## How it works today

`src/course-home/data/api.js` is 384 lines and seventeen functions. Under
TypeScript, `getAuthenticatedHttpClient()` resolves to `any` (frontend-platform's
`interface.d.ts` returns a `HttpClient` typedef that is never declared;
`skipLibCheck` hides it), and `camelCaseObject` is declared `any[] | any`. So
every result type has to be stated on the function, the way
`instructor-toolbar/masquerade-widget/data/api.ts` already does — no axios
import is needed, and none is wanted (axios is not a direct dependency).

**Two determined normalizers**, whose output is fully known because the
function picks the fields:

| Function | Reads (snake_case) | Emits |
|---|---|---|
| `getOutlineTabData` (inline, after the fetch) | `access_expiration`, `cert_data`, `course_blocks.blocks`, `course_goals`, `course_tools`, `dates_banner_info`, `dates_widget`, `enable_proctored_exams`, `enroll_alert`, `enrollment_mode`, `handouts_html`, `has_scheduled_content`, `has_ended`, `offer`, `resume_course`, `user_has_passing_grade`, `verified_mode`, `welcome_message_html`, plus `headers.date` | 19 camel-cased fields + `timeOffsetMillis` |
| `normalizeOutlineBlocks(courseId, blocks)` | per block: `type`, `id`, `display_name`, `children`, `has_scheduled_content`, `complete`, `resume_block`, `hide_from_toc`, `description`, `due`, `effort_activities`, `effort_time`, `icon`, `lms_web_url`, `navigation_disabled` | `{ courses, sections, sequences }` maps; back-references `courseId` / `sectionId` |

Both have the `{}` fallback the current `OutlineTabData` comment describes:
`getOutlineTabData` returns `{}` on a 403, and `courseBlocks` is `{}` when the
view sends `course_blocks: null` (an unenrolled non-staff learner on a course
that is neither public nor public-outline — `outline/views.py` sets it only in
the `show_enrolled` and `allow_public*` branches).

| `getProctoringInfoData` | **raw snake_case `data`**; `{}` on 404 | `outline-tab/utils.ts` already declares its shape (`ProctoringInfo { onboarding_status?; expiration_date? }`) on the consumer side |

| `postWeeklyLearningGoal` | the axios response, unread | — |

**Six `catch` blocks, two idioms.** `getDatesTabData`, `getProgressTabData`
and `getOutlineTabData` read `error?.response?.status`; `getProctoringInfoData`,
`getLiveTabIframe` and `getExamsData` read
`const { httpErrorStatus } = error && error.customAttributes`. In production
the two are the same number: `AxiosJwtAuthService` installs
`createProcessAxiosRequestErrorInterceptor`, whose `processAxiosError` copies
`response.status` to `customAttributes.httpErrorStatus`. In tests they are
not: `MockAuthService` builds its client with a bare `axios.create()` and no
interceptors, so a plain `axiosMock.onGet(url).reply(404)` reaches the second
idiom with `customAttributes` undefined and the destructure throws a
`TypeError`. `OutlineTab.test.jsx` does exactly that twice (lines 578 and 1238,
`proctoringInfoUrl`); both pass today because an errored query (`retry: false`)
renders no panel either, which is the same outcome the `{}` branch produces.
`apiHooks.test.tsx` and `ProgressTab.test.jsx` sidestep it by rejecting with a
hand-built error carrying both `response` and `customAttributes`.

**Types at the hook today** (`apiHooks.ts`): `CourseHomeMeta` (exported,
caveat form, "the fields this repo's TypeScript readers need"),
`OutlineSequence` (exported; no importer anywhere, no README mentions it) and
`OutlineTabData` (local, all-optional caveat form). The other hooks are
untyped, so `useProgressTabData(...).data.studioUrl` in the hook suite compiles
as `any`.

## Findings that shape the work

1. **`OutlineTabData.userTimezone` was typed to a reader, and the read has
   been dead since PR #606 (2021-09-03).** `SequenceDueDate.tsx:25` reads
   `useOutlineTabData(courseId, { enabled: false }).data?.userTimezone`, a
   top-level key. The provenance, link by link:
   - The outline endpoint has carried `user_timezone` inside `dates_widget`
     and nowhere else since the platform added the widget
     (openedx-platform `84b08f366d`, 2020-06-08, AA-122). The view's
     response dict has never had a top-level `user_timezone`; the three
     platform commits that touch the string in `course_home_api/outline/`
     all place it under the widget.
   - `getOutlineTabData` has never emitted a top-level `userTimezone`:
     `git log --follow -S userTimezone -- src/course-home/data/api.js` is
     empty over the file's whole history. It has emitted `datesWidget`
     (camel-cased) since 2020.
   - The `outline` model was always the spread of that function's result
     plus `id` — `fetchTab` in `thunks.js` (2020 → #1997), then the bridge
     (#1997 → now). Nothing else ever wrote it (three commits in history
     touch `modelType: 'outline'`: #73, #80, #1997).
   - PR #198 (`9cbe0b7c`, 2020-08-31, AA-126) introduced the due-date
     timezone in `SequenceLink.jsx` reading the right place:
     `const { datesWidget: { userTimezone } } = useModel('outline', courseId)`.
     It stayed that way through eleven commits.
   - PR #606 (`70e2aa02`, 2021-09-03, AA-877) set out to "update
     `userTimezone` to come from `CourseHomeCourseMetadata` rather than the
     individual tabs" (its body), after the platform added `user_timezone`
     to `course_metadata` (`fe435987b0`, 2021-08-16). It did that in
     `OutlineTab.jsx` and `CourseDates.jsx` (both switched to
     `useModel('courseHomeMeta', courseId)`), and moved `user_timezone` from
     the outline factory to the metadata factory. In `SequenceLink.jsx` it
     removed the `datesWidget: { … }` nesting but left the model as
     `'outline'`:
     ```diff
      const {
     -    datesWidget: {
     -      userTimezone,
     -    },
     +    userTimezone,
      } = useModel('outline', courseId);
     ```
     From that commit on the destructure yields `undefined`.
   - #1632 (`f39a50e7`, 2025-03-18) rewrote `SequenceLink` as the TypeScript
     section-outline components and carried the flat read into
     `SequenceDueDate.tsx` unchanged; #2093 swapped `useModel` for
     `useOutlineTabData` and wrote `userTimezone?: string` into
     `OutlineTabData` to make it compile.
   So sequence due dates on the outline tab have formatted in the browser's
   zone, not the learner's preference, for four years; every other date on
   the tab (`CourseDates`, `Day`, the course-end and certificate alerts)
   honours the preference via `useCourseHomeMeta`. The complete
   `CourseHomeOutline` type turns the read into a compile error, which is
   how it surfaced (D4).

2. **A result type for `getProctoringInfoData` already exists, on the
   consumer.** `outline-tab/utils.ts` declares `ProctoringInfo` with the two
   fields `getReadableProctoringStatus` reads. `ProctoringInfoPanel.jsx` also
   reads `onboarding_link`, `onboarding_past_due`, `onboarding_status`,
   `onboarding_release_date`. The type moves to `api.ts` beside the function
   and `utils.ts` imports it.

3. **Two callers still pass the removed `rootSlug`.** `setupTest.js:175` and
   `CourseExit.test.jsx:64` call `getCourseHomeCourseMetadata(courseId, 'courseware')`.
   Both files are JavaScript, so `npm run types` will not flag a
   one-parameter signature; they are stale all the same (D5).

4. **`searchCourseContentFromAPI` and `unsubscribeFromCourseGoal` return the
   camel-cased axios response, not its payload.** Their callers read `.data`.
   The result types say so (`{ data: … }`); changing what they return is out
   of scope.

5. **The live endpoint can answer 200 without `iframe`.** When the live tab is
   disabled the view returns `{ developer_message }` with a 200, so `iframe`
   is optional on the result and `LiveTab.jsx`'s `tabDataQuery.data?.iframe`
   already treats it so.

6. **The hook suite depends on `any`.** `apiHooks.test.tsx:248-249` read
   `result.current.data.studioUrl` and `.gradesFeatureIsFullyLocked` with no
   guard; once `useProgressTabData` is typed, `data` is possibly undefined
   under `strict` and those lines need `data?.` (or `!`). Expect a few such
   edits in that file only.

7. **Nothing outside the repo names the types that move.** `OutlineSequence`
   has no importer; `OutlineTabData` is module-local; `CourseHomeMeta` is
   imported only by in-repo TypeScript (`course-tabs/hooks.ts`,
   `SidebarContext.tsx`, …) and the READMEs reference the hooks, not the
   type's path. So the file moves and the renames in D2 are `refactor:`, no
   `!`.

## Decisions to settle

**D1 — where the types and normalizers live (settled 2026-10-01: (b), the
new file).** The issue body (written before
#2129's review) says "`api.js` → `api.ts`, types beside functions". #2129's
review then settled a different shape for determined normalizers:
`data/<typeName>.ts` exports `normalize<TypeName>`, output types first, then
the input type, then the function, with a header naming the endpoint — and
its decisions doc (entry 1) calls this module "the same kind of work".

- **(a) One file, as the issue says.** `api.ts` holds everything: the two
  normalizers with their types, the fetchers, the passthrough types beside
  each fetcher. 384 lines becomes roughly 550.
- **(b) #2129's shape for the normalizer, `api.ts` for the rest
  (recommended).** The inline normalization at the end of `getOutlineTabData`
  and `normalizeOutlineBlocks` move to `course-home/data/courseHomeOutline.ts`
  (name per D2) as `normalizeCourseHomeOutline(response, requestTime)` and
  `normalizeCourseHomeOutlineBlocks(courseId, blocks)`, with their output and
  input types; `getOutlineTabData` keeps the fetch, the 403 branch and the
  `Date.now()` stamps and calls the normalizer — the same split
  `courseware/data/api.js`'s `getCourseMetadata` → `normalizeCoursewareMeta`
  has, down to the headers-for-clock-offset argument. `api.ts` keeps the
  fifteen fetchers and declares each passthrough's caveat-form result type
  beside its function (there is no normalizer to name a file after, and the
  masquerade `api.ts` precedent is exactly this). `getTimeOffsetMillis` stays
  in `api.ts` (two importers keep their path).

**D2 — names for the outline's types (settled 2026-10-01).** The endpoint,
as exposed, is `course_home` / `outline` (`GET api/course_home/v1/outline/{course_key}`;
no `tab` in the URL or the body — "Tab" exists only in the platform's class
names, route name and docstring). The repo already names this API's objects
by module: `course_home` / `course_metadata` → `CourseHomeMeta`. The same
rule gives `CourseHomeOutline`, and the user chose one prefix throughout:
with as many versions of "course", "outline" and "sequence" as this
application has, a child named `CourseOutlineSequence` under a
`CourseHomeOutline` parent is one more thing to confuse. #2129's settled
`CourseOutlineSequence` is extended by its own rule, not replaced.

| Today | Settled | Shape |
|---|---|---|
| `OutlineTabData` (local, partial) | `CourseHomeOutline` | the 20 emitted fields, complete |
| `courseBlocks` (untyped) | `CourseHomeOutlineBlocks` | `{ courses, sections, sequences }` |
| — | `CourseHomeOutlineCourse` | `{ id, title, sectionIds, hasScheduledContent }` |
| — | `CourseHomeOutlineSection` | `{ complete, id, title, resumeBlock, sequenceIds, hideFromTOC, courseId }` |
| `OutlineSequence` (exported) | `CourseHomeOutlineSequence` | `{ complete, description, due, effortActivities, effortTime, icon, id, showLink, title, hideFromTOC, navigationDisabled, sectionId? }` |
| `normalizeOutlineBlocks` | `normalizeCourseHomeOutlineBlocks` | — |
| (inline) | `normalizeCourseHomeOutline` | — |
| — | `courseHomeOutline.ts` | the file (D1b) |

Not `CourseOutline`: that is the platform's name for the learning-sequences
object (`CourseOutlineView` / `CourseOutlineData`), which `MinimalCourseOutline`
models. Not `CourseOutlineTab` / `OutlineTab…`: internal names, and the
reviewer did not like the latter in #2129. The nested camel-cased objects
(`accessExpiration`, `certData`, `courseGoals`, `courseTools`,
`datesBannerInfo`, `datesWidget`, `enrollAlert`, `offer`, `resumeCourse`,
`verifiedMode`) stay `unknown` as #2129 entry 4 did, until a TypeScript reader
names their insides — none does today (`ShiftDatesAlert.tsx` takes
`datesBannerInfo` as a prop with its own type).

**D3 — which readers set the caveat types' fields (settled 2026-10-01: all
readers).** The rule is "name what we read": a field goes on a passthrough's
type because something in this repo reads it, JavaScript or TypeScript;
nothing goes on because the serializer declares it. The serializer is
consulted only for the nullability of a field we read. `CourseHomeMeta`'s
comment ("this repo's TypeScript readers need") was the narrower reading and
is reworded; the issue body ("the fields this repo's readers use") is the
rule. What that means per type:

- Dates: `courseDateBlocks`, `datesBannerInfo`, `hasEnded` (`DatesTab.jsx`,
  `Timeline.jsx`, `UpgradeToCompleteAlert.jsx`); `learnerIsFullAccess` and
  `userTimezone` are declared by `DatesTabSerializer` but read by nothing,
  so they stay under the index signature.
- Progress: the top-level fields the 23 `useProgressData()` sites read
  (`assignmentTypeGradeSummary`, `certificateData`, `completionSummary`,
  `courseGrade`, `creditCourseRequirements`, `disableProgressGraph`, `end`,
  `enrollmentMode`, `finalGrades`, `gradingPolicy`, `hasScheduledContent`,
  `sectionScores`, `studioUrl`, `userHasPassingGrade`, `verificationData`,
  `verifiedMode`) plus the four computed fields, with the nested shapes the
  readers destructure (`completionSummary`, `courseGrade`, `gradingPolicy`,
  `sectionScores[].subsections[]`); surveyed exactly at implementation,
  nullability from `ProgressTabSerializer`.
- Live: `iframe?` (finding 5). Exams: `exam?`. Proctoring: the six
  snake_case fields `ProctoringInfoPanel.jsx` and `outline-tab/utils.ts` read.
- `CourseHomeMeta`: the ten named today plus what the JavaScript readers
  use (`courseId`, `username`, `userTimezone`, `isEnrolled`, `isMasquerading`,
  `isStaff`, `isSelfPaced`, `canViewCertificate`, `courseModes`, …; surveyed
  exactly at implementation). That is close to everything
  `CourseHomeMetadataSerializer` declares, because the repo reads close to
  everything — the rule did not change.

**D4 — the broken `userTimezone` read in `SequenceDueDate.tsx` (finding 1;
settled 2026-10-01).** Filed as #2148, a sub-issue of #1946, and fixed as its
own bug-fix layer *below* this one (failing test, then #606's intended
change: read `useCourseHomeMeta(courseId, { enabled: false }).data?.userTimezone`).
Deleting the read was rejected: it throws away the broken thing instead of
fixing it. This layer then drops the `userTimezone?` placeholder from the
outline type without touching the component.

**D5 — the stale `rootSlug` arguments (finding 3; settled 2026-10-01).**
Dropped in this layer. Both callers are test files (`setupTest.js`, the
shared test setup, and `CourseExit.test.jsx`); no production caller passes
a second argument. They are the only callers of a function this layer gives
a one-parameter signature.

**D6 — error handling.** All six `catch` blocks read the status through
`getResponseStatus` from `src/data/http-error`, as the issue says. The
consequence worth stating in the decisions doc: the two `OutlineTab.test.jsx`
cases that `reply(404)` to the proctoring request stop throwing a `TypeError`
inside the query function and start exercising the intended `{}` branch; their
assertions are unchanged. `apiHooks.test.tsx`'s hand-built errors carry
`response.status`, so they keep working; their `customAttributes` lines
become inert (left alone — they document what the real client attaches).

**D7 — the empty-object branches.** For the caveat-form types every field is
already optional, so `{}` needs no special typing (the current
`OutlineTabData` comment says why). For the complete `CourseHomeOutline`, the
function's return is `Promise<CourseHomeOutline | Record<string, never>>` and
`courseBlocks` is `CourseHomeOutlineBlocks | Record<string, never>`: the two
`{}` sites are real (a 403; `course_blocks: null`), and `Record<string, never>`
is the idiom that lets the TypeScript readers' optional chains
(`data?.courseBlocks?.sequences` in `Section.tsx`) type through. The
JavaScript readers that destructure `.data ?? {}` are unaffected.

**D8 — `getTimeOffsetMillis` parameters are `number`.** Both production
callers pass `Date.now()`; `api.test.js` passes `Date` objects and stays
JavaScript (coerces through `valueOf`), as the issue says.

**D9 — `useExamAttemptsData`'s generic.** It is `useQuery<Record<string, unknown>[]>`
today; with `getExamsData` typed `{ exam?: Record<string, unknown> }` the
hook's `.exam || {}` infers that same element type, so the hand-written
generic goes.
