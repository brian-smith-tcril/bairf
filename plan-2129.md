## The sweep: everything that reshapes an API response

Two kinds of reshaping exist in the repo, and they call for different typing.

**Determined normalizers** pick a fixed set of fields from the response and
build a new object. Their output is fully known — the normalizer *is* the
schema — so the output type can be complete, with no index signature and no
caveat, and the input type names the fields the normalizer reads and stays
open (the response is openedx-platform's to describe).

rest `unknown`. They are *not* this issue's.

**Two precedents for where types live.** `instructor-toolbar/masquerade-widget/data/api.ts`
is already TypeScript and declares its result interfaces beside the
functions that return them — the shape this issue wants. `courseOutline.ts`
puts the types in a sibling `.ts` file beside a JavaScript normalizer, the
half-way form taken when `utils.js` was left as is.

**One naming collision to resolve.** `course-home/data/apiHooks.ts` already
exports an `OutlineSequence` (the outline *tab*'s sequence row: `complete`,
`due`, `showLink`, …). B introduced a second `OutlineSequence` for the
learning-sequences outline (`{ id, title, sectionId }`) in
`courseware/data/apiHooks.ts`. Different endpoints, different shapes, same
name in two modules a reader may import together.

## Scope decisions to settle

**S1. This issue is the courseware normalizers only.** Convert
`courseware/data/utils.js` → `utils.ts` and type its four functions. The
course-home `getOutlineTabData` + `normalizeOutlineBlocks` are the same kind
of work in a 384-line JavaScript module whose other fifteen functions are
passthroughs; converting that file is #2130, filed as a sibling (sized in
review at about twice this layer, most of it caveat-form types for the
passthroughs), slotted after #2089 and before #1999. The passthrough sites
elsewhere keep the caveat form and are nobody's issue.

**S2. `courseOutline.ts` stays, and `normalizeOutlineBlocks` declares its
return as `CourseOutlineData` from it.** The file also holds
`applyUnitCompletion`, logic on the same shape, so it is a real module, not
just a types file; folding its four interfaces into `utils.ts` would leave
that function importing its types back from the normalizer module.

**S3. `CoursewareMeta` is typed fully — all thirty fields `normalizeMetadata`
builds, with scalar types where it copies a scalar; only the nine camel-cased
sub-objects (`accessExpiration`, `celebrations`, `entranceExamData`, …) are
`unknown`, since their insides are the platform's and no reader has named
them yet.** The issue body said the placeholder stays until
#2089 names fields, on the reader-driven rule that types grow as readers
convert. Typing the producer inverts that rule for the producer's own
output: every field `normalizeMetadata` emits is known by name, and the
input type has to list them anyway to read `data.enrollment.mode` and the
rest under TypeScript. What is *not* known is the inner shape of
`camelCaseObject(data.access_expiration)`, `celebrations`, `entranceExamData`
and the other seven sub-objects, which stay `unknown` until a reader names
their fields (#2089's readers will, for `entranceExamData` at least). A
placeholder return type on a function whose every field is visible in its
body would be the odd outcome.

**S4. Inputs are typed as what the normalizer reads, open-ended.** Four
response interfaces (`LearningSequencesOutlineResponse`,
`CoursewareMetadataResponse`, `SequenceMetadataResponse`,
`OutlineBlockResponse`), each naming the snake-case fields the function
touches with an index signature and the `DiscussionTopic`-style note. Not
exported unless a caller needs them: `api.js` stays JavaScript, so nothing
does yet.

**S5. The learning-sequences `OutlineSequence` is renamed to avoid the
course-home collision.** Candidates: `LearningSequence`,
`CoursewareOutlineSequence`. B's uses (`Sequence`, `Course`, the alert,
`CoursewareContainer`) refer to the map, not the type name, so the rename
touches the type declaration and B's one type import.

**S6. `apiHooks.ts` imports; nothing re-exports.** #2128 exported
`SequenceUnit` from `apiHooks.ts` and its breaking-change footer pointed
plugins at that path; #2128 is a draft on the stack, so the path can move
before anything ships. `SequenceUnit`, `SequenceMetadata`, `SequenceMetadataData`,
`CoursewareMeta` and the outline types are imported from `./utils`; the
#2128 footer is amended to name the new path. `DiscussionTopic` stays
beside its query.

  (`/api/course_home/v1/navigation/`, `CourseNavigationBlocksView`):
  `courseOutline.ts` → `courseNavigationOutline.ts`, `CourseOutlineData` →
  `CourseNavigationBlocks`, `CourseOutlineSection` / `Sequence` / `Unit` →
  `CourseNavigationSection` / `Sequence` / `Unit`; `normalizeOutlineBlocks`
  declares that return. Two importers, both in `courseware/data`. This
  replaces S2's "stays as is": the file stays a module (it also holds
  `applyUnitCompletion`), only its names change.
- **The outline tab's sequence type is `CourseOutlineSequence`** (reviewer's
  preference, 2026-09-26: it matches the endpoint URL
  `/api/course_home/outline/`; `OutlineTabSequence`, the platform's view
  name, was offered and not liked). The rename itself lands in #2130, not
  this layer. Consequence for the open item below: `CourseOutline…` is the
  outline tab's prefix, so the learning-sequences types cannot also take it.
- **Naming rule, from the endpoint survey**: a type is named after the
  endpoint object it models, partial or not — the rule `CourseHomeMeta` and
  `DiscussionTopic` already follow. The platform names a sequence in the
  learning-sequences outline (`CourseLearningSequenceData`) and the whole
  sequence payload (`SequenceMetadata`); for the two `CourseBlockSerializer`
  endpoints it names only "a block of type `sequential`", so the
  `…Sequence` suffix there is ours, qualified by the endpoint.

**Settled last (2026-09-26): the learning-sequences outline types.**
`/api/learning_sequences/v1/course_outline/` returns a user-specific course
outline — structure plus scheduling (`start` / `effective_start` / `due` at
every level), access (`accessible`, `inaccessible_after_due`), exam state and
provenance — and `normalizeLearningSequencesData` keeps the hierarchy and
titles, consuming the schedule and access fields only as a release filter.
Set against `SequenceMetadata` (the `/api/courseware/sequence/` payload, what
it takes to render one sequence), the overlap is `id` and `title`; the rest
is disjoint. So the type is named for what it is relative to that one:

- `MinimalSequenceMetadata` — `{ id, title, sectionId }`
- `MinimalSectionMetadata` — `{ id, title, sequenceIds, courseId }`
- `MinimalCourseMetadata` — `{ id, title, sectionIds, hasScheduledContent }`
- `MinimalCourseOutline` — the map `{ courses, sections, sequences }`

The input type keeps the endpoint's own name, `CourseOutlineResponse`. Not
chosen, in order: the platform's names (`CourseOutline` /
`CourseLearningSequence` — claim the full object, and `CourseOutline…` is
the outline tab's prefix), `CourseStructure*` (invents a word),
`SequenceOutlineEntry` ("entry" adds nothing), `SequenceIdentifiers` (plural
reads as a list of ids), `SequenceIdentity` (identity-function baggage),
`SequenceRef` / `SequenceListing` / `SequenceHeader` (close but none felt
right), `SequenceBasics` (the runner-up: same meaning, no relationship
named). The chosen name states the contrast with `SequenceMetadata`, which
is what a reader of `Sequence.jsx`, where both appear, most needs.
