# Plan: #1975 close-out — retire the `courseHome` Redux slice

## Context

Part of epic #1946 (Redux → React Query, Stage 1). #1975 was "convert course-home
tab data to React Query; remove the `courseHome` reducer". Everything but the
last clause is done and stacked: the five tabs (#1984 dates, #1991 outline,
#1998 progress, #2002 live, #2003 discussion), the CTA toast (#1980),
`requestCert` (#1994), `dismissWelcomeMessage` (in the outline conversion),
courseware search (#1979), and — as its own layer because it is a plugin
contract — the exam attempts fetch (#2075 → PR #2077). `thunks.js`,
`redux.test.js` and `slice.test.js` are already gone.

What remains of the slice on the tip of stack #2062 (after #2077):

```js
initialState: {
  courseStatus: 'loading',      // dead — no reducer writes it, no reader
  courseId: null,               // dead
  proctoringPanelStatus: 'loading',
  errorMessage: null,           // dead
  errorCode: null,              // dead
},
reducers: {
  fetchProctoringInfoResolved: (state) => { state.proctoringPanelStatus = LOADED; },
},
```

One live signal: **"has the proctoring-info fetch settled?"** Its writer and
readers sit in three different components:

- **Writer** — `outline-tab/widgets/ProctoringInfoPanel.jsx`: a mount effect
  calls `getProctoringInfoData(courseId, username)` (username from
  `useModel('courseHomeMeta')`, i.e. the possibly-masqueraded learner), spreads
  the response into six `useState`s (link, status, readable status, release
  date, past-due, show-panel), swallows every error (the api already maps 404 →
  `{}`; the panel's `.catch` swallows the rest), and in `.finally` dispatches
  `fetchProctoringInfoResolved()`.
- **Reader 1** — `outline-tab/OutlineTab.jsx:176`, the panel's parent: defers
  `WeeklyLearningGoalCard` until `!enableProctoredExams || status === 'loaded'`
  so the sidebar doesn't jump while the panel resolves.
- **Reader 2** — `product-tours/ProductTours.jsx:78`, rendered by
  `LoadedTabPage` as a *sibling* of the tab content: on the outline tab it
  holds `useTourData` back until `status === 'loaded'`, because the tour anchors
  to the weekly-goal widget that reader 1 gates.

Everything else touching the slice is registration: `store.ts`,
`setupTest.js`'s `initializeTestStore`, and `course-home/data/index.js`, which
now exports only the reducer.

## Approach: the signal is query status, so make it a query

Convert `getProctoringInfoData` to a React Query hook and read "settled" off
the query. This follows the pattern the tab conversions set (`courseStatus`
strings became `metadataQuery` / `tabDataQuery` state): the Redux field was a
hand-rolled loading flag for a fetch, and a query already carries that flag.
No new context, no lifted `useState` — both readers call the same hook and
React Query dedupes.

### 1. `course-home/data/queryKeys.ts` + `apiHooks.ts`

```ts
proctoringInfo: (courseId: string, username?: string) => (
  [...courseHomeQueryKeys.all, 'proctoringInfo', courseId, username] as const
),
```

```ts
export const useProctoringInfoData = (courseId: string, username?: string, enabled = true) => useQuery({
  queryKey: courseHomeQueryKeys.proctoringInfo(courseId, username),
  queryFn: () => getProctoringInfoData(courseId, username),
  enabled,
  retry: false,
});
```

`getProctoringInfoData` is unchanged (404 → `{}` stays in the api; its
`api.test.js` cases stay). The hook sets **`retry: false`** — see "Settled
vs. error" below.

### Settled vs. error (decided: `!isPending` + `retry: false`)

Today the panel's effect chains `.then(...).catch(() => {}).finally(() =>
dispatch(fetchProctoringInfoResolved()))`. The api maps 404 → `{}` so the
common no-proctoring case is a *success* with an empty object; only 5xx and
network failures reach the `.catch`, which swallows them silently, and
`.finally` marks the panel resolved on the first outcome regardless.

History (PR #727, 2021-11-09, "defer goals widget for proctoring"): the
`.catch` and `.finally` were added together. The intent was that the goals
widget must never stay hidden because of this request — hence settle on any
outcome. The catch's comment ("API throws 404 when class does not have
proctoring") was already wrong when written (the api had mapped 404 → `{}`
since the panel's first commits), and before #727 a 5xx surfaced as an
unhandled rejection. So "always settle" is intentional; the silence on real
failures is a side effect nobody chose.

Preserve the intent, drop the accident:

- Readers gate on **`!isPending`** (true once the query has data *or* an
  error), never `isSuccess` — a persistent 5xx must not hide the weekly-goal
  card or block the outline tour.
- **`retry: false`** on this query. The app default `shouldRetryQuery`
  retries 5xx/network up to 3× with 1s/2s/4s backoff, which would hold the
  card and tour ~7s on a failing endpoint; #727's design was an immediate
  unblock, so keep it.
- **No swallow in `queryFn`.** The error lands in `isError` and reaches the
  app `QueryCache.onError` → `logError`. The panel renders nothing on error
  (no data → `showInfoPanel` false), same as today, but the failure is now
  logged where it used to vanish.

### 2. `ProctoringInfoPanel.jsx` — derive, don't store

Replace the effect + six `useState`s with the query and plain derivation
from `data` (`onboardingStatus`, `onboardingLink`, `expirationDate` →
readable status, `onboardingReleaseDate`, `onboardingPastDue`, "show panel" =
non-empty response). The response is **not** camelCased today
(`getProctoringInfoData` returns raw `data`; the panel reads
`response.onboarding_status`) — keep reading snake_case, or camelCase in the
hook and update the reads; either way byte-for-byte the same rendered output.
Drop `useDispatch`, the slice import, and the `react-hooks/exhaustive-deps`
disable that guarded the mount-only effect.

### 3. `OutlineTab.jsx` — reader 1

`const { proctoringPanelStatus } = useSelector(state => state.courseHome)` →
`const { isPending: isProctoringInfoPending } = useProctoringInfoData(courseId, username)`
(username already in scope from the `courseHomeMeta` read), and the gate
becomes `(!enableProctoredExams || !isProctoringInfoPending)`. Same key as
the panel's call → one fetch. `useSelector` and the `react-redux` import leave
the file.

### 4. `ProductTours.jsx` — reader 2

Same hook, `enabled: outlineTabActive` so no proctoring request fires on
other tabs (today the panel only mounts on the outline tab). **Username
source:** the panel keys on the `courseHomeMeta` username (masquerade-aware);
`ProductTours` currently has only `getAuthenticatedUser().username`. Using
that would produce a second key/fetch under masquerade and a wrong "settled"
read. Take the `courseHomeMeta` username instead. **Landed as: `ProductTours`
reads `useModel('courseHomeMeta', courseId).username` itself** (the plan's
`courseHomeUsername` prop from `LoadedTabPage` was dropped in review as
plumbing for its own sake; the extra `useModel` site is one more for #1977's
sweep). `useSelector` + `react-redux` leave the file.

### 5. Delete the slice

- `course-home/data/slice.js` — delete (dead fields go with it).
- `course-home/data/index.js` — delete (only re-exported the reducer).
- `store.ts` — drop `courseHome`; the store is `models` + `specialExams` +
  `plugins`.
- `setupTest.js` `initializeTestStore` — drop `courseHome`.
- `constants.ts` — `LOADED` may lose its last importer; check before removing
  (`LOADING`/`FAILED` have other users).

## Behavior changes (decision doc)

1. Non-404 proctoring-info failures are now logged (via the app
   `QueryCache.onError`) instead of silently swallowed; timing is unchanged
   (`retry: false`, settle on first outcome). See "Settled vs. error".
2. Under masquerade `ProductTours` now keys on the masqueraded username like
   the panel does (today it read a Redux flag that was username-agnostic, so
   this only changes which request dedupes, not what renders).
3. The proctoring request no longer fires when `ProductTours` is on a
   non-outline tab — it never did; `enabled: outlineTabActive` preserves that.
