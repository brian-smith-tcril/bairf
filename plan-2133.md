## Scope revision (2026-10-14, after the first implementation)

The first implementation (steps 1–7 below) gave only the three queries with an
imperative site a `queryOptions` function and switched only the
`getQueryData` / `setQueryData` sites to `xQuery(...).queryKey`. Review found
that this left every key spelled two ways in source — `coursewareMetadataQuery(courseId).queryKey`
at a write in `useSaveIntegritySignature`, `coursewareQueryKeys.metadata(eventCourseId)`
at an invalidation in `useIFrameBehavior.ts` — and asked what the key factories
still bought if the query function's key is the one call sites use. Survey:

- The factories' `all` prefix is referenced only inside the factories; no
  `removeQueries` / `resetQueries` / prefix-scoped `invalidateQueries` exists.
- The `appId` prefix is the one thing worth keeping (a QueryClient shared with
  another app under the frontend-base shell must not collide); it survives in
  the literal.
- JavaScript callers (`celebration/utils.jsx`, `streak-celebration/utils.jsx`,
  14 JS test files) can call `xQuery(id).queryKey` as well as a factory.
- No ADR, README or plugin export names the factories; #2083 only set the
  `string` / `string | undefined` seam.

Settled: one commit, full key literal in each function, revisit after the
amend if it reads badly. Revisited: the feature name repeated in every function
(twice in courseware-search), so each hooks file now has one module-level
const named for the feature (`coursewareKey = [appId, 'courseware'] as const`
and so on) that the functions spread. The layer now:

1. gives every query a `queryOptions` function (11 more: six course-home tabs,
   two courseware-search, recommendations, tours, sidebar toggles), named
   `useX` ↔ `xQuery`, with the key written as
   `[appId, '<feature>', …] as const` inside it;
2. switches every key use outside its own function — imperative reads and
   writes, the 7 `invalidateQueries` in source, the 3 JavaScript source lines,
   every test — to `xQuery(...).queryKey`;
3. deletes the five `queryKeys.ts` modules.

Test files that `jest.mock` a hooks module with a bare factory and whose code
under test now reaches a query function spread `jest.requireActual` first
(`useIFrameBehavior.test.js`). The one local that shadows an imported query
function (`courseHomeMetaQuery`, a query *result*, in
`CourseBreadcrumbsSlot/index.test.tsx`'s gate component) is renamed
`courseHomeMetadataQuery`; the same-named locals in `useIsCourseLoaded`,
`CoursewareContainer.tsx` and `CourseExit.jsx` do not import the function and
are left alone.

The decisions below (D1–D7) stand where they still apply; D1's "no builder for
the sidebar toggles or other course-home hooks" is superseded by (1).

## How it works today

**The library side.** `@tanstack/react-query` 5.104.2 is installed
(`package.json` says `^5.90.19`). `queryOptions(...)` returns its argument
unchanged at runtime (`queryOptions.js`: `return options;`) but typed as the
options `& QueryKeyWithDataTag<TQueryKey, TQueryFnData, TError>`, where

```ts
type DataTag<TType, TValue, TError = UnsetMarker> = TType & {
  [dataTagSymbol]: TValue;
  [dataTagErrorSymbol]: TError;
};
```

The two symbols are declared but never set on an object, so a tagged key is
the same array at runtime and hashes the same as the raw tuple. The reader and
writer on `QueryClient` are generic over the key:

```ts
getQueryData<TQueryFnData = unknown, TTaggedQueryKey extends QueryKey = QueryKey,
  TInferredQueryFnData = InferDataFromTag<TQueryFnData, TTaggedQueryKey>>(queryKey: TTaggedQueryKey): TInferredQueryFnData | undefined;
setQueryData<…same three…>(queryKey: TTaggedQueryKey, updater: Updater<NoInfer<TInferredQueryFnData> | undefined, …>, …): …;
```

`InferDataFromTag` yields the tagged value when the key carries one and falls
back to the hand-written `TQueryFnData` (default `unknown`) when it does not.
So a raw key makes the call site name the type, and a wrong name compiles; a
tagged key makes the call site infer it, and a wrong *key* fails to compile.

The docs' TypeScript page, section "Typing Query Options"
(https://tanstack.com/query/latest/docs/framework/react/typescript#typing-query-options),
states it verbatim:

> Further, the `queryKey` returned from `queryOptions` knows about the
> `queryFn` associated with it, and we can leverage that type information to
> make functions like `queryClient.getQueryData` aware of those types as well:
>
> ```ts
> const data = queryClient.getQueryData(groupOptions().queryKey)
> //     ^? const data: Group[] | undefined
> ```
>
> Without `queryOptions`, the type of `data` would be `unknown`, unless we'd
> pass a generic to it:
>
> ```ts
> const data = queryClient.getQueryData<Group[]>(['groups'])
> ```
>
> Note that type inference via `queryOptions` does _not_ work for
> `queryClient.getQueriesData`, because it returns an array of tuples with
> heterogeneous, `unknown` data.

## Findings that shape the work

1. **Two test generics name shapes that exist nowhere else.** Lines 170 and
   943 of `apiHooks.test.tsx` and the updater annotation in
   `DiscussionsProvider.test.tsx` declare one-field object types inline. They
   compile because the raw key gives `getQueryData` nothing to check against.
   This is the hazard the issue describes, in the repo's own tests.

2. **Two test seeds are deliberately partial.** `apiHooks.test.tsx:959`
   seeds the courseware metadata entry as `{ userNeedsIntegritySignature: true }`
   with a comment saying the hook patches only that field; the bookmark test
   seeds a sequence entry whose `sequence` is `{}`. `CoursewareMeta` has about
   thirty required fields and `SequenceMetadata` twelve. On the project's
   TypeScript 4.9.5 a `setQueryData` value is unchecked even under a tagged
   key (finding 8), so both seeds compile today whichever key they use; they
   stop compiling the day TypeScript passes 5.4 if they are under a tagged
   key by then. The read sites beside them (943, 27) are in the hand-typed
   table. Full-shape seeds are available in both suites: `apiHooks.test.tsx`
   already calls `normalizeSequenceMetadata(Factory.build('sequenceMetadata', …))`
   (lines 235, 571) and `Factory.build('courseMetadata', …)` has a
   `user_needs_integrity_signature` field (`courseMetadata.factory.js:65`),
   fed through `normalizeCoursewareMeta({ data, headers })`.

3. **The sidebar outline's `null` is real and lives in the fetcher.**
   `getCourseOutline` (`api.js:104`) returns `null` when the response has no
   `blocks`. The hook's `useQuery<CourseNavigationOutline | null>` carries
   it; the source read at line 224 repeats it; the test read at 638 drops it
   and adds `!`. A builder with `queryFn: (): Promise<CourseNavigationOutline | null>`
   puts the union in one place and both reads inherit it.

4. **`updateSequenceUnit` types its key parameter by the factory.** With the
   factory's return type the body has to say `<SequenceMetadataData>` itself.
   A `DataTag` is an intersection with two symbol properties, so a raw tuple
   is not assignable to the tagged type: if the parameter becomes the tagged
   key, every caller has to pass one (the two source callers and test line
   716).

5. **`useCourseHomeMeta`'s `RequestError` is load-bearing and cannot be
   mixed with a builder.** `RequestError` (`data/http-error.ts`) is
   `{ response?: { status?; data? } }` — every field optional, and it does not
   extend `Error`. Probed with the project's compiler (TypeScript 4.9.5,
   `strict`, `strictFunctionTypes: false`):
   - `UseQueryResult<CourseHomeMeta>` (the default error) is not assignable to
     `UseQueryResult<CourseHomeMeta, RequestError>`: "Type 'Error' has no
     properties in common with type 'RequestError'" (the weak-type check). So
     `TabPage.tsx`'s `CourseStatus` rejects a hook that drops the generic.
   - The reverse fails too: `RequestError` lacks `name` and `message`. So the
     hook's result cannot be handed to anything typed with the default error.
   - Spreading a data-only `queryOptions(...)` into
     `useQuery<CourseHomeMeta, RequestError>` does not compile: the builder's
     callback-typed options (`staleTime`, `retry`, `enabled`, …) carry
     `Query<…, Error, …>` and the explicit generics demand
     `Query<…, RequestError, …>`.
   - `queryOptions<CourseHomeMeta, RequestError, CourseHomeMeta, ReturnType<typeof courseHomeQueryKeys.metadata>>({ … })`
     compiles. There is no option field that sets `TError`; it is only ever
     the second explicit type argument, and TypeScript has no partial
     inference, so all four must be spelled.
   Nothing reads a query's `error` through the type: `TabPage.tsx` and
   `CourseAccessErrorPage.jsx` go through `getErrorDetail(error: unknown)` /
   `isError` / `isPending`, and no other TypeScript file names `RequestError`
   or a two-argument `UseQueryResult`.

6. **`invalidateQueries`, `removeQueries` and `setQueryDefaults` take
   `QueryKey`.** A tagged key extends the tuple, so the four sites that pass
   one (`apiHooks.ts:231`, test 722, `seedQueryData`) need no change.

7. **No non-test site outside `courseware/data/apiHooks.ts` is TypeScript.**
   The bookmark hook passes a key but never reads or writes the cache itself.
   So the source conversion is one file plus one call site.

8. **The project's TypeScript predates what the installed TanStack typings
   assume, and `skipLibCheck` hides it.** `@tanstack/query-core` 5.104.2's
   `.d.ts` uses the `NoInfer` builtin (TypeScript 5.4) three times, including
   on `setQueryData`'s updater and return. The docs' TypeScript page says:
   "TanStack Query follows DefinitelyTyped's support window and supports
   TypeScript versions released within the last 2 years. At the moment, that
   means TypeScript **5.7** and newer." The project runs 4.9.5
   (`npm run types` is `tsc --noEmit`; TypeScript is transitive via
   `@openedx/frontend-build` 14.6.17 → `@edx/typescript-config` 1.1.0, whose
   every published version pins `^4.9.4`; frontend-base 1.0.1 ships
   `^5.6.3`). `@edx/typescript-config` sets `skipLibCheck: true`, so the
   unresolved `NoInfer` is not an error; it resolves to `any`. Probed with
   the project's flags:
   - `getQueryData(taggedKey)` with no contextual type infers the data type.
     `getQueryData<T>(rawKey)` gives `T | undefined`; `getQueryData(rawKey)`
     gives `unknown`. Reads work both ways.
   - `setQueryData`'s updater parameter is `any` under a tagged key **and**
     under today's hand generic; `setQueryData(key, { nope: 1 })` compiles
     under both. So the six `<SequenceMetadataData>` / `<CoursewareMeta>`
     generics on write sites type nothing today; the writes are unchecked
     and `noImplicitAny: false` keeps that quiet.
   Consequence for this issue: the conversion is right as written, but the
   write-side safety it is meant to buy arrives only when TypeScript moves to
   ≥ 5.4 — which the frontend-base port (#1905) does. Until then the layer
   removes the hand generics, gets inference on reads, and leaves the writes
   as unchecked as they are now. The decisions doc has to say so, and the
   verify step cannot claim a wrong update fails to compile.

## Decisions to settle

**D1 — which builders to add.** The hook-to-builder naming is already fixed
by the five that exist (`useSequenceMetadata` ↔ `sequenceMetadataQuery`,
`useMinimalCourseOutline` ↔ `minimalCourseOutlineQuery`): drop the `use`,
append `Query`. Needed by a site in the survey:

| Builder | For | Sites |
|---|---|---|
| `coursewareMetadataQuery(courseId)` | `useCoursewareMetadata` | source 304; tests 943, 959 |
| `courseOutlineStructureQuery(courseId)` | `useCourseOutlineStructure` | source 224/229; tests 638, 644, 821 |
| `courseHomeMetaQuery(courseId)` | `useCourseHomeMeta` | tests 170, `CelebrationModal.test.tsx` 49/62, `DiscussionsProvider.test.tsx` 106 |

`useCoursewareOutlineSidebarToggles` has no imperative site and gets no
builder (nothing would use it). The other course-home hooks likewise. The
three hooks keep their signatures and spread the builder the way the five
existing ones do.

**D2 — `courseHomeMetaQuery` and the error type (finding 5; settled 2026-10-14:
(b)).** The earlier draft's "builder types the data only, hook keeps its
generics" does not compile and is withdrawn. What is left:
- **(a)** `courseHomeMetaQuery` with all four generics spelled:
  `queryOptions<CourseHomeMeta, RequestError, CourseHomeMeta, ReturnType<typeof courseHomeQueryKeys.metadata>>({ … })`.
  The hook spreads it with no generics; `TabPage.tsx` is untouched; the key's
  error tag is `RequestError`, which nothing reads. One builder that looks
  unlike the other five, to keep an error type whose only consumer is a prop
  declaration.
- **(b)** Drop `RequestError` from the hook (`useQuery({ ...courseHomeMetaQuery(courseId!), enabled })`,
  the shape of the five courseware builders) and from `CourseStatus` in
  `TabPage.tsx` (`metadataQuery: UseQueryResult<CourseHomeMeta>`); the
  `RequestError` import there goes with it. `getErrorDetail` and
  `getResponseStatus` already take `unknown` and cast to `RequestError`
  inside, so no read changes. `RequestError` stays what it is: the structural
  view the two helpers apply, not a claim the hook makes about what it
  throws (it throws axios errors, which do carry `response`). This also ends
  the situation in finding 5 where the metadata query's result cannot be
  handed to anything typed with the default error.
- **(c)** Leave course-home alone; `CelebrationModal.test.tsx` 49/62,
  `apiHooks.test.tsx` 170 and `DiscussionsProvider.test.tsx` 106 keep their
  hand types as survivors. Rejected: 170 and 106 are two of the three
  invented shapes in finding 1.

**D3 — `updateSequenceUnit`'s key parameter (finding 4; settled 2026-10-14: (a), revisit in review if it reads badly).**
- **(a)** Type the parameter `ReturnType<typeof sequenceMetadataQuery>['queryKey']`
  and drop the body's generic; the two source callers and test 716 pass
  `sequenceMetadataQuery(sequenceId, isPreview).queryKey`. Minimal, and the
  key is still spelled in exactly one place (`coursewareQueryKeys.sequence`,
  via the builder).
- **(b)** Change the signature to `(queryClient, sequenceId, isPreview, unitId, patch)`
  and build the key inside. Fewer characters at the callers, but a signature
  change the issue does not ask for.

**D4 — the two partial seeds (finding 2; settled 2026-10-14: (b)).** Both
suites seed the full shape under the tagged key: the integrity-signature
suite with `normalizeCoursewareMeta` over `Factory.build('courseMetadata', { user_needs_integrity_signature: true })`,
the bookmark suite with `normalizeSequenceMetadata` over a factory-built
sequence whose units carry the ids the suite uses. The integrity suite's
comment saying the fragment is deliberate goes (its reason, that
normalization is covered elsewhere, is unaffected). Rejected: (a) seeding
under the raw key and reading under the tagged one — "fewer lines" was its
only case once the issue's out-of-scope line was read as being about
production cache writes, which it is; a test fixture is not one. Rejected:
(c) `as CoursewareMeta` on the fragment, a wrong type that compiles. Note
from finding 8: on 4.9.5 the fragments compile under either key; (b) is what
keeps them compiling after the TypeScript upgrade as well.

**D5 — the celebration and streak writers (JavaScript).** Out of reach until
those files are TypeScript; they are the survivors the issue's verify line
allows ("each survivor has a reason"). No change, and no `courseHomeMetaQuery`
import into a `.jsx` file just to look consistent.

**D6 — the `| null` on the sidebar outline (finding 3).** The builder's
`queryFn` return type carries it; the source read at 224 drops its generic and
keeps its `if (!cachedOutline) return`; the test helper at 638 drops both
the generic and the `!` is kept (it asserts the seed happened). No semantic
change.

**D7 — local key helpers in tests.** Where a suite names a key once
(`outlineQueryKey`, `sequenceKey`, `metadataKey`, `queryKey` in
`CelebrationModal.test.tsx`), the constant becomes the builder's `.queryKey`
and every use in the suite — typed reads, untyped `toBeUndefined` reads,
`removeQueries`, seeds under D4(a) excepted — goes through it. One spelling
per suite.
