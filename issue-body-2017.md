Part of #1946 — Redux → React Query migration (Stage 1).

**Goal:** convert the plugin-store override registry off Redux to a React context / module-level registry, so the `plugins` reducer can leave `src/store.ts`.

**Context — this is *not* `@openedx/frontend-plugin-framework` (FPF).** FPF is the declarative `PluginSlot` system (`PluginSlot` / `DIRECT_PLUGIN` / `PLUGIN_OPERATIONS`), used in `src/plugin-slots/*` and config-driven — it never touches `state.plugins`. `generic/plugin-store` is a separate, bespoke Redux "override-method" registry: `registerOverrideMethod` stores function references by plugin+method (hence the serializable-check exemption in `store.ts`), and `usePluginsCallback(name, default)` folds registered overrides over a default. Its only in-repo consumer is the iframe-URL override in `src/courseware/course/sequence/Unit/index.jsx`.

**Why Stage 1:** this is learning's *own* Redux. Getting `redux` / `react-redux` / `@reduxjs/toolkit` out of learning's `package.json` must happen before the frontend-base move, so this slice has to go regardless of the special-exams blocker. Only the *later* reshaping of the override API onto the frontend-base `Slot` system is Stage 2.

**Tasks**
- Replace the `plugin` slice + `registerOverrideMethod` + `usePluginsCallback` with a React context / module-level registry.
- Remove the `plugins` reducer from `store.ts` (and its `ignoredActions` serializable exemption).
- Keep the single in-repo consumer (`Unit/index.jsx` iframe-URL override) working.

**Open question (settle when scoped):** whether the external `registerOverrideMethod` dispatch contract can be preserved in Stage 1, or whether that reshaping must wait for the Stage-2 Slot migration — the redux removal itself does not.

**Verify:** iframe-URL override still applies; `plugins` reducer gone from the store; no `react-redux` in the plugin-store.

Prerequisite for #1978's "specialExams-only" store endpoint.

Investigation findings that settle the open question above and shape the task list:

- **This is client state, so it goes to context, not React Query.** Nothing in the registry is fetched, cached or invalidated: plugins (descendants) contribute overrides and the host component (an ancestor) reads them. That is the React-context half of OEP-0067 ADR-0010. A `PluginOverridesProvider` holds the registry in `useState` and is mounted once at the route root beside `ToastProvider`, the migration's established client-state pattern (state in the provider, use in the consumer).
- **The generic contract is preserved; only the transport changes.** The `registerOverrideMethod({ pluginName, methodName, method })` payload, the fold (`defaultMethod()` first, then each registered override receives the previous result, in registration order), overwrite on re-register, and persistence after the registrar unmounts all stay exactly as today. The registry is a public extension surface and operator `env.config.jsx` files are unsearchable, so replacing it with per-behavior typed hooks would break plugins we can't see. Functions in state were only awkward under Redux's serializability rule (hence the `store.ts` middleware exemption); context has no such rule, so the generic shape costs nothing.
- **Plugins register from their own effect, imperatively.** `useDispatch()` + `dispatch(registerOverrideMethod(...))` becomes `usePluginOverrides()` + `registerOverrideMethod(...)`; the plugin keeps ownership of its effect deps. An effect-owning convenience hook can come later without breaking this.
- **No implicit cleanup on unmount, but an opt-in `unregisterOverrideMethod`.** `SequenceContent` renders `<Unit key={unitId}>`, so the slot widget remounts per unit; for a registrar gated behind an async fetch (the known external plugin), implicit cleanup would make the next unit's iframe load un-overridden first and then reload once the plugin re-registers. Today the previous unit's override covers that first render. So the provider does not clean up on its own, and plugins that want cleanup return `unregisterOverrideMethod` from their effect.
- **Names drop the Redux vocabulary.** `generic/plugin-store` → `generic/plugin-overrides`; `PluginOverridesProvider` / `usePluginOverrides()`. `registerOverrideMethod` keeps its name (it describes what the plugin does, not the transport), and the host-side `usePluginsCallback(methodName, defaultMethod)` keeps its signature, so `Unit/index.jsx` changes only an import path.
- **`store.ts` loses its only middleware option along with the reducer** (the serializable-check exemption existed for this slice alone), leaving `models` + `specialExams`.

# Plan: #2017 — Move the plugin override registry off Redux onto React context

## Context

Part of epic #1946 (Redux → React Query, Stage 1). `generic/plugin-store` is
the last learning-owned reducer besides `models` (which #1977 removes), so this
is a prerequisite for #1978's "store = `specialExams` only" endpoint. It is
**not** `@openedx/frontend-plugin-framework` (FPF): FPF decides *where a plugin
renders*; this registry is a side channel a rendered plugin uses to *change host
behavior elsewhere in the tree*. Both arrived in the same commit (PR #1330,
2024-03-27, which also added FPF to `package.json`).

**Which half of OEP-0067 ADR-0010 this is.** The registry holds no server
state — nothing is fetched, cached or invalidated — so React Query does not
apply. It is client state contributed by descendants (plugins) and read by an
ancestor (the host component), which is exactly what React context is for.
The provider owns the state; plugins write to it from effects; the host reads
it during render. Same split as `ToastProvider` (state in the provider, use in
the consumer).

**Generality is preserved on purpose.** We know of one registrar and one
override point, but the registry is a public extension surface: any operator's
`env.config.jsx` plugin may register other method names or override
`getIFrameUrl` differently, and those files are untracked and unsearchable.
Replacing the registry with per-behavior typed hooks would force a new host
hook for every such use and break plugins we can't see. So the *contract* stays
generic — `(pluginName, methodName) → method`, folded over a default — and only
the *transport* changes (Redux dispatch → context). What made functions-in-state
awkward was Redux's serializability rule (hence the middleware exemption in
`store.ts`); React context has no such rule, so the generic shape costs nothing.

The baseline example (`env.config.jsx`, posted on the issue) is the reference
for "functional equivalent": ported to the new API it must behave identically.

### How it works today

Three files, no tests of their own:

- `slice.js` — `createSlice({ name: 'plugin', initialState: {} })` with one
  reducer, `registerOverrideMethod({ pluginName, methodName, method })`, which
  sets `state[pluginName][methodName] = method`. Registering the same pair
  again **overwrites**. Nothing removes an entry.
- `hooks.js` — `usePluginsCallback(methodName, defaultMethod)`:
  `useSelector(state => () => fold(state.plugins), shallowEqual)`. The fold runs
  `defaultMethod()` first, then every registered `plugin[methodName]` receives
  the previous result, in `Object.values` insertion order. The selector returns
  a fresh function each run, so `shallowEqual` never matches and the consumer
  re-renders on every store change.
- `store.ts` — mounts the reducer as `plugins` and carries the file's **only**
  middleware option: the serializable-check exemption for
  `plugin/registerOverrideMethod` / `plugins` (the payload is a function).

**Consumer (one in-repo):** `courseware/course/sequence/Unit/index.jsx` —
`const getUrl = usePluginsCallback('getIFrameUrl', () => getIFrameUrl({ id, view, format, examAccess, jumpToId, preview }))`.
The default closure is re-created per render, so overrides compose over the
unit's current props.

**Registrar (none in-repo; one known external):** the published
`@edx/unit-translation-selector-plugin` (npm 0.5.0; source repo is private).
An FPF `DIRECT_PLUGIN` in `org.openedx.frontend.learning.unit_title.v1`, so it
renders inside the app's react-redux `Provider`. It calls `useDispatch()` and,
in a `useEffect` keyed on `[courseLanguage, selectedLanguage]`, dispatches
`registerOverrideMethod({ pluginName: id, methodName: 'getIFrameUrl', method })`,
importing the action creator from the **`@src/generic/plugin-store` alias** (it
compiles against learning's source via `env.config.jsx`). `id` is the widget id
FPF passes from the slot config. Registration is gated behind an async config
fetch (the widget renders nothing until `fetchTranslationConfig` resolves).

**Semantics observed (the contract to preserve):**

1. Registration from a slot-rendered component inside the React tree.
2. Keyed by `(pluginName, methodName)`, overwrite on re-register; latest wins.
3. Fold order: default first, then each override receives the previous result.
4. **No unregister.** An override outlives the component that registered it.
5. The consumer's default closure is evaluated per call (sees current props).

**Test surface today:** `setupTest.js` `jest.mock`s the module so
`usePluginsCallback` returns the default callback untouched — because
`initializeTestStore` never mounts a `plugins` reducer, the real hook would
throw on `Object.values(undefined)`. No test exercises the registry.

## Design decisions

### D1 — A context provider holds the registry

`PluginOverridesProvider` keeps `Record<pluginName, Record<methodName, method>>`
in `useState`. Consumers read it with `useContext`. Mounted once at the route
root in `src/index.jsx` beside `ToastProvider` (any ancestor of the host
component works; root matches the sibling and means every slot in the app can
register). The alternative — a module-level `Map` with `useSyncExternalStore`,
which would let `registerOverrideMethod` stay a plain importable function — has
no precedent in this repo and would widen the contract to registration from
outside React; rejected for Stage 1.

### D2 — Plugins register imperatively from their own effect

Today's shape is "action creator + dispatch inside the plugin's `useEffect`".
The context equivalent is "setter from context + call inside the plugin's
`useEffect`": the plugin keeps ownership of *when* it registers (its deps), and
the payload `{ pluginName, methodName, method }` is unchanged.

```js
// before                                   // after
const dispatch = useDispatch();              const { registerOverrideMethod } = usePluginOverrides();
useEffect(() => {                            useEffect(() => {
  dispatch(registerOverrideMethod({ … }));     registerOverrideMethod({ … });
}, [deps]);                                  }, [deps]);
```

An effect-owning convenience hook (`useOverrideMethod(payload)`) can be added
later without breaking this; not in this PR.

### D3 — Additive `unregisterOverrideMethod`; no implicit cleanup

Today nothing removes an entry, and the host relies on that: `SequenceContent`
renders `<Unit key={unitId}>`, so `Unit` and the slot widget remount on every
unit change. For a registrar gated on an async fetch (the translations plugin),
implicit cleanup-on-unmount would mean unit B's first render has no override →
iframe loads untranslated → fetch resolves → register → URL changes → iframe
reloads. Today unit A's override (closing over course-level language values)
covers B's first render and the iframe loads once. So the provider does **not**
clean up on its own. It does expose `unregisterOverrideMethod({ pluginName, methodName })`
so a plugin that wants cleanup can return it from its effect — a React-idiomatic
opt-in that the Redux version had no room for.

### D4 — Names drop the Redux vocabulary, keep the plugin-facing verbs

- Directory `generic/plugin-store/` → **`generic/plugin-overrides/`** ("store"
  is the word we're removing; the break is happening anyway, so the import-path
  change rides along in the same major and is one line in the migration note).
- `PluginOverridesProvider`, `usePluginOverrides()` (context value:
  `{ overrideMethods, registerOverrideMethod, unregisterOverrideMethod }`).
- `registerOverrideMethod` keeps its **name and payload** — it describes what
  the plugin does, not the transport.
- Host-side `usePluginsCallback(methodName, defaultMethod)` **keeps its name
  and signature**; it was never Redux vocabulary and `Unit/index.jsx` stays
  byte-identical. (Renaming it is possible later; not a de-Redux concern.)

### D5 — Throw outside the provider

`usePluginOverrides` / `usePluginsCallback` outside `PluginOverridesProvider`
throw, matching `useToast`. The provider is mounted at the root in the app and
in `setupTest`'s `render` wrapper; the only tests rendering a real `Unit`
(`Unit/index.test.jsx`, the `Sequence`/`Course` suites) go through that
wrapper, and `CoursewareContainer.test.jsx` mocks `Unit`.

### D6 — Stack placement

A layer on top of #2081 in stack #2080, like every layer so far, rather than a
standalone PR off `master`. The only overlap with the open layers is the
`store.ts` reducer map (#2081 removes `courseHome`; this removes `plugins`) —
trivial either way.

## 1. `generic/plugin-overrides/PluginOverridesContext.tsx` (new, TS)

Replaces `plugin-store/{slice,hooks,index}.js`; `index.ts` re-exports. Shape,
following `ToastContext.tsx`:

```ts
export type OverrideMethod<T = unknown> = (previousResult: T) => T;
type OverrideMethods = Record<string /* pluginName */, Record<string /* methodName */, OverrideMethod<any>>>;

interface PluginOverridesContextValue {
  overrideMethods: OverrideMethods;
  registerOverrideMethod: (payload: { pluginName: string; methodName: string; method: OverrideMethod<any> }) => void;
  unregisterOverrideMethod: (payload: { pluginName: string; methodName: string }) => void;
}

export const PluginOverridesProvider = ({ children }) => {
  const [overrideMethods, setOverrideMethods] = useState<OverrideMethods>({});
  const registerOverrideMethod = useCallback(({ pluginName, methodName, method }) => {
    setOverrideMethods((current) => ({
      ...current,
      [pluginName]: { ...current[pluginName], [methodName]: method },
    }));
  }, []);
  const unregisterOverrideMethod = useCallback(({ pluginName, methodName }) => {
    setOverrideMethods((current) => {
      const { [methodName]: _removed, ...rest } = current[pluginName] ?? {};
      return { ...current, [pluginName]: rest };
    });
  }, []);
  const value = useMemo(() => ({ overrideMethods, registerOverrideMethod, unregisterOverrideMethod }), [overrideMethods]);
  return <PluginOverridesContext.Provider value={value}>{children}</PluginOverridesContext.Provider>;
};

export const usePluginOverrides = () => { /* useContext; throw outside provider */ };

export const usePluginsCallback = <T,>(methodName: string, defaultMethod: () => T): () => T => {
  const { overrideMethods } = usePluginOverrides();
  return () => Object.values(overrideMethods).reduce(
    (result, plugin) => (plugin[methodName] ? plugin[methodName](result) : result),
    defaultMethod(),
  );
};
```

- The fold is the same behavior as `hooks.js`: default first, insertion order,
  only plugins that define `methodName`.
- The setters are stable (`useCallback([])`), so a plugin effect listing them in
  deps does not loop. Re-registering (even the same function) produces a new
  `overrideMethods` object and re-renders consumers — parity with today's
  every-dispatch re-render; not optimized here.
- Typing: the registry is heterogeneous by nature (a method's value type is
  whatever the host's default returns for that name), so the stored map is
  `OverrideMethod<any>` at the boundary and `usePluginsCallback<T>` gives the
  host a typed `() => T`. That is a precise boundary cast at one place, not
  `as any` sprinkled at call sites.

## Decision doc (for the PR body)

1. Client state → context, not React Query (nothing is fetched); provider at
   the root beside `ToastProvider`.
2. Generic `(pluginName, methodName) → method` contract preserved — a public,
   unsearchable extension surface; functions in context state need no
   serializability exemption.
3. Plugins register imperatively from their own effect (`usePluginOverrides()`);
   payload unchanged; effect-owning hook deferred.
4. No implicit cleanup (mechanism: keyed `Unit` remount + async-gated
   registrar → double iframe load); additive `unregisterOverrideMethod`.
5. `plugin-store` → `plugin-overrides`; `usePluginsCallback` keeps its
   signature so `Unit/index.jsx` changes only an import path.
6. Throw outside the provider; `setupTest` provides it and the module mock is
   deleted so tests run the real code.
7. `store.ts` loses its only middleware option along with the reducer.
8. BREAKING footer; README with the migration note; coordinate with #1977's
   break of the same plugin.
9. Heterogeneous registry typed `OverrideMethod<any>` at the boundary,
   `usePluginsCallback<T>` typed at the host; no `as any` at call sites.
