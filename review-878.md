### 4. What frontend-base makes public about widget ids, and whether aliases cover them

Status: resolved, no comment (feeds entry 3)
Rests on: openedx/frontend-base at ae5ec93 (2026-10-26): runtime/slots/Slot.tsx, runtime/slots/hooks.ts, runtime/slots/widget/types.ts, runtime/slots/widget/utils.tsx, docs/decisions/0009-slot-naming-and-lifecycle.rst, docs/decisions/0016-shell-layout-replacement-seams.rst; openedx/frontend-base#178

Aliases are slot-only. #178 (brian-smith-tcril, merged 2026-02-26, port of frontend-plugin-framework#110) added `idAliases?: string[]` to `<Slot>`; `useSlotOperations` passes `[id, ...idAliases]` to `getSlotOperations`, which matches an operation's `slotId` against that list. Widgets have no equivalent: a widget has one `id`, and the four relative operations resolve `operation.relatedId` by exact match in `findRelatedWidgetIndex`.

Widget ids are a targeting surface: of the seven `WidgetOperationTypes`, five take `relatedId` (`INSERT_AFTER`, `INSERT_BEFORE`, `REPLACE`, `REMOVE`, `OPTIONS`); only `APPEND` and `PREPEND` do not. A site config that hides, replaces, reorders around, or passes options to the header links names `headerLinkCourses.v1` or `headerLinkDiscover.v1`.

The written contract covers slots, not widgets. ADR 0009 defines the id format (`org.openedx.frontend.slot.<module>.<identifier>.<version>`), says a slot's contract is its props, its page location and the general kind of content, and states that "the presence, absence, shape, or implementation of child widgets ... is explicitly not part of the slot's contract, and may change at any time". That sentence is about what bumps a slot's version, not a licence to rename widget ids. ADR 0016 treats default widget ids as public in practice: "All existing inner slot ids and default widget ids are preserved", and a new widget id is counted as "the public surface gains ... one new widget id ... following the reverse-DNS-versioned convention from ADR 0009". No ADR gives widget ids a deprecation path, and with no alias a renamed widget id simply stops matching old `relatedId`s.

Net for entry 3: renaming the two header widget ids is a break for any 1.0.0 site config that targets them, with no compatibility shim available, so it is a documented `!` change in the 2.0.0 line or not done. Adding `idAliases` for widgets in frontend-base is the shim that does not exist yet; filed as openedx/frontend-base#334 (2026-10-30), implemented in openedx/frontend-base#335 (open, 2026-10-31).

Follow-up (Brian asked whether several operations could stand in for a widget alias). Checked in `runtime/slots/widget/utils.tsx` and `runtime/slots/utils.ts` at ae5ec93: `findRelatedWidgetIndex` returns null on a miss and every relative operation (`insertAfter`, `insertBefore`, `replace`, `remove`) is then a silent no-op; a widget carries exactly one `id`; and operations are gathered app by app in `siteConfig.apps` order, so the app's own operations run before an operator's and the app cannot sequence anything after them. The one shape that resembles an alias is a second, empty widget registered under the old id beside the real one under the new id: positional inserts against the old id keep working, but `REMOVE` on the old id removes only the empty anchor (the operator's hide stops hiding) and `REPLACE` on it renders the operator's widget next to the app's (a duplicate). Not a workaround. The real shim is `idAliases` on widgets in frontend-base: `findRelatedWidgetIndex` matching `relatedId` against `[id, ...idAliases]`, the mirror of #178.

### 5. Reordering the default header links moves plugins that insert relative to them

Status: posted https://github.com/openedx/frontend-app-learner-dashboard/pull/878#issuecomment-6540498868 (2026-10-31, points at the contract question); contract question filed as openedx/frontend-base#336 (settled 2026-10-31)
Rests on: src/widgets/LearnerDashboardHeader/app.tsx at aca7e369ba and at v1.0.0; PR body as of 2026-10-31; openedx/frontend-base at ae5ec93: runtime/slots/widget/types.ts, docs/decisions/0009-slot-naming-and-lifecycle.rst, docs/decisions/0016-shell-layout-replacement-seams.rst

Brian's question (2026-10-31): default content is outside the slot contract, but a plugin that wanted "after the last link" would `INSERT_AFTER` the Discover widget and one that wanted "before the first" would `INSERT_BEFORE` the Courses widget; after the reorder both land in the wrong place, which feels breaking unless it is explicitly said not to be.

Mechanism. aca7e36 keeps every widget id bound to the same link and changes only the declaration order of the three `APPEND`s in `app.tsx`, which is their render order: master and v1.0.0 are `headerLinkCourses`, `headerLinkPrograms`, `headerLinkDiscover`; the PR is `headerLinkDiscover`, `headerLinkCourses`, `headerLinkPrograms`. `INSERT_AFTER headerLinkDiscover.v1` therefore lands in position 2 of 3 and `INSERT_BEFORE headerLinkCourses.v1` lands in the same gap. Nothing throws or is dropped; the position is wrong. A plugin cannot say "last" with `APPEND` without depending on `siteConfig.apps` order, so naming the last default is the natural idiom.

Contract text. ADR 0009 section 2: "a given slot's content, default or otherwise, is explicitly not part of the slot's contract, and may change at any time" (by the letter, order is content, so no slot version bump). ADR 0016, scoped to the shell's header and footer only (Brian, 2026-10-31): "All existing inner slot ids and default widget ids are preserved. Plugins that target [them] continue to work without modification" (for the shell, ids are a compatibility surface; no ADR says so for any other app). The `INSERT_AFTER` comment in types.ts promises placement relative to the target id and says nothing about the target's own position. learner-dashboard documents none of its widget ids. Nobody has said which of the two a reorder falls under.

The PR body says it "only covers the new dashboard heading" and does not mention the header links being renamed or reordered; only the commit subject does.

Two axes. (a) frontend-base: write down either that relative operations place against the target's current position and an app's default order may change between versions, or that default ids and their order are public surface and a reorder is a major; a docs issue beside #334, not for 878. (b) 878 regardless: the repo is on 2.0.0-alpha and marks majors `feat!:` with a footer (aed66d1, 70576cf), so `feat!:` on aca7e36 with the old and new order in a BREAKING CHANGE footer costs nothing; the floor is the PR body naming the change.

### 9. The sticky heading's stuck-state detection is a hand-rolled sentinel and observer; Paragon has `Sticky`

Status: posted by Brian https://github.com/openedx/frontend-app-learner-dashboard/pull/878#discussion_r4525629339 (2026-11-10, comment review https://github.com/openedx/frontend-app-learner-dashboard/pull/878#pullrequestreview-5842902246, on the observer effect at `CoursesPanel/index.jsx` line 64): could Paragon's `Sticky` be used instead of a custom implementation
Rests on: src/containers/CoursesPanel/index.jsx, index.scss, index.test.jsx at 1d14a29dc6; openedx/paragon src/Sticky/index.jsx and index.scss on release-23.x (last change 477e1eec4d, 2025-10-14); the dashboard lock at @openedx/paragon 23.23.0

What the PR does: a zero-height `<div ref={sentinelRef} />` above `.course-list-heading-container`, an `IntersectionObserver` on it with default root and threshold, `isStuck` set when the sentinel leaves the viewport, and `.is-stuck` in `index.scss` drawing a 1px `light-400` bottom border and `box-shadow-down-1`. The container itself carries `position: sticky; top: 0; z-index: 2`, white background and vertical `spacer-2` padding.

What Paragon's `Sticky` does: a `div.pgn__sticky.pgn__sticky-top` with `position: sticky`, `top: var(--pgn-spacing-sticky-offset)` (or a spacer via `offset`), `display: flex; width: 100%; align-self: self-start`. In a `useLayoutEffect` it observes the sticky element itself with `threshold: [1]` and a `rootMargin` of minus (1 + computed top) pixels, so `intersectionRatio < 1` means pinned; that sets `pgn__sticky-shadow`, which is `box-shadow: var(--pgn-elevation-sticky-shadow-bottom)` (the two-layer sticky elevation token). No sentinel, no border. The `useLayoutEffect` is guarded on the ref; the test would mock `IntersectionObserver` the same way.

What a switch changes for this file: the sentinel div, the ref, the state and the effect go, and the heading container becomes `Sticky`'s child or `Sticky` takes its classes; the border and the `down-1` shadow in `.is-stuck` go in favour of Paragon's sticky shadow, unless the design asks for the border; `z-index`, background and padding stay as custom styles on the inner container (Paragon's class sets none of them); the three sticky-heading tests change to check `pgn__sticky-shadow` or go, since the behaviour is then Paragon's. The sticky scoping to the Courses section (entry 7 of the State) is unchanged either way: both pin inside `.course-list-container`. Waiting on ChrisChV.

Added (Brian, 2026-11-10, from the Figma stuck and unstuck frames): the mock's stuck bar spans the whole content area, Refine out past the course column over the sidebar column, and the stuck heading and icon render smaller than the unstuck ones; the stuck bar also has a bottom border and light shadow. The PR's bar stays at column width (the container is inside `.course-list-container` inside the main `Col`, and `position: sticky` keeps normal-flow width) and the heading is `h3` in both states; only the border and shadow match. Paragon's `Sticky` wrapper is `width: 100%` of its parent, so it does not give full width either. Full width while stuck needs the stuck state to drive a layout change (a breakout to the container edges, or `position: fixed` with the section scoping redone by hand), or the heading lifted above the `Row`, where scoping to the Courses section is the harder part. With the PR's own observer the stuck state is React state; with `Sticky` it is only the `pgn__sticky-shadow` class, readable from CSS alone (no callback, render prop or context in `src/Sticky/index.jsx`), so width and size changes would hang off a Paragon-internal class. Whether the bar should go full width is a question for the author and design ahead of the `Sticky` thread; nothing posted on it yet.
