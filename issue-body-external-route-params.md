`resolveRouteByRole(role, params)` fills `params` into an installed app's route and drops them when the role is provided by an absolute external URL, so a role whose route takes a param, a course id for instance, only resolves to a usable link while the app that declares it is installed. Found while porting Learning's progress tab (openedx/frontend-app-learning#2190, part of openedx/frontend-app-learning#1905), whose links resolve course-scoped roles. Related to #348, which asks whether a site can point an installed app's role at an external route at all.

## How a role with params resolves today

- A role is declared on a route, and the route's path decides which params the role takes: `/gradebook/:courseId` carries `org.openedx.frontend.role.gradebook` ([`src/routes.tsx`](https://github.com/openedx/frontend-app-gradebook/blob/f57f7adef252f0c779315f66abb402d383ccf483/src/routes.tsx#L6-L13) in openedx/frontend-app-gradebook), `instructor-dashboard/:courseId` carries `org.openedx.frontend.role.instructorDashboard` ([`src/routes.tsx`](https://github.com/openedx/frontend-app-instructor-dashboard/blob/fc556946e9ec9cfbff5e9e274f89bdefd724e13c/src/routes.tsx#L77-L81) in openedx/frontend-app-instructor-dashboard).
- A caller passes those params: [`resolveRouteByRole(gradebookRole, { courseId })`](https://github.com/openedx/frontend-app-instructor-dashboard/blob/fc556946e9ec9cfbff5e9e274f89bdefd724e13c/src/grading/components/GradingActionRow.tsx#L24-L32) in the instructor dashboard, [`resolveRouteByRole(instructorDashboardRole, { courseId })`](https://github.com/openedx/frontend-app-gradebook/blob/f57f7adef252f0c779315f66abb402d383ccf483/src/components/GradebookHeader/index.jsx#L28-L29) in gradebook.
- [`resolveRouteByRole`](https://github.com/openedx/frontend-base/blob/72d70535cf77e98be8f859aa5746c3dddb4d02d2/runtime/routing/utils.ts#L74-L100) returns `isInternal ? generatePath(path, params) : path`. A path in this site has its params filled; anything else is returned as configured, and the params are discarded without a warning. The TSDoc says so ("an external URL is returned as configured"), and [a test](https://github.com/openedx/frontend-base/blob/72d70535cf77e98be8f859aa5746c3dddb4d02d2/runtime/routing/utils.test.ts#L123-L126) pins it by passing `{ courseId: 'c1' }` for a role whose external URL is `https://apps.example.com/profile/` and expecting that URL back.
- [`ExternalRoute`](https://github.com/openedx/frontend-base/blob/72d70535cf77e98be8f859aa5746c3dddb4d02d2/types.ts#L11-L14) is a role and a URL. An external route written as `https://lms.example.com/courses/:courseId/progress` comes back with the literal `:courseId` in it.
- The caller cannot tell which case it is in before it calls: who provides a role is a property of the site, not of the role.
- One exception follows from the same line: an external route written as a path (a single leading `/`) is classed as internal by `isInternalUrl`, so its params are filled, and it is linked through react-router.

## What the docs say

- The migration guide's [URL Config changes](https://github.com/openedx/frontend-base/blob/72d70535cf77e98be8f859aa5746c3dddb4d02d2/docs/how_tos/migrate-frontend-app.md#url-config-changes) presents the two as interchangeable: URLs "should now be expressed as part of the `apps` config as route roles, or as `externalRoutes`, and resolved in code via `resolveRouteByRole()`. It substitutes route params, drops a trailing splat, and reports whether the result is a path in this site or an external URL". It does not say the substitution applies to one of the two only.
- No ADR in `docs/decisions/` covers route roles with params or external routes; 0013 mentions roles for the course bar's `provides`.

## How it got here

- #320 added `resolveRouteByRole` (closing #317 and #319) to replace logic two apps had each written by hand. Both substituted params into whatever the role resolved to, an external URL included: openedx/frontend-app-gradebook#627 called `getUrlByRouteRole(instructorDashboardRole)?.replace(':courseId', courseId)`, and openedx/frontend-app-instructor-dashboard#246's `src/utils/routeByRole.ts` ran ``url.replace(`:${name}`, value)`` for each param before it tested whether the URL was absolute. Neither had a test of an external URL with a param.
- #320's description states the new behavior ("an external URL is returned as configured") and gives no reason; the PR has no review comments.
- react-router's `generatePath`, which #320 uses for the substitution, does not take an absolute URL: on react-router 6.30.6, `generatePath('https://lms.example.com/courses/:courseId/progress', { courseId })` returns `https:/lms.example.com/courses/<courseId>/progress`, the `//` collapsed.

## Where it bites

- Both call sites above keep a URL of their own for when the role resolves to nothing (`gradebookRoute?.url ?? data.gradebookUrl`, `dashboardRoute?.url ?? instructorDashboardUrl(courseId)`), and that fallback is the only way either reaches a destination outside the site with the course in it. A site that declares an external route for one of those roles replaces the fallback with a URL that cannot name the course.
- The shell's own [`ProfileLinkMenuItem`](https://github.com/openedx/frontend-base/blob/72d70535cf77e98be8f859aa5746c3dddb4d02d2/shell/menus/ProfileLinkMenuItem.tsx#L15-L24) reaches a user's profile by appending `/u/<username>` to the profile role's URL, which works for an app route and an external route alike because the role's route takes no param: openedx/frontend-app-profile declares the role on `profile` and serves the user's page from its child `u/:username` ([`src/routes.tsx`](https://github.com/openedx/frontend-app-profile/blob/c4ff88501d36a60fef8761b0a2dfcee07ba1dd09/src/routes.tsx#L12-L32)).
- Learning declares `org.openedx.frontend.role.courseOutline`, `courseDates`, `courseProgress` and `courseware` on routes under `course/:courseId`, and its progress tab links to them by role (openedx/frontend-app-learning#2190). If #348 lets a site point one of them at an external route, the link the site gets has no course in it.

## Questions

- Should a site be able to provide a role whose route takes params with an external route?
- If so, how does an external route say where the params go?
- Until then, where does an app author declaring a role, or an operator writing `externalRoutes`, learn that params are dropped for an external URL?
- Should the resolver report it when it is handed params it will not use?
