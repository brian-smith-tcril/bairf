# Plan: #2086 — Read `courseHomeMeta` from the query: courseware, shared, and widgets (B3)

Layer in the running stack on top of B2 (#2085, PR #2109). Layer B3 of the
#1977 model-store dissolution; the last `courseHomeMeta` layer. Depends on B2
for the `CourseHomeMeta` type, the three tab-URL hooks in `course-tabs/hooks.ts`
and the seven *requests the course metadata once per load* cases, and on #2098
(merged as #2102) for `{ enabled }` on `useCourseHomeMeta`.

Scope is the issue body plus its one comment, which sends the three tab readers
here through B2's hook façades and asks whether `HiddenAfterDue` can drop its
`courseId` prop.

### Why `{ enabled: false }` at the readers

Same as `decisions-2083.md` entry 3, `decisions-2098.md` entry 4 and
`decisions-2085.md` entry 2. Every B3 site mounts after its owner's fetch has
settled, so a fetching observer would find the entry stale at `staleTime: 0` and
refetch on mount; the seven count cases from B2 measure exactly that and must
keep reading one.

### 2. The two writers move onto the query

A literal port (settled in review, open question 1): every signature stays,
`dispatch` becomes `queryClient` in the same slot, and each `dispatch(updateModel(…))`
block becomes one `queryClient.setQueryData` call that spreads the same
`celebrations` argument the store version spread. The three components swap
`useDispatch()` for `useQueryClient()` (imported from `@tanstack/react-query`,
as `SidebarContextProvider.jsx:3` does).

```js
// courseware/course/celebration/utils.jsx — in recordFirstSectionCelebration, and again
// in shouldCelebrateOnSectionLoad's clearing branch, replacing the two dispatch blocks
import { courseHomeQueryKeys } from '../../../course-home/data/queryKeys';

queryClient.setQueryData(
  courseHomeQueryKeys.metadata(courseId),
  (meta) => ({ ...meta, celebrations: { ...celebrations, firstSection: false } }),
);
```

```js
// shared/streak-celebration/utils.jsx — recordModalClosing
queryClient.setQueryData(
  courseHomeQueryKeys.metadata(courseId),
  (meta) => ({ ...meta, celebrations: { ...celebrations, streakLengthToCelebrate: null } }),
);
```

The write is React Query's documented way to update a cache entry after telling
the server something (`postCelebrationComplete` stays exactly as it is, a
fire-and-forget POST outside React Query). Its proper home is a `useMutation`
whose callback does this write; that is #1973's item for this POST
(`courseware/course/celebration (single POST)`), and this layer deliberately
does the minimal thing and leaves the mutation to it. The updater form is used
only to spread the existing entry:

> Synchronous way to immediately update a query's cached data. If the updater
> (or the value passed) resolves to `undefined`, the cache is left untouched and
> no query is created; otherwise, if the query does not exist yet, it will be
> created.
>
> Updates must be performed immutably: do not mutate `oldData`, or data
> previously retrieved via `QueryClient#getQueryData`, in place.
> — [QueryClient › setQueryData](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient)
> (source: `docs/framework/react/reference/classes/QueryClient.md` in TanStack/query)

> Updates via `setQueryData` must be performed in an _immutable_ way. **DO NOT**
> attempt to write directly to the cache by mutating data (that you retrieved
> from the cache) in place.
> — [Updates from Mutation Responses › Immutability](https://tanstack.com/query/latest/docs/framework/react/guides/updates-from-mutation-responses#immutability),
> whose correct example is `(oldData) => oldData ? { ...oldData, title: '…' } : oldData`

Against the store version, case by case:

- **Entry present** (the only reachable case — every writer runs under a
  component the gate renders after the owner's fetch): the store wrote
  `{ ...existing, celebrations: { ...celebrations, flag } }` with the
  component's render-time `celebrations`; the cache write is the same object
  literal over the same argument. `celebrations: null` is a real value (the
  serializer's when celebrations are off, and the factory default);
  `{ ...null, firstSection: false }` is `{ firstSection: false }` both ways.
- **Entry absent**: the store created a bare `{ id, celebrations }` model;
  spreading an undefined `meta` creates a bare `{ celebrations }` entry.
  Unreachable, and faithful.
- **Readers**: `setQueryData` notifies every observer of the key, disabled
  ones included, so the 22 `{ enabled: false }` readers and B2's
  `LoadedTabPage` re-render on the write as the `useSelector` readers did. This
  is pinned by a test (below) rather than a quote.
- **Freshness**: the write stamps the entry as updated now; at `staleTime: 0`
  it is stale again immediately, so the next owner mount (the next tab
  navigation) refetches from the server, which `postCelebrationComplete` has
  already told. That is the resync the store version relied on too (the bridge
  overwrote the model on the next fetch). No `invalidateQueries`: the old code
  did not refetch, and a refetch here would be a second request for data the
  writer has just made correct.

What this port keeps, on purpose: the writers still spread the component's
render-time `celebrations` (as the store version did), `recordModalClosing`'s
unused `org` parameter stays, and the two identical first-section writes stay
inline in `celebration/utils.jsx` (open question 2). All three are things the
#1973 mutation conversion rewrites anyway. After this layer `react-redux` is
imported by no component under `courseware/course/` or `shared/`; the remaining
`useDispatch` calls are the D-layer mutation hooks.

For #1973 to know (to be noted on that issue): the POST and the cache write are
not paired one to one in `shouldCelebrateOnSectionLoad` — the streak-precedence
branch (`:71-77`) posts without patching, and the clearing branch (`:79-94`)
patches without posting — so a mutation whose callback always patched would
change those two branches.

### 4. The bridge entry goes

## Open questions (all settled in review, 2026-09-23)

1. **Writer signatures — settled: the literal port.** Every parameter stays,
   `dispatch` becomes `queryClient` in the same slot, and each dispatch block
   becomes one `setQueryData` call spreading the passed `celebrations`
   (`(meta) => ({ ...meta, celebrations: { ...celebrations, flag } })`). The
   first draft recommended the updater form reading the cache's own
   `celebrations`, dropping that parameter and `recordModalClosing`'s unused
   `org`; rejected as cleanup riding on the swap. The principle set in review:
   the local patch is React Query's documented pattern, but doing it by hand
   beside a fire-and-forget POST is the untidy part, and #1973 already owns
   turning that POST into a mutation, so this layer does the minimal change
   and the real cleanup happens there. The stale-copy hazard the updater form
   would remove is exactly what the Redux code has today.
2. **The two identical first-section writes stay inline — settled**, same
   principle. The first draft proposed one private helper.
3. **`CourseHomeMeta` gains no fields — settled.** §5. Fields are named when a
   TypeScript reader needs them; until then the index signature returns
   `unknown`, which fails `npm run types` at the point of use and is the cue
   to add the field.
4. **`CourseExitContent` reads through a disabled observer — settled.** §1.
   Two observers on one key are one entry; the prop through `TabWithTimer`'s
   children buys nothing.
5. **Test seeding, per suite — settled: mount where the suite can fetch
   (`Course`, `Sequence`, `LockPaywall`, the `CourseExit` bodies), seed where
   its own adapter precludes it (`HonorCode`, `StreakCelebrationModal`),
   mock-swap where the suite mocks module boundaries (`UpgradePanel`,
   `SidebarContextProvider`); `Course.test.jsx` gets a `renderCourse` helper
   for its 19 renders.** Alternatives set aside: re-registering the metadata
   GET on the two suites' own adapters (widens what those adapters exist to
   observe); seeding everywhere (`decisions-2098.md` entry 3).
6. **`HiddenAfterDue` drops `courseId` — settled**, per the comment's question
   and §3; one `Sequence.test.jsx` case renders under a `:courseId` route.
7. **README — settled: rewritten queries-first (§6).** The first draft asked
   only whether to reword "models" on the `course` object lines; in review the
   requirement became that the README never suggests `useModel` gives more
   than it does. So the section leads with the context arguments, then the two
   metadata queries (both work today), and keeps one line for the
   `discussionTopics` read that has no query hook yet. Wording is for code
   review.
