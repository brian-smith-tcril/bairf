**What:** the shell's "skip to main content" link does not land on the page's main landmark, and no app can make it. Deciding what the skip target is, and who owns the `main` landmark, belongs here.

**Where it comes from** (2.0.0-alpha.16): the header's skip link is `<a class="sr-only sr-only-focusable" href="#main-content">` in `shell/header/Header.tsx`, and the element with that id is the shell's own `<div id="main-content" class="flex-grow-1">` in `shell/DefaultLayout.tsx`, the wrapper around the content slot (`org.openedx.frontend.slot.content.main.v1`). The shell renders no `<main>`. The apps do, each where it likes: the template's `Main.tsx` renders `<main>` around its outlet, profile and account render `<main id="main">` in theirs, catalog `<main>` in its, learner dashboard `<main>` in its dashboard container, and frontend-app-learning's tab page renders `<main>` around a tab's content (checked in each repo's default branch on 2026-10-26). So activating the skip link moves focus to a div above the app's content; the landmark a screen reader's rotor lists as "main" is somewhere below it, and an app cannot put the id on its landmark without duplicating the shell's.

**How this surfaced:** openedx/frontend-app-learning#2026 (open) fixes landmark structure on the legacy build by putting `<main id="main-content">` on the element that holds the primary content only, with the course outline sidebar as a `<nav>` sibling outside it, so the skip link lands on the semantic `<main>`. The landmark half ports to frontend-base as is. The skip-link half cannot: under the shell the id is the shell's, so the port drops it and the skip link keeps landing on the shell's div. The PR's accessibility claim about the skip target is only true on the legacy build until this is settled.

**The guidance:** the ARIA Authoring Practices Guide, [Landmark Regions, `main`](https://www.w3.org/WAI/ARIA/apg/patterns/landmarks/examples/main.html): "Each page should have one main landmark." and "The main landmark should be a top-level landmark." A skip link exists to bypass the repeated header and reach that content, so the target and the landmark should coincide.

**Options**

1. **The shell owns the landmark.** `DefaultLayout` renders `<main id="main-content">` in place of the div, and apps stop rendering `<main>`: the template's `Main.tsx`, the four converted apps above and Learning's tab page each change one element to a `div`. The skip target and the landmark are the same element for every site, and an app's `<main>` becomes a nested-landmark bug it can be linted for. Costs a change in every app, and the landmark then includes whatever an app renders above its content (Learning's alerts, for one), which is what #2026 set out to avoid.
2. **The app owns the landmark, the shell targets it.** The shell keeps its wrapper div but drops the id, and the skip link targets the app's `<main>` (by role, or by an id the shell documents for apps to put on their landmark). Each app keeps deciding what its main content is, which lets #2026's finer target survive. Costs a convention every app has to follow, and a page with no app `<main>` has no skip target.
3. **Document the status quo.** The skip target is the content container; apps render their own `<main>` and must not use the id. Cheapest, and the skip link keeps landing above the landmark.
