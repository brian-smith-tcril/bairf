## What the route does on `master`

The discussion tab ([`src/course-home/discussion-tab/`](https://github.com/openedx/frontend-app-learning/tree/master/src/course-home/discussion-tab)) renders the tab-page frame with the `discussion` tab active and, inside it, an iframe of the discussions app at `DISCUSSIONS_MFE_BASE_URL/<course id>/<path>`, sized from the iframe's height messages, with the iframe's navigation events rewriting Learning's URL. It dates from 2022 (#879), when the then-new discussions app was kept inside Learning's chrome. Nothing in openedx-platform builds this URL: the LMS discussion tab links straight to the discussions app. Course content and old bookmarks can still carry it, so the route is kept.

## What moves

- The route, `course/:courseId/discussion/:path/*`, keeps its path from #2188 under the URL-decoding wrapper from #2195, carries no role (nothing should resolve a redirect; the destination role is the discussions app's), and gets a loader in place of the page. The loader resolves the discussions role through `resolveRouteByRole`, appends the course id, the path and the search string, and returns react-router's `redirect`: to the external URL when a site supplies the role as an external route, to the in-site path when a converted discussions app is installed. When no app or external route provides the role, the loader throws a 404 response and the shell renders its not-found page. The shell's own home redirect ([`getAppRoutes.ts`](https://github.com/openedx/frontend-base/blob/main/shell/router/getAppRoutes.ts)) and `authenticatedLoader` are the loader precedents.
- The discussions role, the one #2199's widget also resolves, is `org.openedx.frontend.role.discussions`, following the destination-named ids the converted apps use (`org.openedx.frontend.role.dashboard`, `org.openedx.frontend.role.profile`, `org.openedx.frontend.role.courses`). No converted discussions app has declared it yet. A site supplies it today as an `externalRoutes` entry pointing at its discussions deployment; the discussions conversion declares it on its course route.
- The iframe component and its test are not ported; the manifest records them as dropped. The two iframe hooks in the generic hooks module that only it used (height, plugin events) stay in place; whether they go is for the pull request, as a line in it.

## Why a redirect

The iframe exists to show the discussions app inside Learning's header and tabs. Under frontend-base the shell owns the header and the course bar on every app's pages, so the discussions app, installed or external, already sits in the same chrome, and the LMS's own discussion tab link goes straight to it. A redirect gives an old link the same destination the course bar gives a click, with no second copy of the discussions app inside a frame. The alternative, porting the iframe with the role-resolved URL as the auxiliary sidebar does, keeps a page Learning would otherwise not have; the review round decides.

## Testing

The route's tests reach it through the exported route array at a discussion path and assert the loader: with the role supplied as an external route, the redirect target is the external URL with course id, path and search string; with a stub app in the test site config providing the role on a route, the target is that in-site path; with neither, the response is a 404 and the shell's not-found page renders. Mocks follow the conventions #2189 set. The manual test follows a discussion link on a site with the real discussions app as an external route and records where it lands.
