Part of #1905. Depends on #2189.

**Goal:** a learner who follows the one-click unsubscribe link in a notification email lands on a frontend-base site, has their email notification preferences updated, and sees the result as on `master`: the success message, or the failure message with a link to the notification preferences in the account settings. No login is needed, as on `master`. The preferences unsubscribe stub route from #2188 is replaced.

## What moves

Files port from the legacy `src/` tree to the same relative path under `frontend-base/src/`, with their tests, and get a line each in `frontend-base/manifest.tsv`.

- The page ([`src/preferences-unsubscribe/`](https://github.com/openedx/frontend-app-learning/tree/master/src/preferences-unsubscribe)): the component, which calls the endpoint on mount, shows the loading state, then the success or failure content with the preference-center link; its data module; messages.
- The endpoint is `/api/notifications/preferences/update/<token>/` on the LMS, which the platform leaves unauthenticated and rate-limits per token ([`notifications/views.py`](https://github.com/openedx/openedx-platform/blob/master/openedx/core/djangoapps/notifications/views.py), `preference_update_from_encrypted_username_view`): the token is the learner's encrypted username, placed in the email by `get_unsubscribe_link` as `<learning URL>/preferences-unsubscribe/<token>/`, so the path stays as it is.
- The route, `preferences-unsubscribe/:userToken/:updatePatch?`, with no role (#2188) and no authentication loader, as `master` initializes without requiring an authenticated user. The optional `updatePatch` segment is read by nothing: the component uses only the token, the data module builds the URL without it, and the email link never carries it; the pattern ports as it is, and the pull request records whether the unused segment stays.
- Config reads change form per the reviewed table: `LMS_BASE_URL` becomes the site config's `lmsBaseUrl`; the preference-center link resolves `org.openedx.frontend.role.account`, the role the account app declares, with the `#notifications` fragment appended, in place of `ACCOUNT_SETTINGS_URL`; the tracking and error-logging calls move to frontend-base's functions of the same names.
- The header: on `master` the page renders the default header from `@edx/frontend-component-header`, not Learning's course header. Under frontend-base the shell renders its header on every page, in its logged-out form for an anonymous visitor, so the page renders only its content.

## Testing

The page's tests port with it and reach the page through the exported route array at a token path: a successful call renders the success heading and message, a failing call renders the failure heading, message and the preference-center link, with the request mocked per the conventions #2189 set.

The manual test needs a link. The manual-testing record carries the recipe: with email notifications enabled for a learner, take the unsubscribe link from a notification digest email (or build it from `encrypt_string(username)` in an LMS shell), open it in a logged-out browser, record the result and the learner's preferences afterward; then open it with a made-up token for the failure page.

## Acceptance

- [ ] A valid link, opened logged out, updates the learner's email notification preferences and shows the success message; an invalid token shows the failure message with the preference-center link resolving the account role
- [ ] The page renders under the shell's header with no header of its own
- [ ] Types, lint and tests of the new package pass; the legacy workflow stays green; `npm run dev` from the package serves the page
- [ ] Manifest lines added for every file moved; the directory's coverage compared against the `master` baseline
