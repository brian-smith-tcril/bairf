# Plan: #2075 — progress-tab exam attempts (`courseHome.examsData`) → React Query hook

Filed as https://github.com/openedx/frontend-app-learning/issues/2075, a direct
sub-issue of #1946. The issue body was lifted from the draft at the bottom.

## Context

Part of epic #1946 (Redux → React Query, Stage 1) and the `courseHome` slice
teardown (#1975). After the courseware teardown (#1976), `src/store.ts` still
registers `models`, `courseHome`, `specialExams`, `plugins`. The `courseHome`
slice is down to two reducers: `fetchProctoringInfoResolved` and
`setExamsData`. This layer removes `setExamsData` and everything that feeds it;
the proctoring status is the rest of #1975 and goes in the next layer.

This gets its **own layer** because it isn't a plain de-Redux move: the data
has no in-repo reader, and exists only so that plugins can read it. The
decision here is about a plugin-facing contract, not about a Redux slice.

### How it works today

Added in PR #1829 (merged 2025-12-15, "Fetch exams data on the progress page"),
whose description says: *"This allows children of the root `ProgressPage` or
downstream plugin slots to access this data from the Redux store."* 2U
cherry-picked it to their fork (edx/frontend-app-learning#38), so it is in use
by at least one deployer's plugins even though nothing in this repo reads it.

The chain, top to bottom:

1. `course-home/progress-tab/ProgressTab.jsx:19-24` — `ProgressTabContent`
   takes `sectionScores` from the progress query, flattens every subsection's
   `blockKey` into `sequenceIds`, and calls `useGetExamsData(courseId, sequenceIds)`.
2. `course-home/progress-tab/hooks.jsx` — `useGetExamsData` is a `useEffect`
   that dispatches `fetchExamAttemptsData(courseId, sequenceIds)`.
3. `course-home/data/thunks.js` — `fetchExamAttemptsData` runs
   `Promise.all` over the ids, one `getExamsData(courseId, sequenceId)` each,
   keeps `response.exam || {}`, and on any throw does `logError(e)` and keeps
   `{}`. Then `dispatch(setExamsData(results))`.
4. `course-home/data/api.js:383` — `getExamsData` GETs the LMS
   `edx_proctoring` attempt endpoint (or the edx-exams `student/exam/attempt`
   endpoint when `EXAMS_BASE_URL` is set), camelCases the body, and maps a 404
   to `{}`.
5. `course-home/data/slice.js` — `setExamsData` stores the array at
   `state.courseHome.examsData` (initial `null`).

So the value a plugin reads is: **an array, positional with `sectionScores`'s
flattened subsection order, one entry per subsection, `{}` for subsections
with no exam (or any fetch failure), otherwise the camelCased `exam` object;
`null` until the first fetch resolves.** The fields available are whatever the
endpoint puts under `exam`; the in-repo fixtures (`redux.test.js`,
`ProgressTab.test.jsx`) use `id`, `courseId`, `contentId`, `examName`,
`attemptStatus`, `timeRemainingSeconds`.

**Relation to `@edx/frontend-lib-special-exams`.** `getExamsData` hits the same
two URLs as the library's own `fetchExamAttemptsData`
(`dist/data/api.js`, v4.1.0). The library fetches one exam — the sequence
currently rendered by `SequenceExamWrapper` — into its own `specialExams`
slice; the progress tab needs attempt status for every subsection at once, on a
page that renders no exam, so #1829 re-implemented the fetch and fanned it out.
This is learning's own Redux and is not gated on #2018. If #2018 ends in a
React Query conversion of the library, a follow-on could have the library
export the query hook and the progress tab drop its copy.

### What we established (2026-09-16)

- **No in-repo reader.** `git grep examsData src` outside `course-home/data/`
  finds nothing but tests. Deleting only the `useGetExamsData(...)` call in
  `ProgressTab.jsx` fails five of the six tests in the
  `Progress Tab › Exam data fetching integration` block of
  `ProgressTab.test.jsx` (69 of 74 pass), and nothing outside that block;
  every assertion in the block counts attempt requests or inspects
  `store.getState().courseHome.examsData` directly. Nothing rendered changes.
- **No visible external reader.** A GitHub code search over the `openedx` org
  for `examsData` finds only this repo's tests and an unrelated
  instructor-dashboard file. Operator `env.config.jsx` files and the edx fork's
  private plugins are not searchable, so absence there proves nothing — the
  fork cherry-pick is the evidence of use.
- **Baseline probe.** A local `env.config.jsx` inserts one `DIRECT_PLUGIN`
  widget into every progress-page slot; the widget reads
  `useSelector(state => state.courseHome.examsData)` and renders the count, a
  line per exam, and the raw JSON. Against the Tutor demo course all 17
  entries are `{}` (no proctored exams; the LMS attempt endpoint answers 200 + empty `exam`). With a
  dev-only stub in `getExamsData` returning one exam per subsection, all six
  slots show the identical 17-entry array. Slots that rendered the probe:
  `progress_tab_course_completion`, `progress_tab_certificate_status_main_body`,
  `progress_tab_course_grade`, `progress_tab_grade_breakdown`,
  `progress_tab_certificate_status_side_panel`, `progress_tab_related_links`.
  The nested `progress_certificate_status` slot only mounts when a certificate
  card renders and did not appear for this learner.
- **`pluginProps` are the slot contract, and `examsData` is not in any of
  them.** The six slots pass `enableProgressGraph` (course completion) or
  nothing; the nested certificate slot passes `courseId`. The exam data was
  never part of a slot's contract — it was reachable because plugins render
  inside the app's Redux `Provider`. Threading it through `pluginProps` would
  *add* it to the contract of six slots, which we don't want.

## Decision

**Replace the Redux path with an exported React Query hook that a plugin
imports from learning's source.** The plugin side goes from

```jsx
import { useSelector } from 'react-redux';
const examsData = useSelector(state => state.courseHome.examsData);
```

to

```jsx
import { useExamsData } from './src/course-home/progress-tab/hooks';
const examsData = useExamsData();
```

(final hook name/location settled in the implementation plan; the source-import
pattern is the one operator `env.config.jsx` files already use for components
like `CourseBreadcrumbs`). React Query dedupes by key, so the plugin's call and
the progress tab's call share one fetch and no context provider is needed —
the query cache does the job the Redux store did. This is the direct-hooks
pattern the rest of the conversion has used.

The hook preserves the value shape a plugin sees today: the positional array
with `{}` holes, and `null` (not `undefined`) before the first result.

The Redux read stops working, so this is a **breaking change** for any plugin
using it: `refactor!:` subject + `BREAKING CHANGE:` footer, as #2016 did for
the sidebar `prefetch` contract, and the PR names the old store path and the
new import. Tag the #1829 author on the PR.

## 1. `course-home/data/queryKeys.ts` + `apiHooks.ts` — the query

Add the key beside the others:

```ts
examAttempts: (courseId: string, sequenceIds: string[]) => (
  [...courseHomeQueryKeys.all, 'examAttempts', courseId, sequenceIds] as const
),
```

The id list is part of the key, so a progress-tab refetch that changes
`sectionScores` yields a new key and a fresh fan-out — the thunk's
"re-dispatch when `sequenceIds` changes" effect, expressed as cache identity.
No `targetUserId`: the attempt endpoints take no user and today's thunk
ignores masquerade too (the request goes as the authenticated user).

Add the hook in `apiHooks.ts`, named for the thunk it replaces
(`fetchExamAttemptsData`) the way its siblings are named for theirs:

```ts
// One query over all subsections, resolving to the same positional array the
// thunk produced: `{}` for a subsection with no exam (the api maps 404 → {}) and
// for a failed request (logged, the rest continue), otherwise the `exam` object.
export const useExamAttemptsData = (courseId: string, sequenceIds: string[]) => useQuery({
  queryKey: courseHomeQueryKeys.examAttempts(courseId, sequenceIds),
  queryFn: () => Promise.all(sequenceIds.map(async (sequenceId) => {
    try {
      return (await getExamsData(courseId, sequenceId)).exam || {};
    } catch (error) {
      logError(error);
      return {};
    }
  })),
});
```

One query with the fan-out inside `queryFn`, not `useQueries`: the stored
value *is* the array, so a single query reproduces it directly, keeps the
positional contract without a merge step, and dedupes across every plugin that
calls the hook. Per-entry failures are swallowed inside `queryFn` exactly as
the thunk swallowed them, so the query itself never errors and the app's
retry policy never engages — the thunk had no retry either. `Promise.all([])`
resolves to `[]`, matching `setExamsData([])` for a course with no subsections.
No `meta` — nothing reads this through `useModel`, so nothing to bridge.

`getExamsData` in `api.js` is unchanged (its five `api.test.js` cases stay).
**Remove the dev-only stub currently sitting in the working tree before the
layer is committed.**

## 2. `course-home/progress-tab/hooks.jsx` — the plugin-facing hook

Replace `useGetExamsData(courseId, sequenceIds)` (an effect that dispatched
the thunk and returned nothing) with a self-sufficient sibling of
`useProgressData()`:

```js
export function useExamsData() {
  const { courseId } = useParams();
  const sectionScores = useProgressData()?.sectionScores;
  const sequenceIds = sectionScores?.flatMap((section) => section.subsections)
    .map((subsection) => subsection.blockKey);
  const { data } = useExamAttemptsData(courseId, sequenceIds ?? [], { enabled: !!sequenceIds });
  return data ?? null;
}
```

(`useExamAttemptsData` grows an `options` pass-through for `enabled`, or the
gate lives inside it as `enabled: sequenceIds.length > 0 || ...` — settle in
code; the point is a plugin can call this before the progress query resolves
and get `null`, never a request with no ids.)

- **No arguments.** Any plugin in any progress-tab slot calls `useExamsData()`.
  It derives the subsection ids the same way `ProgressTabContent` did
  (`sectionScores.flatMap(subsections).map(blockKey)`), from the progress
  query it shares with the tab.
- **Returns data-or-`null`**, like `useProgressData()` returns `.data`:
  the array once resolved, `null` before — the same two states
  `state.courseHome.examsData` had.
- **Name.** `examsData` is the name plugin authors know from the store path;
  the hook keeps it. The query hook underneath is `useExamAttemptsData`
  (section 1), so the two don't collide.
- `useMemo` is unnecessary: the id list is a query-key input and React Query
  hashes keys structurally.
- Stays in the existing `.jsx` file (no new file, so no TypeScript question).
  `useDispatch` and the thunk import leave the file.

## Behavior changes (for the decision doc + PR body)

1. **Reading `state.courseHome.examsData` no longer works** — the
   `refactor!:` / `BREAKING CHANGE:` item. Replacement: `useExamsData()`
   imported from `./src/course-home/progress-tab/hooks`.
2. **No eager fetch.** Attempt requests fire only when some plugin calls the
   hook. Same network shape per call (one GET per subsection, `Promise.all`).
3. **Standard query posture**: default `staleTime: 0` means a later remount
   refetches (the thunk's effect also refetched on every mount);
   `refetchOnWindowFocus: false` app-wide; retries never engage because
   `queryFn` never rejects.
4. `deprecatedSaveCourseGoal` / `deprecatedPostCourseGoals` removed (dead
   since #789, 2022-01-10).

## Issue body as filed (#2075)

**Title:** Convert the progress-tab exam attempts fetch (`courseHome.examsData`) to a React Query hook

Part of #1946 — Redux → React Query migration (Stage 1). Part of the
`courseHome` slice teardown (#1975); split out because it is a plugin-facing
contract change, not just a slice removal.

**What it is.** PR #1829 made the progress tab fetch exam attempt status for
every subsection and store the array at `state.courseHome.examsData`, so that
plugins in the progress-tab slots could read it. Nothing in this repo reads it;
2U's fork carries it (edx/frontend-app-learning#38). The fetch uses the same
endpoints as `@edx/frontend-lib-special-exams`' own `fetchExamAttemptsData`,
but fans out course-wide instead of one sequence at a time.

**Goal.** Keep the data available to plugins without Redux: an exported React
Query hook (imported from learning's source, the way operator `env.config.jsx`
files already import components) replaces the `useSelector` read. `pluginProps`
are the slot contract and the exam data is deliberately *not* added to them.

**Tasks**
- `fetchExamAttemptsData` thunk → a query (fan-out over the subsection ids,
  `{}` per 404 / failed entry, positional order preserved).
- Export a plugin-facing hook; keep `null` before the first result to match
  today's initial state.
- Delete `setExamsData` / `examsData` from the `courseHome` slice and the
  thunk; convert the five store-inspection tests in `ProgressTab.test.jsx`.
- Document the new import in the progress-tab slot READMEs' shared section
  (or a note in `ARCHITECTURE.md`), and mark the PR breaking
  (`refactor!:` + `BREAKING CHANGE:`), naming the old store path and the new
  hook.

**Verify.** With an `env.config.jsx` that inserts a widget into each
progress-tab slot and renders the hook's result: same array in every slot as
the Redux baseline; `git grep examsData src` finds only the new hook and its
tests; `courseHome` slice has no `examsData`.
