## What moves

Each file ports to the same relative path under `frontend-base/src/` and gets a line in `frontend-base/manifest.tsv`:

- `course-home/progress-tab/`: the tab, header, hooks (`useProgressData`, `useExamsData`), utilities, messages, README; `certificate-status/`; `course-completion/` with the donut chart and its `CompletionDonutChart.scss`; `credit-information/`; `grades/` (course grade with `GradeBar.scss`, detailed grades, grade summary, messages); `related-links/`; `ProgressTab.test.jsx` and `hooks.test.jsx`.
- `plugin-slots/ProgressCertificateStatusSlot`, `ProgressTabCertificateStatusMainBodySlot`, `ProgressTabCertificateStatusSidePanelSlot`, `ProgressTabCourseCompletionSlot`, `ProgressTabCourseGradeSlot`, `ProgressTabGradeBreakdownSlot`, `ProgressTabRelatedLinksSlot`: the seven index files, as placeholder slots. Their READMEs and images (7 and 9 files) are dropped with `dropped` manifest lines, as #2189 did for the banner slot's: they document the plugin-framework contract, and #2185 writes the Slot API ones.
- `shared/links.jsx`, with a new `links.test.jsx` beside it (no test on `master`; its lines were covered through the progress and course-exit suites).
- `courseware/course/course-exit/utils.js`, `messages.ts` and `utils.test.ts`. The certificate status reads the mode helper (`COURSE_EXIT_MODES`, `getCourseExitMode`) and the links module reads three of the messages, so this is their first consumer in page order; decision 29's amendment had them port with CW2's unit navigation (#2196) and is amended by this plan. Both files port whole: `GetCourseExitNavigation`, `logClick` and `logVisit` ride along without a caller until #2196 and #2202, and `utils.js`'s two courseware hooks come from the stub below.
- `course-tabs/hooks.ts` and `hooks.test.tsx`: their `dropped` manifest lines become port lines. `RelatedLinks.jsx` reads `useCourseOutlineUrl` and `useDatesTabUrl`, `DetailedGrades.jsx` reads `useCourseOutlineUrl`; the module reads the tab URLs the LMS sends in the course metadata (`tabs[].url`, built by the LMS from its learning URL setting) and ports unchanged. Resolving `courseDatesRole` and `courseOutlineRole` instead, with `tabs` gating presence, is the alternative: it would make Learning's own links independent of the LMS setting, as `TabPage`'s redirect prefix is; it is not taken here because the subsection links in `SubsectionTitleCell.jsx` and the studio link come from the same response as LMS-built absolute URLs and would stay LMS-built either way, and the LMS setting has to point at the site's Learning root for the LMS to send learners to the app at all.

## What changes in the moved code

- Imports: every `@edx/frontend-platform*` import becomes one from `@openedx/frontend-base`; `getConfig()` reads become the site-config field or `getAppConfig(appId)` per the key table above. The 404 redirect to the LMS's legacy progress page keeps `global.location.replace`: it leaves the site.
- **Links resolve roles (decision 34).** `DashboardLink` resolves `org.openedx.frontend.role.dashboard` with `getUrlByRouteRole`; `ProfileLink` resolves `org.openedx.frontend.role.profile` and appends `/u/<username>`, as the shell's `ProfileLinkMenuItem` does; both render the Paragon `Hyperlink` with `getLinkProps(url)`, so a path in this site navigates client-side and an external route is a plain anchor. When the site declares no route for the role, the link renders nothing, as the shell does for both roles (`ProfileLinkMenuItem` returns `null`; the dev home page omits its dashboard link); a site that wants the LMS destination declares it as an external route. The two role strings go in `constants.ts` beside Learning's own. `IdVerificationSupportLink` reads `SUPPORT_URL_ID_VERIFICATION` from the app config and renders nothing when it is `null`, as on `master`.
- Placeholder slots: each of the seven keeps its file and component name and renders its default content in a bare fragment with no plugin-framework import. `ProgressCertificateStatusSlot` still renders its children; `ProgressTabCourseCompletionSlot` keeps its `enableProgressGraph` prop, which gates the chart as well as being a plugin prop; the main-body and side-panel slots keep their window-width gates. The props the slots passed to plugins (`courseId`, `enableProgressGraph`) are recorded in the manifest line's commit for #2185.
- Routes: both progress route objects (`progress`, `progress/:targetUserId`) become `lazy`, loading `./course-home/progress-tab/ProgressTab` (the directory has no index on `master`) with the `learning-progress` chunk name; the id stays on the first. Their page-rule assertion moves from `routes.test.tsx` to the progress test.
- Styles: `style.scss` gains `@use` lines for `CompletionDonutChart.scss` and `GradeBar.scss` (decision 33's pattern; both use only Paragon variables and their own).
- Console: `GradeSummaryHeader.jsx` and `GradeSummaryTableFooter.jsx` take `trigger={['hover', 'focus']}` in place of `trigger="hover"` (react-bootstrap's accessibility warning, 134 blocks on `master`, assigned to this port by the inventory). The one `forwardRef render functions do not support propTypes` block the inventory attributes to the progress suite has no `forwardRef` in the directory, so its source is a dependency, found at port time and fixed in the component or silenced under its upstream issue as the setup file does for Paragon's.
- The progress README ports; its plugin-framework example is replaced by one line under #2185's URL, since the Slot API port writes the widget example.
- `useExamsData` is not exported from the package index. `index.ts` exports the app and the routes, as account, profile and learner dashboard do (catalog adds its slot prop types); the hook is for widgets a site mounts in the progress slots, which is #2185's mechanism, so the export is decided there. The PR states this.

## Test changes

- `ProgressTab.test.jsx` reaches the page through the exported route array with `renderRoutes` at `/learning/course/<id>/progress` and `/learning/course/<id>/progress/10`; `fetchAndRender` wraps it and waits for the page's level-one heading before the loaded wait, since a lazy route has nothing fetching until it loads (#2189's dates test). Track events are asserted on `getAnalyticsService().sendTrackEvent`. The `jest.mock` of `courseware-search/hooks` goes: its only readers were the tabs navigation and its slot, dropped in #2189. `logUnhandledRequests` goes: it answered every unmocked request with an empty 200 and a log line; under the adapter an unmocked request rejects, and the case that needed it fails, which is the better signal. The two `SHOW_UNGRADED_ASSIGNMENT_PROGRESS` cases use `mergeAppConfig(appId, …)` and restore the value after. The 404 case stubs `location.replace` with `mockLocation`.
- The five masquerade-banner cases and the "with the instructor toolbar mounted" request-count case render the toolbar for real and are kept whole as `it.skip` under #2194's URL (decision 37). The two "exam attempt data for plugins" cases mount a plugin through the plugin framework and cannot compile without it; they go in a block comment under #2185's URL, as `TabWithTimer.test.tsx`'s timer cases did. `hooks.test.jsx` ports whole at its component-router seam and keeps `useExamsData` covered.
- `links.test.jsx`, new: each link with its role declared as an app route and as an external route, the profile link's username suffix, nothing rendered when the role is undeclared, the support link present with the app config key set and absent when `null`.
- `course-exit/utils.test.ts` grows cases for `logClick` and `logVisit` (event names and the falsy guards) and for `GetCourseExitNavigation` through the stubs (no courseware data: inactive, default text). `course-tabs/hooks.test.tsx` ports as it is.
- The progress test asserts `expect(runPageRules(document)).toEqual([])` once the page has rendered.
