viewport, a `MemoryRouter` for `useSearchParams`.

### What the real provider needs, and what it does

`SidebarProvider` takes `courseId` and `unitId` and calls `useCourseHomeMeta`
(a query client), `useModel` ×2 (the Redux store), `useSearchParams` (a
router), `useWindowSize`, `getEnabledWidgets()` and the storage utils. It
wraps its children in every enabled widget's `Provider` — `UpgradeWidgetProvider`
(localStorage reads) and `DiscussionsProvider` (a topics query when the
course-home metadata has a discussion tab). It renders no trigger or panel;
`SidebarTriggers` and `Sidebar` do that where a suite renders them.

Its state is a function of what it reads: with the default jsdom viewport
(1024, below the 1200 extra-large breakpoint) `shouldDisplayFullScreen` is
`true`, and `useInitialSidebar` returns the stored preference or `null`;
with `global.innerWidth` set wide, `isInitiallySidebarOpen` is `true` and the
cascade picks the stored panel, the first available widget, or
`COURSE_OUTLINE`. `toggleSidebar(id)` opens/closes and writes storage.

## The change

### 1. The ten reads become `useSidebar()`

Each file: `import SidebarContext from …` → `import { useSidebar } from …`
(same path); `useContext(SidebarContext)` → `useSidebar()`; drop
`useContext` from the React import where nothing else uses it. Bodies
unchanged. `Sidebar.jsx` and `SidebarTriggers.jsx` each drop a guard for a
value the typed context cannot hold — `!SIDEBARS` (`Sidebar.jsx:8`) and
`!SIDEBAR_ORDER` (`SidebarTriggers.jsx:18`) — keeping the real conditions
beside them (open question 1, settled).

### 2. `SidebarContext` is no longer exported

`SidebarContext.ts` keeps `const SidebarContext = createContext<…>(null)`
module-private, exports `useSidebar`, the types, and — because
`SidebarContextProvider.tsx` renders `<SidebarContext.Provider>` — the
provider needs the object. Two shapes (open question 2): export the context
under a name that says what it is for (`SidebarContext` stays exported but
only `SidebarContextProvider.tsx` imports it, enforced by review), or move
the `createContext` call into `SidebarContextProvider.tsx` and have the hook
import it from there. `sidebar/index.js` drops
`export { default as SidebarContext }`. `test-utils.jsx` drops its no-op
wrapper. After this, `git grep "SidebarContext.Provider" src` returns the
provider file only.

### 3. The suites render the real `SidebarProvider`

The principle for every suite: the sidebar state a test needs is expressed
through what the provider reads — the widget registry (`getEnabledWidgets`
mocked, the `SidebarContextProvider.test.jsx` shape, or the real one),
localStorage (`sidebar.{courseId}` for a stored panel), the viewport
(`global.innerWidth`), the `sidebar` search param — and the assertions on a
`toggleSidebar` spy become assertions on what the user sees after the
toggle. Per group:

**A — courseware components.** Replace the `SidebarContext.Provider` with
`<SidebarProvider courseId={…} unitId={…}>`; `LockPaywall` gains
`wrapWithRouter: true`; `unitId` comes from the test store's units. "Nothing
open" is the provider's default in jsdom. `Sequence`'s two `UPGRADE` cases:
the factory course has a `verifiedMode`, so the upgrade widget is available;
set `global.innerWidth` wide and `localStorage.setItem('sidebar.{courseId}',
JSON.stringify('UPGRADE'))` so the cascade opens it (the
`Course.test.jsx` *sidebar behavior* shape); *handles click on upgrade panel
close button* asserts the panel is hidden afterwards instead of a spy call.
`SidebarWrapper`'s `contextValue` prop goes.

**B — course-outline widget.** Same wrapper inside the existing
`AppProvider`/`QueryClientProvider`/router nesting. The outline is the
cascade's fallback, so a wide viewport with nothing stored opens it; where a
suite wants it closed, `sessionStorage` `sidebarClosedByUser` or a stored
`DISCUSSIONS` preference (with `getEnabledWidgets` mocked to a discussions
stub that is available) does that. `toggleSidebar: jest.fn()` assertions
become "the tray collapses" / "the trigger's aria state flips".
`CourseOutlineTrigger`'s `currentSidebar: discussionSidebarId` case mocks the
registry the same way.

**C — framework components.** These suites move onto `setupTest`'s `render`
(store via `initializeTestStore` in `beforeAll`, query client, intl,
`wrapWithRouter: true`) with `getEnabledWidgets` mocked to the stub widgets
they already define, and render `<SidebarProvider><SidebarTriggers /><Sidebar /></SidebarProvider>`
where a case needs to open a panel by clicking its trigger. `Sidebar`'s
"renders NOTES when currentSidebar is NOTES" becomes "opens NOTES when its
trigger is clicked" or "when NOTES is the stored preference on a wide
viewport". The impossible-state cases (`SIDEBARS: null` / `undefined` / `{}`
with a current sidebar, `SIDEBAR_ORDER: null`, `currentSidebar: 'NONEXISTENT'`)
are deleted: the typed provider never produces them (open question 1).
`SidebarTriggers`' three *external widget integration* cases already call
the real `getEnabledWidgets` against a mocked `getConfig`; under the provider
they drop their hand-built registry entirely. `SidebarBase`'s
`shouldDisplayFullScreen: true` cases set a narrow viewport; its
`currentSidebar: 'OTHER_SIDEBAR'` case stores a different panel.

**D — widget components.** The discussions suites gain `wrapWithRouter: true`
and the wrapper; the topics seed stays (readers are on `useModel` until
#2087). Under the provider the discussions panel is `d-none` unless it is the
current sidebar, which the existing `queryByTitle` assertions do not depend
on. The upgrade suites: `UpgradePanel` and `UpgradeTrigger` drop their
explicit `<UpgradeWidgetProvider>` (the provider mounts it), add a router and
a query client, and keep their module mocks (`useModel`, `useCourseHomeMeta`,
localStorage), which now feed the provider as well. `UpgradeWidgetContext.test.jsx`
and `DiscussionsProvider.test.tsx` test components the provider itself
mounts: they mock `getEnabledWidgets` to `[]` and render the component under
test as the provider's child, so nothing is mounted twice and **no test-only
seam is needed** — the issue's open item, answered.

widget READMEs' *Context Requirements* lines name the hook.

## Open questions

1. **The `!SIDEBARS` / `!SIDEBAR_ORDER` guards and their tests — settled in
   review (2026-09-24): delete the guards with the tests.** `Sidebar.jsx`'s
   `!currentSidebar || !SIDEBARS || !SIDEBARS[currentSidebar]` loses its
   middle condition; `SidebarTriggers.jsx`'s `!SIDEBAR_ORDER ||
   SIDEBAR_ORDER.length === 0` loses its first. Both guarded a value the
   provider never produces (`buildSidebarsRegistry` and `getSidebarOrder`
   always return an object and an array; the types say so) and that only a
   test's faked context could supply — before #2111 the default context
   value already had `{}` and `[]` there. The four cases that exist to hit
   them (`SIDEBARS` null / undefined, `SIDEBAR_ORDER` null, and the
   empty-`SIDEBARS`-with-a-current-sidebar case, which the surviving
   `!SIDEBARS[currentSidebar]` condition covers) go. The real conditions
   stay with a test each under the provider: a stored preference for a
   widget that is no longer registered renders no panel, and a registry
   mocked empty renders no triggers. Same reasoning as #2111's removal of
   the default context value: code whose only job is to make an unreachable
   state render quietly.

2. **Where the context object lives once it is not public — settled in
   review (2026-09-24): the repo's shape, one module.** The four typed
   contexts (`ToastContext.tsx`, `PluginOverridesContext.tsx`,
   `CoursewareSearchContext.tsx`, `TourContext.tsx`) each keep the context
   object, the provider and the hook in one file and export only the
   provider, the hook and the types; nothing imports the objects. The
   sidebar is split across two files only because #1885 wrote it that way
   for `useContext(SidebarContext)` readers. So: `SidebarContextProvider.tsx`
   and `SidebarContext.ts` merge into one module holding the types, the
   `createContext` call, `SidebarProvider` and `useSidebar`; the object is
   module-private and needs no export. Consumers import the hook from the
   merged module; `sidebar/index.js` re-exports `SidebarProvider` and the
   hook. The file name (keep `SidebarContextProvider.tsx`, or
   `SidebarContext.tsx` like the four) is for implementation. The first
   draft recommended keeping `SidebarContext` exported with only the
   provider importing it — an approximation of the pattern held together by
   review, rejected in favour of the pattern.

   **Outcome (implementation, 2026-09-24):** the merged module is
   `SidebarContext.tsx`, named like the four. Merging put the provider's
   import of `defaultWidgets.js` on a cycle (`SidebarContext.tsx →
   defaultWidgets.js → widgetConfig.ts → DiscussionsProvider.tsx →
   SidebarContext.tsx`, `import/no-cycle`), resolved by giving
   `SidebarProvider` a required `widgets` prop that `Course.jsx` fills with
   `getEnabledWidgets()`; `buildSidebarsRegistry` and `getSidebarOrder`
   moved into the module. With `widgets` a prop, the two suites §3 said
   could not render the provider render it with `widgets={[]}`, so the
   test-only seam was not built. `decisions-2112.md` entries 3–5.

3. **Sequence order versus #2087.** Settled in review 2026-09-24: this layer
   first. `plan-2087.md`'s *Stack* line changes to "on top of #2112".
