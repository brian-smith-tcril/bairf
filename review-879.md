### 1. The dev server crashes on load with `Cannot read properties of undefined (reading 'ENABLE_PROGRAMS')`

Status: resolved, no comment (pre-existing on master, not this PR; filed 2026-10-31 as openedx/frontend-base#337, the `getAppConfig` return, and openedx/frontend-base#338, the per-app audit tracker)
Rests on: src/widgets/LearnerDashboardHeader/app.tsx, src/app.ts, site.config.dev.tsx at f4852b343a (none touched by the PR); @openedx/frontend-base 2.0.0-alpha.15 dist/runtime/config/index.js `getAppConfig`, dist/runtime/initialize.js `runtimeConfig`, dist/tools/webpack/common-config/dev/getDevServer.js; commit aed66d1 (arbrandes, 2026-08-29)

Observed by Brian (2026-10-31) on first load of http://apps.local.openedx.io:1996/learner-dashboard with the author's patch applied. The read is the header widget's condition `getAppConfig(appId).ENABLE_PROGRAMS === true` in `app.tsx`. `getAppConfig` returns `appConfigs[id]` unmerged when the app has no `defaultConfig` and the site has no `commonAppConfig`; the app has had neither a `config` nor a `defaultConfig` since aed66d1 ("bundle only real defaults in app config", which called the `ENABLE_PROGRAMS` read "already guarded": the `=== true` guards the value, not the object), and `site.config.dev.tsx` sets neither `commonAppConfig` nor `runtimeConfigJsonUrl`. So in a dev run `getAppConfig(appId)` is `undefined` and the first header render throws. Reachable on a deployed site too (Brian, 2026-10-31): runtime config is optional (`runtime/config/index.ts` module doc: "can be enabled by supplying a runtimeConfigJsonUrl"), ADR 0007 makes the JS site config a configuration method of its own, and frontend-base#118 lets the URL be a static `.json`; a site config with no `commonAppConfig` hits it in production. Sites on the LMS's `/api/frontend_site_config/v1/` never see it because that endpoint always serves `commonAppConfig`.

The LMS does serve the config: `GET http://local.openedx.io:8000/api/frontend_site_config/v1/` is 200 with a 29-key `commonAppConfig` (no `ENABLE_PROGRAMS` key, which is fine) and `baseUrl: http://apps.local.openedx.io:8080`; the dev server proxies that path (getDevServer.js) and frontend-base's own shell dev config consumes it through `runtimeConfigJsonUrl: '/api/frontend_site_config/v1/'`. The runtime merges the fetched JSON over the local site config (`mergeSiteConfig`, initialize.js), so taking that route in dev would also replace `baseUrl` 1996 with the LMS's 8080.

Solution space for the local run (dev config only, uncommitted): `commonAppConfig: {}` in `site.config.dev.tsx` (minimal, gives `getAppConfig` an object); or `runtimeConfigJsonUrl: '/api/frontend_site_config/v1/'` (what frontend-base's shell does, pulls the tutor config, but overrides `baseUrl`). For master: `getAppConfig` returning `{}` instead of `undefined` in frontend-base, or a `defaultConfig` / dev `commonAppConfig` here. Brian's call.

Prior art (Brian asked how other converted apps avoid this; enumerated 2026-10-31 over every openedx repo with a `site.config.dev.tsx`, found by code search for `EnvironmentTypes.DEVELOPMENT`, then grepped in blobless clones): account, admin-console, aspects, authn, catalog, gradebook, instructor-dashboard, notifications, profile, plus frontend-template-application and frontend-template-site. None sets `runtimeConfigJsonUrl`; only frontend-base's own shell and test-site do. Every app that reads its config bundles a `defaultConfig` with every key it reads, nulls and falses included: account (`SUPPORT_URL: null`, `SHOW_PUSH_CHANNEL: false`, ...), authn, profile (`CREDENTIALS_BASE_URL: null`), catalog (`HOMEPAGE_COURSE_MAX`). admin-console, aspects, gradebook, instructor-dashboard and notifications read no config at all. The frontend-base migration how-to (docs/how_tos/migrate-frontend-app.md, "App-specific configuration") says to "bundle an app's own values in `defaultConfig`; `config` is where operators override them". learner-dashboard is the one app that reads config and bundles no `defaultConfig`: aed66d1 dropped the keys as "not genuine defaults" rather than keeping them as `null`/`false` defaults the way account and profile did, which is what left `getAppConfig` able to return `undefined`. `getAppConfig` on frontend-base master (ae5ec93) still has the early return.

Correction after Brian pointed at openedx/frontend-app-learner-dashboard#868 (2026-10-31). 868 (arbrandes, merged 2026-08-29, closes #867, part of openedx/frontend-base#299) applied frontend-base ADR 0017 to this app: none of the five bundled keys was a genuine default, so no `defaultConfig` was added and reads fall back at the read site, which the ADR's "Dropping bundled defaults entirely" section calls "often the right answer for a given app". catalog#156 was the model and kept one real default (`HOMEPAGE_COURSE_MAX`). So a `defaultConfig` here would reverse a merged decision and is off the table; the read sites were only ever value-guarded (`=== true`), never object-guarded, and that is the learner-dashboard half. The early return in `getAppConfig` predates `defaultConfig` (before 97241fe it was `if (commonAppConfig === undefined) return appConfigs[id]`), so `undefined` was always possible for an app with no `config`; 868 removing `config` is what exposed it in dev. The declared return type is `AppConfig`, non-nullable, so the runtime contradicts its own type: that is the frontend-base half. The other converted apps avoid it in dev by spreading the app with a `config` block in `site.config.dev.tsx` (catalog, account, authn, profile, instructor-dashboard), which Brian reads as the thing that should go, not the thing to copy.

Tracking checked 2026-10-31: nothing on openedx/frontend-base issues (searched "config"; #268 is the origin and lists only the `config` → `defaultConfig` moves; #118 is runtime config in dev), nothing org-wide for `site.config.dev` or `getAppConfig` beyond conversion epics. Project board https://github.com/orgs/openedx/projects/65 (288 items, read 2026-10-31 after a `read:project` refresh): nothing tracks dev-config `config` blocks or the `getAppConfig` return; the config-related rows are #268 (done), #118 (done, runtime config JSON in dev), #208 (done), #278 (todo, route loaders) and openedx-platform#37255 (todo, DEPR of the MFE runtime config API).

Brian's direction (2026-10-31): fix the read sites in learner-dashboard; the dev-config `config` blocks in the other converted apps should go, tracked on the frontend-base board if anywhere; the `getAppConfig` return is a frontend-base question of its own. None of it is for #879.

Workaround for the local run (Brian, 2026-10-31): `commonAppConfig: {}` added to `site.config.dev.tsx` in the code worktree, uncommitted, beside the author's dummy-data patch. The real fix depends on the outcome of openedx/frontend-base#337.

### 4. The custom category colors: where defined, how configured, how they reach the app, what UI, are they accessible

Status: drafted as comment 2 in `review-879-comments.md` (2026-10-31)
Rests on: src/components/CategoryBadge.tsx, src/utils/colors.ts, src/containers/CourseCard/components/CourseHeaderActions.tsx, src/hooks/usePathwayData.ts, src/data/services/lms/__mocks__/pathways.ts at f4852b343a; openedx-core main `src/openedx_catalog/models/pathway_category.py` and `admin.py`, openedx/openedx-core#820 and openedx/openedx-platform#39204 diffs, openedx/frontend-app-catalog#176 diff, openedx/frontend-app-learning#2159 diff, and the Willow Pathways Decision Log (Confluence 6630834191), all read 2026-10-31

Asked by Brian (2026-10-31).

**In this PR.** `PathwayData.pathway` carries optional `categoryBackgroundColor` and `categoryTextColor` strings per pathway (they are category properties, repeated on each pathway). `CategoryBadge` applies them as inline `style` only when both are present and both pass `isValidCssColor`; otherwise it falls back to the Paragon utilities `bg-info-200 text-info-800`. `isValidCssColor` (`src/utils/colors.ts`) asks `CSS.supports('color', value)`, with a fallback that assigns the value to a `span` and checks it stuck: it answers "is this a CSS color", nothing more. The "Course" badge on course cards is the same component with a fixed `className="text-dark-900 bg-light-500"` and no color props. The inline-style route exists because Paragon's color utilities carry `!important` (comment in the component). Only the mock data sets colors (`#FCE4F3` on `#9B1766` for the Tutorial category); Bootcamp uses the default.

**Where they are defined: nowhere yet.** The product decision is in the Willow Pathways Decision Log: "Each category has its own badge colour. The default background colour is #BFDBEA (info/200) blue with #004C77 (info/900) text. It's used whenever no other colour is set. More colours can be added by the instance admin as new categories are created. Courses use a fixed 'Course' badge with background colour #E1DDDB (light/500) and #000000 (black) text. Authors cannot change its wording or colour, and categories cannot use that colour. An instance can change it through theming." The backend does not implement that yet: `PathwayCategory` on openedx-core main has `category_code`, `title` and `title_plural` and no colour fields; openedx-core#820 (the Pathway content APIs, draft) adds none; openedx-platform#39204's `PathwaySerializer` emits `category` and `categoryLabel` and no colours. So the two fields this PR reads have no producer anywhere in the open backend work.

**Configuration path and UI, as intended.** Instance admin, per category, in the Django admin for `PathwayCategory` (openedx-core `admin.py` registers it with title, plural and code). That is the only UI the decision log names; no Studio or MFE surface. The learner-home API would carry the pair per pathway, as #39204 carries the label today. The catalog side has its own contract for the same pair: catalog#176's ADR 0003 says a backend "category registry" owns the slug, label and "an optional category color pair. When present, both colors are canonical `#RRGGBB`", enriched into the search response as `category_background_color`/`category_text_color`. That registry is the same `PathwayCategory` model, which has no such fields either.

**Accessibility: nothing checks it.** No contrast check in this PR, in catalog#176 (which duplicates `isValidCssColor` verbatim) or in learning#2159 (which types the fields but renders the strip without them). The decision log says nothing about contrast or accessibility. With a per-category free-form pair, the only guard would be on the admin side, and that side does not exist yet; `isValidCssColor` accepts any valid color, including a pair with no contrast. Also `CSS.supports('color', 'red')` is true, so the "canonical `#RRGGBB`" rule in the catalog ADR is not enforced here either.

**Small inconsistencies.** The default text token is `text-info-800` here while the decision log says info/900 (`#004C77`). The decision log's Explore section gives a different default ("dark blue with white text"), which is what catalog#176's mock uses (`#000cb0` on `#ffffff`), so the two apps' defaults diverge inside the same document.

Candidate comments: (1) the color props have no backend producer in #39204 or openedx-core#820, so either the serializer grows the pair or the props are premature; (2) no contrast guard anywhere, and where one should live (admin validation, since the frontend cannot refuse an operator's color without a policy); (3) `#RRGGBB` canonical form versus "any CSS color". (1) and (2) are cross-repo and may belong on the decision log or #39204 rather than here.

### 5. The inlined `CardsStackIcon` cites no source; Paragon alternatives

Status: drafted as comment 1 in `review-879-comments.md` (2026-10-31)
Rests on: src/utils/icons/CardsStackIcon.tsx, src/containers/PathwaysPanel/PathwaysList.tsx at f4852b343a; @openedx/paragon icons in the code worktree's node_modules (`icons/copy-mui-icons.js`, `icons/es5/*`); Figma comment thread (ChrisChV asked, cassiezamparini answered: "I used an icon from Google", Material Symbols `cards_stack`), pasted by Brian 2026-10-31; #878 at aca7e36 (`CoursesPanel/index.jsx`)

Source: the path in `CardsStackIcon.tsx` is byte-identical to Material Symbols Outlined `cards_stack` at weight 400, 24px (`fonts.gstatic.com/s/i/short-term/release/materialsymbolsoutlined/cards_stack/default/24px.svg`, fetched 2026-10-31), including the `0 -960 960 960` viewBox. Material Symbols is Apache 2.0, so inlining is allowed, but the file carries no attribution or licence note. The repo has no precedent for inlined icon components: `src/utils/icons/` is new in this PR, and the three `.svg` files under `src/assets` on master are illustrations. The only use is the category heading in `PathwaysList.tsx`, next to where #878 puts Paragon's `MenuBook` on the Courses heading.

What Paragon has: its icon set is copied from `@material-icons/svg` (Material Icons, the `sharp` variant, by `copy-mui-icons.js`), not Material Symbols. 2319 icon modules, three of them `*Outlined`; everything is the filled weight. There is no `cards_stack` equivalent by name.

Rendered side by side (reference first), file for Brian: `/tmp/claude-1000/-var-home-bsmith-code-reviews/9b317eef-413d-4b14-988b-c22d0db5876f/scratchpad/icons/montage.png`. Ranked by visual closeness to `cards_stack` with semantics that fit a pathways category heading:

1. `LibraryBooks`: a card with text lines over a trailing card, the same composition as `cards_stack`; "library" reads as a collection of learning content; filled, so it pairs with `MenuBook` on the Courses heading.
2. `DynamicFeed`: stacked cards with a header bar, very close in silhouette; "feed" is neutral.
3. `AutoAwesomeMotion`: three stacked rounded squares, the plainest "stack"; name is about an effect but the glyph is neutral.
4. `Collections` (overlapping frames with an image, reads as photos) and `FilterNone` (two overlapping outline squares, the one outline-weight candidate, but it reads as "copy").

Pathway-semantic but not visually similar: `Route`, `Signpost`, `Timeline`, `AccountTree`. Not recommended: `Style` (fanned swatches with a hole), `Queue` (stack with a plus), `CopyAll`, `WebStories`.

Candidate comment: either switch the heading icon to a Paragon icon (`LibraryBooks` first choice) so it matches the icon set the rest of the dashboard uses and themes with it, or, if the design team wants the Material Symbols glyph kept, add the source and licence to `CardsStackIcon.tsx`.

### 6. Full pass for dealbreakers and bigger conversations

Status: A drafted as comment 3 in `review-879-comments.md` (2026-10-31); B, C, D not posted
Rests on: the whole diff 162fad7fde..f4852b343a (3 commits, 37 files); #875 review threads (rpenido and ChrisChV on `src/components/ItemBadge.tsx`, kdmccormick on `README.rst`), read 2026-10-31; openedx/openedx-platform#39204 diff and body, read 2026-10-31

Scope: what should block or needs a conversation beyond this PR. Code-quality findings are deferred to the next pass. Already carried: colors (entry 4, bigger conversation), icon (entry 5, dealbreaker), panel placement (entry 2, resolved), cards not interactable (entry 3, resolved).

**A. The "Course" badge ships to every learner on every site now, before any pathway exists.** `CourseHeaderActions` renders `CategoryBadge` with the fixed "Course" label unconditionally on every course card. In #875 it was behind `ENABLE_PATHWAY_PILOT_UI`; rpenido asked to move the flag check out of the badge, ChrisChV answered that "using that card for courses only makes sense if another item exists, in this case, the pathways", and kdmccormick then asked to drop the flag with the reasoning that an operator who does not want pathways "will not create enrollable pathways". That reasoning holds for the panel, which renders nothing with no pathways, and not for the badge, which has no such gate. Result: a visible change on every Open edX dashboard for a pilot feature, labelling every card "Course" on sites that will never have a second kind of card, by the author's own account of when the badge makes sense. Conversation: gate the badge on the learner having at least one pathway (the data is already on the page), or accept the badge as a permanent design change and say so in the body.

**B. The data contract is a frontend guess that already disagrees with the backend draft, and it is frozen into a `.v1` slot.** `PathwayData` and `PathwaysInCategoryData` are defined in `src/hooks/usePathwayData.ts` with `itemCount`, `progress.completedItemCount`, per-pathway `categoryLabelPlural` and the two color fields; the grouping has no field of its own, so the panel reads the plural label off `pathways[0]`. openedx-platform#39204's serializers emit `courseCount` and `completedCourseCount`, put `categoryLabelPlural` on the group, carry no colors, and its body says the item-count fields are "for design discussion" and that the plural "temporarily returns the localized singular". The TODO in `api.ts` says the response "must be mapped here", so the mapping is deferred to a PR that does not exist. Meanwhile `PathwaysPanelSlot` publishes `pathwaysByCategory` in that shape as the prop of `org.openedx.frontend.slot.learnerDashboard.pathwaysPanel.v1`, and the slot README documents plugins reading `pathways[0].pathway.categoryLabelPlural`. A `.v1` plugin contract whose shape is expected to change when the backend lands is the same conversation as openedx/frontend-base#336 from #878: what an app's slot props promise. Conversation: settle the shape with #39204 before the slot is public, or ship the slot without the prop, or mark it unstable. Downgraded (Brian, 2026-10-31): the dashboard is on the `2.0.0-alpha` channel, so the slot's prop shape can change before a stable release promises it; the mismatch with #39204 is a mapping-PR concern, not a merge blocker.

**C. The panel loads separately, fails silently, and pushes the courses down when it arrives.** `usePathwaysByCategory` is its own query; the dashboard renders `DashboardLayout` once `useInitializeLearnerHome` resolves, and the panel is inserted above `CoursesPanel` whenever the pathways query resolves, so with a real backend the course list jumps down after first paint (compounded by entry 2). `data ?? []` also hides `isError`: a failed pathways request shows no panel and nothing else, with react-query's default retries. For the pilot that may be acceptable; it should be a decision rather than a default. Smaller conversation.

**D. Shipped mock data names real institutions.** `src/data/services/lms/__mocks__/pathways.ts` ships in `src/` with "MIT OpenCourseWare", "Stanford" and "OpenCraft" as providers. It is test-only unless the dev patch is applied, but it is in the repo. Small; placeholder names would do.

Not dealbreakers, parked for the quality pass: the hard-coded `width: '250px'` on the card actions (narrow screens), `className="h3"` on a `Stack` and the non-heading category labels (entry 2), the `key={categoryLabelPlural}` collision if two categories share a plural, the `jest.config.js` ignore pattern widening from `src/__mocks__` to `__mocks__`.

Summary for Brian: dealbreaker is the icon (entry 5). Bigger conversations are the colors (entry 4) and the Course badge for everyone (A). B, C and D are smaller.
