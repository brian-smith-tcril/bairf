# Decisions while writing the slot how-to for openedx/frontend-base#340

1. **Nothing from the FPF era is cited.** The three v1/v2 pairs in the org (recorded in `plan-340.md`, Prior art) shaped the examples only. Brian, 2026-11-02.
2. **Examples are invented, ordered least to most complex**: a prop rename, a prop type change, several changes at once. The rename is written; the other two are placeholders in the first draft. Brian, 2026-11-02.
3. **One arrangement, `v2` wraps `v1`.** The how-to prescribes it and does not describe siblings or `v1`-wraps-`v2`. Every existing pair in the org took it, and it is the one where every old operation keeps working and a new-version replace takes the old version with it.
4. **`@deprecated` notes are split by where an editor shows them**: the interface note names the new interface and the new slot id; each renamed member's note names its new name. Brian's reaction to the first wording, 2026-11-02.
5. **Props interfaces are versioned from the first bump** (`GreetingSlotV1Props`, `GreetingSlotV2Props`), with the unversioned name kept as a deprecated alias of `v1` until `v1` is removed, so a site config typed against it compiles through the coexistence window. Open question 2 of the plan, taken provisionally in the draft; not yet confirmed by Brian.
6. **The DEPR ticket is filed when the new version first ships from `stable`**, not when it lands on `main`. Brian, 2026-11-03: `main` publishes alpha prereleases (`.releaserc`: `main` → channel `alpha`, `stable` → `latest`), so there is no ticket to link at commit time. The `README.v1.md` warning therefore says only "deprecated and will be removed in a future release" and gets the ticket link added later by step 6. Supersedes the earlier reading of ADR 0009 §3 as "at landing" (plan open question 1); the draft still cites ADR 0009 §3 for the process and does not cite ADR 0018 (openedx/frontend-base#343). **Step dropped from the draft on 2026-11-03**: Brian wants the DEPR-ticket step written after the PR-body question about tracking deprecations (plan, "Open questions for the PR body") has been discussed. The removal step still says to wait for the deprecation process.
7. **Runtime warnings, pre-release apps, and a link from ADR 0009 are not mentioned** (plan open questions 3, 4, 5), pending Brian.
8. **File is `docs/how_tos/add-a-slot-version.md`, Markdown**, title "How to: Add a New Version of a Slot". The first draft was `slot-versioning.md`, "How to: Change a Slot's Props"; Brian found both titles confusing (2026-11-02), and the readability pass renamed the file after the procedure the reader follows. The link from the migration how-to's "Refactor slots" section is not yet added.
9. **Each slot version gets its own README**: `README.md` is the current version and links to the previous one, `README.v1.md` is the old version with the deprecation note at its top. Brian recalled FPF slots not sharing one README across versions (2026-11-03); checked this session: all three surveyed v1/v2 pairs keep separate files (authoring `CourseAuthoringUnitSidebarSlot/README.md` + `README.v1.md` in openedx/frontend-app-authoring#2000; header `v1/README.md` + `v2/README.md` subfolders in openedx/frontend-component-header#663 and #682). The how-to uses the sibling-file layout and, per decision 1, does not cite any of them.
10. **The person inserting widgets is an "operator"**, ADR 0009's word, not "plugin author" (ADR 0011's). "Site config" is named only where the operator's diff is shown. Brian's objection to site configs framing the overview, 2026-11-03.
11. **The overview and first example were rewritten with Brian sentence by sentence** (2026-11-03). Settled framing: a change that would break the contract cannot land without bumping the version; a bare bump is a breaking change to the app; ideally both versions coexist with the old one deprecated and removed later; the guide provides examples of some ways to do that. "Breaking change" is said only of the app, never as a label for the category of slot change. The classification table is gone: which changes need a new version is ADR 0009's and openedx/frontend-base#343's job. The rename example opens with two what-not-to-do diffs (rename in place; bump without keeping v1) before the steps.
12. **The examples are tested from `runtime/slots`, not `docs/`** (Brian, 2026-11-03). Jest's projects are `tools`, `runtime`, `shell`, and `tsconfig.json` includes only `runtime/**` and `shell/**`, so nothing under `docs/` runs or type-checks. Fixtures live in `runtime/slots/testMocks/` because `tsconfig.build.json` excludes `**/testMocks/**` from the published build (precedent: `runtime/testMocks/`, `shell/testMocks/`). One fixture per state the markdown shows (three per example). `howToExamples.test.tsx` runs the operator-usage matrix from the plan; `howToExamples.drift.test.ts` asserts every `tsx` block under an `## Example:` heading is a verbatim substring of one of that example's fixtures, ignoring import lines (fixtures import `Slot` by relative path; no `@openedx/frontend-base` self-mapping exists) and doc-comment lines (the how-to shows the interfaces with and without `@deprecated` notes), with each `@deprecated` line checked separately. Results at commit time: `npm run test -- runtime/slots` 111 passed; `npm run typecheck` clean, including widgets typed `({ userName }: GreetingSlotProps)` with no cast, so the how-to's operator diff compiles under the repo's config; `eslint .` and `lint:tools` clean; the test-site lint step needs a built `dist/` (`openedx` CLI) and was not run.
13. **Review round, 2026-11-03.** A context-free agent reviewed the branch. Taken: the step 2 bullet claiming a `v2` layout "replaces `v1` and everything in it" contradicted `useWidgets()` (a replacement layout still receives `defaultContent`, the inner `v1` slot) and the test "keeps v1 and its widgets inside a replaced v2 layout"; it is now its own bullet saying the layout receives `v1` as its `defaultContent` widget. "Computed once" dropped from the rename's step 2 (nothing is computed there). Step 3 heading is "Mark the old version as deprecated" in both examples (the "where an operator will see it" clause promised a place the body no longer named once the editor sentence was cut). The drift test now checks both sides of every `diff` block, not only `tsx` fences: Brian's rule, "either we check the diffs or not", since even the what-not-to-do diffs produce valid slots. That needed fixtures for the two what-not-to-do states (`GreetingSlotRenamedInPlace.tsx`, `GreetingSlotBumpedInPlace.tsx`) and for the operator's widget before and after its move (`greetingWidgets.tsx`), each with a behaviour test that verifies the how-to's stated reason: the renamed-in-place slot gives a widget reading `userName` undefined and the typecheck rejects that widget (one test, `@ts-expect-error` on the widget; Brian merged the earlier two tests because a jest test cannot assert a compile failure); the bumped-in-place slot no longer renders a `v1` widget; the operator's widget replaces the default content on the states each side of the diff applies to. The four `useSlotContext() as unknown as X` casts became one `useSlotProps<Props>()` helper; Brian accepts it in a test only. Nothing in the runtime gives a layout a typed read of the slot's props (`SlotContext` is its fixed members plus an index signature; the dev showcase narrows with `typeof`); a possible runtime issue, outside this how-to. Kept as written: "ideally" (Brian: coexistence may not always be possible, deprecating without a replacement would be the rare exception); the alias note "Renamed to `GreetingSlotV1Props`" (true, one hop more); no sentence on the `Banner` stand-in's own props changing (it exists only for the tests). Deferred: an `OPTIONS` test to the widget-options example, since neither example takes options. Not decided: "Moving a widget to `v2`" sitting after step 6, an `idAliases` steer, the README and `index.ts` conventions being stated without repo precedent.
14. **The third example is "a prop that becomes a list", not "several changes at once"** (Brian, 2026-11-03). A taggable item slot's (`TaggableItemSlot`, Brian's name over "filter") `selectedTag: string` becomes `selectedTags: string[]`. The nearest `v1` value, `selectedTags[0]`, loses the rest of the list, so `v1` gains `selectedTags` as well (adding a member does not break the contract) and `selectedTag` is deprecated within `v1` pointing at `selectedTags`; `v2` is `v1` without the old member. Brian's reasoning: a `v1` widget only sees the inner slot's props, so adding the list to `v1` is the only way it can get the rest without moving slot id; the removal of the deprecated member is the break, so the removal is what gets the new version. Step 4 differs from the rename for the first time (`README.v1.md` documents the new prop). The banner could have done the same (`v1` gaining `notice`) but its `message` is exact, not degraded, so it is not retrofitted. A widened union of allowed values was considered for this example and set aside with the widget-options example. Fixtures `TaggableItemSlotV1.tsx`, `TaggableItemSlotV1V2.tsx`, `TaggableItemSlotV2.tsx`; the usage matrix plus one test that a `v1` widget gets the first tag under the old name and the whole list under the new one when two are selected. Results: `npm run test -- runtime/slots` 158 passed, typecheck clean, `eslint .` and `lint:tools` clean.
15. **Every example opens the same way: the slot, its code, the change in one sentence** (Brian, 2026-11-03). The banner's and list example's prefaces ("This example follows the same steps as the rename. ...") jumped between ideas before the reader had seen the slot; "follows the same steps" is redundant with the repeated headings and the "Same as for the rename" steps. The idea each preface carried moved to the step that acts on it: the banner's is already step 2's sentence; the list's ("the old prop can hold only one of the tags") now opens step 1.
16. **The list example's step 1 is split: the versioned interfaces first, then "`selectedTags` can also be added to `v1` as a non-breaking change" with a diff adding it** (Brian, 2026-11-03). Three earlier wordings of a single step 1 paragraph failed because they asserted the benefit of adding the list ("instead of only the first tag") before step 2 establishes that `v1` receives `selectedTags[0]`; Brian spotted that nothing in step 1 says the first entry of the list is `selectedTag`. Each fact now sits at the step that shows it: the mapping and the benefit in step 2, the deprecation in step 3. Settled after three corrections from Brian the same hour as three blocks in order: the old interface under its versioned name with the alias; the new interface; then "`selectedTags` can also be added to `v1` as a non-breaking change" with a diff adding it to `TaggableItemSlotV1Props`. The two rejected shapes were one block holding both interfaces (the `v1` part did not belong in a block meant to show `v2`) and a diff against `TaggableItemSlotV1Props` with no block declaring it (it assumed `v1` existed when it did not yet). The state after the first two blocks, `v2` wrapping `v1` with only the first tag passed down, is the fixture `TaggableItemSlotV1V2FirstTagOnly.tsx`, with one behaviour test: a `v1` widget sees only the first tag when two are selected. The claim test (a `v1` widget gets the first tag under the old name and the whole list under the new one) runs on `v2` wrapping `v1`. Results: `npm run test -- runtime/slots` 162 passed, typecheck clean, `eslint .` and `lint:tools` clean.
17. **The list example's steps 1 and 2, settled line by line with Brian (2026-11-03).** Register is imperative, as in the rename's "Give the two interfaces versioned names": prose that narrates what the block shows ("the old interface is renamed", "`v1` gets the first item") was rejected each time as "saying x is done". Step 1's three lead-ins: "Version and alias the old interface." / "Declare the new interface with only the list." / "`selectedTags` can also be added to `v1` so widgets in the `v1` slot can read the list. This is purely additive and non-breaking." (Brian's sentence, minus the "You can" he first wrote; the how-to has no "you"). Step 2 opens with the general point, since this is the first example where the old prop has no direct source in the new ones: "Without a 1:1 mapping from the new props to the old ones, there is a choice to make about what the old slot gets. Here `v1` expects a single tag and `v2` has a list." Rejected on the way: "the maintainer's call" and "judgement call" (a reader following the how-to is the maintainer and should not feel the choice is someone else's), "decided case by case", "whatever makes sense on a case-by-case basis", "is a decision" standing alone; "there is a choice to make" carries Brian's "a choice you'll need to make" without the pronoun. The wrapper is a function so the choice is a named line with a comment: `const selectedTag = selectedTags[0] ?? '';` under "// v1 takes a single tag. This example gives it the first of the list, or an empty string when the list is empty." Brian caught the empty-list hole (`selectedTags[0]` is `undefined` against a `string` contract; the repo does not enable `noUncheckedIndexedAccess`, so the typecheck is silent); of falling back to `''`, not rendering `v1` when empty, or typing the list non-empty, he chose the fallback. The drift test now also requires every `//` line in a how-to block to appear verbatim in a fixture, as it did for `@deprecated` lines, so the comment is guarded. One test added: with an empty list on `v2` wrapping `v1`, a `v1` widget reading `selectedTag` renders `""` (asserted through `JSON.stringify`, which tells `''` from `undefined`). Results: `npm run test -- runtime/slots` 164 passed, typecheck clean, `eslint .` and `lint:tools` clean.

19. **`idAliases` is not used for expand/contract, and the how-to does not offer it** (Brian, from a discussion with Adolfo, relayed 2026-11-04). Example: a slot with optional `propA` is `v1`; add optional `propB`, bump the id to `v2`, keep the `v1` id as an alias. Both ids are now one slot with one props interface holding `propA` and `propB`, so removing `propA` breaks `v2` as well as `v1` and needs a `v3`. An alias never lets the contract contract. Wrapping gives each version its own interface, so removing the inner `v1` is the contraction and `v2`'s contract never grows. `idAliases` stays what `Slot`'s own comment says it is: renaming an id with the contract unchanged. The reviewer's "`idAliases` is never mentioned" (decision 13) is answered by this; whether a sentence saying so goes in the how-to or only in the PR body is Brian's call.
20. **Fourth example, "a slot whose default widget takes options", written 2026-11-04** (Brian: "go ahead and write it up, it might be helpful to see the example instead of talking about it as a hypothetical"). Mechanism, read in `runtime/slots/widget/hooks.ts`, `WidgetProvider.tsx` and `utils.tsx`: every widget renders inside a `WidgetProvider` carrying its slot's id and its own id; `useWidgetOptions()` merges the `OPTIONS` operations on that slot naming that widget; with `v2` wrapping `v1` the default widget is `v1`'s `defaultContent`, and `v2`'s `defaultContent` is the `v1` `<Slot>` element, so a `v2` operator's `OPTIONS` on `defaultContent` matches an element that reads nothing. `useWidgetOptionsForId(slotId, widgetId)` is exported, so the default widget reads `v2`'s options by id as well, merged with `v2` winning. Choices taken without Brian (offered, not yet confirmed): the trigger is a plain rename (`links` to `relatedLinks`) so steps 1, 3, 4 and 5 are "Same as for the rename" and only the options differ; the default widget takes the slot's value as a JSX prop from the wrapper rather than through `useSlotContext()` (the catalog's `DefaultSocialLinksWidget` reads context with the cast Brian dislikes); one scalar option, `max`, not the catalog's function-valued list. Brian's invariant from the alias discussion (decision 19) holds and is stated at step 6: a `v2` operator's `OPTIONS` on `defaultContent` reaches the widget by id before the removal and through `useWidgetOptions()` after, so a `v2` site config does not notice the removal; the usage matrix's `v2 wrapping v1` and `v2 only` columns are the check. The how-to shows the operator's `OPTIONS` operation as a `ts` block, so the drift test now reads `ts` fences as well as `tsx` and that block has a fixture, `relatedLinksOptions.ts`. Fixtures `RelatedLinksSlotV1.tsx`, `RelatedLinksSlotV1V2.tsx`, `RelatedLinksSlotV2.tsx`. Tests beyond the matrix: the operator's `v1` max caps the list on `v1 only` and wrapped (the `OPTIONS` test deferred in decision 13); a `v2` max caps it wrapped and on `v2 only`; a `v2` max wins over a `v1` max wrapped; the `v1` max does nothing on `v2 only`. Results: `npm run test -- runtime/slots` 197 passed, typecheck clean, `eslint .` and `lint:tools` clean. ADR 0009 does not mention widget options (grepped), so the example does not make the option the reason for the bump.
21. **The widget-options example is a tree list gaining a required `foliage`, not related links with a `max`** (Brian, 2026-11-04, after a long search). Brian rejected the related links version because the spread merge of two option objects felt specific; a survey of every `useWidgetOptions`/`useLayoutOptions` call in the org (catalog `CourseAboutSidebarSocialSlot`; frontend-base shell `CoursesLink`, `WidgetWithOptions`, `RevealLinks`, `LabeledLinkColumn`, `NavDropdownMenuSlot`; docs.openedx.org porting how-to) showed one source per consumer and a `??` fallback, nobody merging two, because no slot with options has been versioned yet. The social links slot was the model: its option is a transformation of the prop (an array or a function of the current list), so what breaks a `v1` operator's function is the item shape changing. Brian's technical shape: "we had this info in a free-text description field, now we're moving a piece of it to a structured field and have decided it is required going forward". Constraints that emerged from the rejections, in order: not learning-focused (uncanny valley), not subjective (roast, heat, size), not a messy enum (USB versions, wattage, PD's 100 W), not a field that would obviously have been structured from day one (book format, vehicle fuel), not a fact the app could default to (tabs' `/${id}`, bulbs' "not dimmable", "the provider v1 had"), not per-part of the item (venue access vs a balcony seat), not open-ended (credit roles), not theming (Paragon's variant work), not the real social slot with visible labels (too close, a design change Brian would argue against, and a derived string instead of an enum). The conflict named along the way: a UI-level list the app seeds is homogeneous on any field it did not need yet, so a new field always has a sensible default there; a required field needs items that genuinely differ on a fact the app cannot know, which is domain data. Brian accepted domain data; the "fake real thing" had to feel right. Trees won because Open edX releases are named after them. Field `foliage: 'evergreen' | 'deciduous'` (Brian: "foliage", from the botanical definition of evergreen, not "leaves"); seeded Redwood, Sumac, Willow, avoiding edge species like Teak and bald Cypress; the operator's `v1` option adds Olive. Brian's rendering: `v1` lists names only; `v2` prefixes 🌳 or 🌲; 🪾 for a `v1`-added tree, which he notes nobody would really want for a slot but reads well in an example. Shape of step 2, carrying the invariant from decision 19: `v2`'s option is applied to the plain `v2` list first, exactly as it will be after removal, then `v1`'s option on top to `v1`-shaped trees (foliage stripped going in, restored by id coming out, `'unknown'` for a tree it added), so a `v2` operator's function never receives `'unknown'` and the `v2` contract is the same before and after removal; `ShownTree` with `'unknown'` is the widget's own type and the removal diff deletes it. `Tree` is versioned (`TreeV1`, `TreeV2`, deprecated alias) under the exported-types rule, with the options interfaces local and versioned alongside. Fixtures `TreeListSlotV1.tsx`, `TreeListSlotV1V2.tsx`, `TreeListSlotV2.tsx`, `treeListOptions.ts` (`addOliveV1`). Tests beyond the matrix: the `v1` option lists Olive on `v1 only`, marks it 🪾 wrapped, is ignored on `v2 only`; a `v2` option's Olive shows 🌲 wrapped and on `v2 only`; a `v1` rename keeps the tree's foliage; a `v2` function sees exactly `['evergreen', 'deciduous', 'deciduous']` with a `v1` option adding Olive (the invariant); a `v2` filter and a `v1` add both apply. `defaultContentText` became `string | RegExp` because `v1` prints "Redwood" and `v2` "🌲 Redwood". Results: `npm run test -- runtime/slots` 210 passed, typecheck clean, `eslint .` and `lint:tools` clean. Supersedes the related links parts of decision 20. **Same day, `description` dropped from `Tree`** (Brian): the free-text-to-structured story was the design conversation's, not the how-to's; the example's point is that the list now expects something new (🌲 vs 🌳), so a new required field is clear on its own. The change sentence is now "Each tree is to show its foliage, evergreen or deciduous, which is a new required field."
