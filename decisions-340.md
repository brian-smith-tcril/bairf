# Decisions while writing the slot how-to for openedx/frontend-base#340

1. **Nothing from the FPF era is cited.** The three v1/v2 pairs in the org (recorded in `plan-340.md`, Prior art) shaped the examples only. Brian, 2026-11-02.
2. **Examples are invented, ordered least to most complex**: a prop rename, a prop type change, several changes at once. The rename is written; the other two are placeholders in the first draft. Brian, 2026-11-02.
3. **One arrangement, `v2` wraps `v1`.** The how-to prescribes it and does not describe siblings or `v1`-wraps-`v2`. Every existing pair in the org took it, and it is the one where every old operation keeps working and a new-version replace takes the old version with it.
4. **`@deprecated` notes are split by where an editor shows them**: the interface note names the new interface and the new slot id; each renamed member's note names its new name. Brian's reaction to the first wording, 2026-11-02.
5. **Props interfaces are versioned from the first bump** (`GreetingSlotV1Props`, `GreetingSlotV2Props`), with the unversioned name kept as a deprecated alias of `v1` until `v1` is removed, so a site config typed against it compiles through the coexistence window. Open question 2 of the plan, taken provisionally in the draft; not yet confirmed by Brian.
6. **The DEPR ticket is filed when the new version first ships from `stable`**, not when it lands on `main`. Brian, 2026-11-03: `main` publishes alpha prereleases (`.releaserc`: `main` → channel `alpha`, `stable` → `latest`), so there is no ticket to link at commit time. The `README.v1.md` warning therefore says only "deprecated and will be removed in a future release" and gets the ticket link added later by step 6. Supersedes the earlier reading of ADR 0009 §3 as "at landing" (plan open question 1); the draft still cites ADR 0009 §3 for the process and does not cite ADR 0018 (openedx/frontend-base#343). **Step dropped from the draft on 2026-11-03**: Brian wants the DEPR-ticket step written after the PR-body question about tracking deprecations (plan, "Open questions for the PR body") has been discussed. The removal step still says to wait for the deprecation process.
7. **Runtime warnings, pre-release apps, and a link from ADR 0009 are not mentioned** (plan open questions 3, 4, 5), pending Brian.
8. **File is `docs/how_tos/add-a-slot-version.md`, Markdown**, title "How to: Add a New Version of a Slot". The first draft was `slot-versioning.md`, "How to: Change a Slot's Props"; Brian found both titles confusing (2026-11-02), and the readability pass renamed the file after the procedure the reader follows. The link from the migration how-to's "Refactor slots" section is not yet added.
9. **Each slot version gets its own README**: `README.md` is the current version and links to the previous one, `README.v1.md` is the old version with the deprecation note at its top. Brian recalled FPF slots not sharing one README across versions (2026-11-03); checked this session: all three surveyed v1/v2 pairs keep separate files (authoring `CourseAuthoringUnitSidebarSlot/README.md` + `README.v1.md` in openedx/frontend-app-authoring#2000; header `v1/README.md` + `v2/README.md` subfolders in openedx/frontend-component-header#663 and #682). The how-to uses the sibling-file layout and, per decision 1, does not cite any of them.
10. **The person inserting widgets is an "operator"**, ADR 0009's word, not "plugin author" (ADR 0011's). "Site config" is named only where the operator's diff is shown. Brian's objection to site configs framing the overview, 2026-11-03.
11. **The overview and first example were rewritten with Brian sentence by sentence** (2026-11-03). Settled framing: a change that would break the contract cannot land without bumping the version; a bare bump is a breaking change to the app; ideally both versions coexist with the old one deprecated and removed later; the guide provides examples of some ways to do that. "Breaking change" is said only of the app, never as a label for the category of slot change. The classification table is gone: which changes need a new version is ADR 0009's and openedx/frontend-base#343's job. The rename example opens with two what-not-to-do diffs (rename in place; bump without keeping v1) before the steps.
12. **The examples are tested from `runtime/slots`, not `docs/`** (Brian, 2026-11-03). Jest's projects are `tools`, `runtime`, `shell`, and `tsconfig.json` includes only `runtime/**` and `shell/**`, so nothing under `docs/` runs or type-checks. Fixtures live in `runtime/slots/testMocks/` because `tsconfig.build.json` excludes `**/testMocks/**` from the published build (precedent: `runtime/testMocks/`, `shell/testMocks/`). One fixture per state the markdown shows (three per example). `howToExamples.test.tsx` runs the operator-usage matrix from the plan; `howToExamples.drift.test.ts` asserts every `tsx` block under an `## Example:` heading is a verbatim substring of one of that example's fixtures, ignoring import lines (fixtures import `Slot` by relative path; no `@openedx/frontend-base` self-mapping exists) and doc-comment lines (the how-to shows the interfaces with and without `@deprecated` notes), with each `@deprecated` line checked separately. Results at commit time: `npm run test -- runtime/slots` 111 passed; `npm run typecheck` clean, including widgets typed `({ userName }: GreetingSlotProps)` with no cast, so the how-to's operator diff compiles under the repo's config; `eslint .` and `lint:tools` clean; the test-site lint step needs a built `dist/` (`openedx` CLI) and was not run.
13. **Review round, 2026-11-03.** A context-free agent reviewed the branch. Taken: the step 2 bullet claiming a `v2` layout "replaces `v1` and everything in it" contradicted `useWidgets()` (a replacement layout still receives `defaultContent`, the inner `v1` slot) and the test "keeps v1 and its widgets inside a replaced v2 layout"; it is now its own bullet saying the layout receives `v1` as its `defaultContent` widget. "Computed once" dropped from the rename's step 2 (nothing is computed there). Step 3 heading is "Mark the old version as deprecated" in both examples (the "where an operator will see it" clause promised a place the body no longer named once the editor sentence was cut). The drift test now checks both sides of every `diff` block, not only `tsx` fences: Brian's rule, "either we check the diffs or not", since even the what-not-to-do diffs produce valid slots. That needed fixtures for the two what-not-to-do states (`GreetingSlotRenamedInPlace.tsx`, `GreetingSlotBumpedInPlace.tsx`) and for the operator's widget before and after its move (`greetingWidgets.tsx`), each with a behaviour test that verifies the how-to's stated reason: the renamed-in-place slot gives a widget reading `userName` undefined and the typecheck rejects that widget (one test, `@ts-expect-error` on the widget; Brian merged the earlier two tests because a jest test cannot assert a compile failure); the bumped-in-place slot no longer renders a `v1` widget; the operator's widget replaces the default content on the states each side of the diff applies to. The four `useSlotContext() as unknown as X` casts became one `useSlotProps<Props>()` helper; Brian accepts it in a test only. Nothing in the runtime gives a layout a typed read of the slot's props (`SlotContext` is its fixed members plus an index signature; the dev showcase narrows with `typeof`); a possible runtime issue, outside this how-to. Kept as written: "ideally" (Brian: coexistence may not always be possible, deprecating without a replacement would be the rare exception); the alias note "Renamed to `GreetingSlotV1Props`" (true, one hop more); no sentence on the `Banner` stand-in's own props changing (it exists only for the tests). Deferred: an `OPTIONS` test to the widget-options example, since neither example takes options. Not decided: "Moving a widget to `v2`" sitting after step 6, an `idAliases` steer, the README and `index.ts` conventions being stated without repo precedent.
14. **The third example is "a prop that becomes a list", not "several changes at once"** (Brian, 2026-11-03). A taggable item slot's (`TaggableItemSlot`, Brian's name over "filter") `selectedTag: string` becomes `selectedTags: string[]`. The nearest `v1` value, `selectedTags[0]`, loses the rest of the list, so `v1` gains `selectedTags` as well (adding a member does not break the contract) and `selectedTag` is deprecated within `v1` pointing at `selectedTags`; `v2` is `v1` without the old member. Brian's reasoning: a `v1` widget only sees the inner slot's props, so adding the list to `v1` is the only way it can get the rest without moving slot id; the removal of the deprecated member is the break, so the removal is what gets the new version. Step 4 differs from the rename for the first time (`README.v1.md` documents the new prop). The banner could have done the same (`v1` gaining `notice`) but its `message` is exact, not degraded, so it is not retrofitted. A widened union of allowed values was considered for this example and set aside with the widget-options example. Fixtures `TaggableItemSlotV1.tsx`, `TaggableItemSlotV1V2.tsx`, `TaggableItemSlotV2.tsx`; the usage matrix plus one test that a `v1` widget gets the first tag under the old name and the whole list under the new one when two are selected. Results: `npm run test -- runtime/slots` 158 passed, typecheck clean, `eslint .` and `lint:tools` clean.
15. **Every example opens the same way: the slot, its code, the change in one sentence** (Brian, 2026-11-03). The banner's and list example's prefaces ("This example follows the same steps as the rename. ...") jumped between ideas before the reader had seen the slot; "follows the same steps" is redundant with the repeated headings and the "Same as for the rename" steps. The idea each preface carried moved to the step that acts on it: the banner's is already step 2's sentence; the list's ("the old prop can hold only one of the tags") now opens step 1.
16. **The list example's step 1 is split: the versioned interfaces first, then "`selectedTags` can also be added to `v1` as a non-breaking change" with a diff adding it** (Brian, 2026-11-03). Three earlier wordings of a single step 1 paragraph failed because they asserted the benefit of adding the list ("instead of only the first tag") before step 2 establishes that `v1` receives `selectedTags[0]`; Brian spotted that nothing in step 1 says the first entry of the list is `selectedTag`. Each fact now sits at the step that shows it: the mapping and the benefit in step 2, the deprecation in step 3. The diff's before side and the first block are the state with `v2` wrapping `v1` and only the first tag passed down, so that state is a fixture, `TaggableItemSlotV1V2FirstTagOnly.tsx`, with one behaviour test: a `v1` widget sees only the first tag when two are selected. Results: `npm run test -- runtime/slots` 161 passed, typecheck clean, `eslint .` and `lint:tools` clean.
