### How it works today

**Every model-store write now originates in React Query.** There are no
thunks and no slice writers left. Two write paths:

   `QueryCache`'s `onSuccess` in `src/queryClient.ts`. A query opts in through

### Four structural facts that make this more than a find-and-replace

**1. `useModel` returns `{}` for a missing model; a query returns `undefined`
while pending.** Readers destructure directly off the result
(`const { org, celebrations } = useModel('courseHomeMeta', courseId)`), so a
faithful swap needs a `?? {}` at each site.

**2. `courseHomeMeta` is one model-store entry but two query cache entries.**
`courseHomeQueryKeys.metadata(courseId, rootSlug)` includes `rootSlug`, and
callers pass `'outline'` (every course-home tab, `CourseAccessErrorPage`) or
`'courseware'` (`CoursewareContainer`, `redirects`, `CourseExit`,
`courseware/data/apiHooks`). The same endpoint is fetched under both keys.
`rootSlug` changes exactly one thing in the response —
`normalizeCourseHomeCourseMetadata` maps the API's `courseware` tab id to
`rootSlug`:

```js
slug: tab.tabId === 'courseware' ? rootSlug : tab.tabId,
```

The model store keeps **one** `courseHomeMeta[courseId]` (the bridge's
`addModel` replaces it wholesale), so the bucket always holds whichever variant
was fetched most recently — which is always the right one, because only one
root page is mounted at a time. That is why today's 53 readers need no root:
"which variant" is answered implicitly by what is mounted. A query read cannot
inherit that, since the two variants are separate cache entries. See D2.

**3. Some readers deliberately read a model they do not own.**
`useEnrollmentAlert` and `useLogistrationAlert` are called from
`LoadedTabPage`, i.e. on *every* tab, and read `useModel('outline', courseId)`.
On a tab that never fetched the outline they get `{}` and stay hidden; after
the learner has visited the outline tab they read the populated model. Swapping
in `useOutlineTabData(courseId)` would **fire the outline-tab request on every
tab** — a behavior change. These need a non-fetching cache read.

**4. `sequences` and `coursewareMeta` are merges of two queries.**

- `sequences[id]` is `{ id, title, sectionId }` from the outline query for
  every sequence, *plus* the full `normalizeSequenceMetadata` shape
  (`unitIds`, `activeUnitIndex`, `gatedContent`, `isTimeLimited`, …) for
  whichever sequence is active. So `useModel('sequences', id)` returns a
  different shape depending on which sequence it is, and converted readers must
  pick the query that owns the fields they read.
- `coursewareMeta[courseId]` is `normalizeMetadata(...)` from the metadata
  query merged with `{ id, title, sectionIds, hasScheduledContent }` from the
  outline query's `courses` map. **`title` is written by both** (`data.name` vs
  the outline's `title`); no reader of `coursewareMeta.title` was found, so the
  collision looks inert — confirm during D3.

## Decisions to settle before writing code

**D1 — reader shape.** No new per-model hooks; convert each site to the owning
query with a property read and a default, e.g.
`const { org } = useCourseHomeMeta(courseId).data ?? {};`. Query deduping makes
repeated call sites of the same `useQuery` free, and it keeps each diff to one
line. The only signature change anywhere is `useCourseHomeMeta` *losing* its
`rootSlug` parameter (D2).

**D2 — `tabs[].slug` is view state, not server data (fact 2). Decided: collapse
the cache key and let the comparison carry the rule** (layer B1).

The stamped `slug` is not something the LMS returns — it is a pre-resolved
answer to a comparison. The LMS returns **one** tab entry (`tabId: 'courseware'`)
for a destination learning splits into two pages, and both pages render the same
nav, where highlighting is string equality (`CourseTabLink.tsx:16`,
`active: slug === activeTabSlug`). Neither fixed value works — `'outline'` fails
to highlight on courseware, `'courseware'` fails on the course-home page — so
something has to know that this one tab is "the current page" in two different
situations.

That knowledge has to live either in the data or in the comparison. PR #861
(2022, "unify source of tabs") put it in the data: it pointed both pages at the
course-home metadata endpoint and replaced the hardcoded
`slug: tab.tabId === 'courseware' ? 'outline' : tab.tabId` with a `rootSlug`
parameter, passed `'outline'` by `fetchTab` and `'courseware'` by `fetchCourse`.
That was the cheap choice then: the thunks were *per-page* fetchers, so fetch
time and render time were the same moment and every consumer stayed a dumb
equality check.

It stops fitting here because React Query keys on **what was requested** while
this field encodes **who was asking**. So put the rule where the question is
asked:

- `getCourseHomeCourseMetadata` drops its `rootSlug` parameter;
  `normalizeCourseHomeCourseMetadata` emits `slug: tab.tabId`. The field keeps
  the name `slug` (smaller diff; `CourseTabLinksSlot`'s type and every consumer
  stay as they are).
- `courseHomeQueryKeys.metadata(courseId)` loses the parameter — **one cache
  entry per course** instead of two.
- A shared predicate expresses the rule for the two comparison sites
  (`course-tabs/CourseTabLink.tsx:16` and `tab-page/LoadedTabPage.tsx:46`):

```ts
// The LMS returns a single tab for both the course-home page and courseware,
// so it is the active tab on either of them.
const isActiveTab = (tab, activeTabSlug) => (
  tab.slug === 'courseware'
    ? activeTabSlug === 'outline' || activeTabSlug === 'courseware'
    : tab.slug === activeTabSlug
);
```

- A named accessor beside it (`findCourseHomeTab(tabs)`) covers the two lookups
  that want the course-home link — `DetailedGrades.jsx:41` and
  `RelatedLinks.jsx:28`, today `find(tab => tab.slug === 'outline')` — so the
  API quirk lives in one module instead of two components.

`rootSlug` then exists nowhere: no parameter, no context, no prop, and the 53
readers in B2/B3 are one-line swaps with no extra argument:

```js
const { org, celebrations } = useCourseHomeMeta(courseId).data ?? {};
```

Unaffected: the `'progress'` / `'dates'` / `'discussion'` lookups
(`CertificateStatusAlert`, `CourseInProgress`, `CourseNonPassing`,
`HiddenAfterDue`, `widgets/discussions/widgetConfig.js`) and `key={slug}` in
`CourseTabLinksList`.

Plugins are unaffected: `CourseTabsNavigationSlot` passes no `pluginProps` and
`CourseTabLinksSlot` passes only `activeTabSlug` — the tabs array never reaches
plugin code. The README example renders its own
`<CourseTabLink slug="custom-link" activeTabSlug={…} />`, whose slug never
equals `'courseware'`, so it takes the plain-equality branch exactly as today.

Rejected alternatives:

- **Supply the root from a React context** provided by `TabPage` or the route
  elements, keeping both cache entries. Faithful — no behavior change at all —
  but it keeps a reader-relative value inside request-keyed cache entries and
  adds a provider whose value is a constant string. It relocates `rootSlug`
  rather than removing it.
- **Pre-resolve at display**: collapse the key but have `LoadedTabPage` rewrite
  the Course tab's slug to the current root before rendering, keeping the
  comparison a plain `===`. Rejected because `LoadedTabPage` then still has to
  compute "which root am I on", so the concept survives; it also makes that one
  component a funnel every future tab-list reader has to go through.
- **Put the metadata query result in a context**: makes a React Query result
  travel by prop/context, the coupling the query layer exists to remove.

**D3 — non-fetching cache reads (fact 3).** Recommendation: a small read-only
companion built on `useQuery({ queryKey, enabled: false })`, which subscribes
to the cache entry and returns whatever is there without triggering a fetch —
faithful to today's "empty until some other page loaded it" semantics, and
reactive, unlike `queryClient.getQueryData`. Needed by `useEnrollmentAlert`
and `useLogistrationAlert`; possibly by the `model`-prop alerts in layer A.

**D4 — `UnitNavigationEffortEstimate` is a deliberate pass-through; convert it
verbatim.** It bails unless `nextSequence.effortActivities ||
nextSequence.effortTime`, and those two fields are produced **only** by
`course-home/data/api.js` (the outline *tab*'s blocks, which land in the
`outline` model), never by either writer of the `sequences` model — so the
branch never executes. That is intentional and documented in the file's own
header comment: effort estimation was dropped when the LMS blocks API stopped
being called, and https://openedx.atlassian.net/browse/AA-930 tracks reviving
it. Keep the branch. In D2, `nextSequence` comes from the outline query, so it
stays exactly as unreachable as it is today. Preserve the `Object.keys(...)
.length === 0` guards, which depend on `useModel` returning `{}` (see D1).

**D5 — `CourseBreadcrumbs` calls `useModels` inside `.map()`.** Hooks in a loop;
it only survives because the array identity is stable per render. The
conversion has to restructure it (read the outline query once and index into
its `sections`/`sequences` maps).
