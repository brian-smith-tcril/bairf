# Plan: #2098 — Stop the courseware gate queries refetching from components under the gate

> Implemented with one change from the plan below: `useIsCourseLoaded` and
> `useSequenceIds` never fetch and take no option, instead of a per-call-site
> `{ enabled: false }`, and standalone suites mount the owner's hooks rather than
> seeding data. PR #2102's decision log has the reasoning; the two open questions
> resolved as a local `QueryOptions` and `refactor:`.

Next layer in stack #2080, on top of #2084 (PR #2099). Independent of the
model-store reader layers (#2085 onward), but it adds the `{ enabled }` option
to `useCourseHomeMeta` that B2 (#2085) and B3 (#2086) will need for their gated
readers.

## Context

#2098 was filed while reviewing #2084: one outline → courseware navigation
fetches `course_metadata` exactly three times. Its body blamed three observers
(`CoursewareContainer`, `useIsCourseLoaded`, `useCoursewareRedirects`) plus a
remount across the redirect, and proposed a `staleTime`. Tracing the requests
showed both parts of that diagnosis are wrong, and that the same defect affects
two more queries.

### Measurement

Protocol (tutor dev): hard-reload the course outline, wait for the network to go
idle, clear the log, click a sequence title, wait for idle, count requests.

| endpoint | hook | `staleTime` | requests |
|---|---|---|---|
| `/api/course_home/course_metadata/` | `useCourseHomeMeta` | default (0) | **3** |
| `/api/courseware/course/` | `useCoursewareMetadata` | default (0) | **3** |
| `/api/learning_sequences/v1/course_outline/` | `useCoursewareOutline` | default (0) | **3** |
| `/api/course_home/v1/navigation/` | `useCourseOutlineStructure` | `Infinity` | 1 |

The first three are exactly the queries `useIsCourseLoaded`
(`courseware/data/apiHooks.ts:41-47`) observes. The fourth is the control: it is
outside that hook.

### Where the `course_metadata` requests come from

A temporary log in `useCourseHomeMeta` captured the render-time stack of the
observer whose `queryFn` ran, and a mount/unmount log in `CoursewareContainer`
checked for a remount:

| # | caller (first app frames) | what it is |
|---|---|---|
| 1 | `CoursewareContainer` | the route owner, mounting on the entry the outline page left stale |
| — | `CoursewareContainer` unmount → mount, same pathname, 1ms apart | `StrictMode`'s development double-invoke (`src/index.jsx:46`); **no** unmount/mount when the redirect adds `:unitId` |
| 2 | `UnitNavigation` → `useSequenceNavigationMetadata` → `useSequenceIds` → `useIsCourseLoaded` | a descendant mounting after the gate opened |
| 3 | `UnitNavigationEffortEstimate` → `useSequenceIds` → `useIsCourseLoaded` | the same path, ~2.4s later |

So:

- **The three observers #2098 named are one request.** `CoursewareContainer`
  calls `useCourseHomeMeta` (`CoursewareContainer.tsx:33`) and
  `useCoursewareRedirects()` (`:37`), which calls `useIsCourseLoaded`
  (`redirects.ts:248`) — one render, so React Query dedupes them.
- **There is no remount across the redirect.**
- **The extra requests are descendants re-running the gate check.**
  `useIsCourseLoaded` is the owner's gate check, but it is a *fetching*
  observer of all three queries, and `useSequenceIds` calls it. Every component
  under `TabPage` that needs the sequence list therefore becomes a fetcher of
  all three endpoints; it mounts after the data has landed, finds it stale
  (default `staleTime` 0), and refetches (`shouldFetchOnMount` →
  `refetchOnMount`, `@tanstack/query-core` `queryObserver.js:320-327`).
- **The count is timing-dependent, not structural.** `CourseBreadcrumbs.jsx:20`
  and `sequence-navigation/hooks.js:13` also call `useIsCourseLoaded` directly,
  but did not show up in the trace — they mounted while a fetch was in flight
  and were deduped. A different mount order would give a different count.

Only the `course_metadata` callers were traced; that the other two endpoints'
extra requests come from the same mounts is inferred from the identical count
and identical observer set.

### This is the defect layer A fixed on the course-home tabs

`decisions-2083.md` entry 3: converting the outline and dates readers made them
observers that mount after `TabPage` opens its gate and refetch on mount, which
doubled each tab's own request. The fix was ownership, not freshness — the tab
wrapper owns the fetch and every reader under the gate passes
`{ enabled: false }`, subscribing to the cache entry without fetching. The same
entry rejected `staleTime` for those queries: their payloads change server-side
with no app action, and three writers rely on refetch-on-mount to resync.

The courseware route has the same shape: `CoursewareContainer` is the owner
(like the tab wrappers, it builds `courseStatus` for `TabPage`,
`CoursewareContainer.tsx:105-110`), and the descendants are readers.

### Why not `staleTime`

A `staleTime` would hide the descendant fetches without deciding who owns them,
and it changes freshness for every observer — including the owner's legitimate
on-navigation refetch. That refetch does real work: `course_metadata`'s view
calls `UserCelebration.perform_streak_updates`
(openedx-platform `openedx/core/djangoapps/courseware_api/utils.py:26`,
`common/djangoapps/student/models/user.py:1943-1983`), which records the
learner's daily streak on the first GET of each day. The duplicates seconds
later record nothing (`already_updated_streak_today`), so removing them loses
nothing, but the owner's refetch should keep today's timing.

## The change

1. **`{ enabled }` on the three gate queries**, following
   `useOutlineTabData`'s shape (`course-home/data/apiHooks.ts:113-123`):
   `useCourseHomeMeta(courseId, { enabled = true }: QueryOptions = {})` and the
   same for `useCoursewareMetadata` and `useCoursewareOutline`
   (`courseware/data/apiHooks.ts:20-38`), each with
   `enabled: enabled && !!courseId`.
2. **`useIsCourseLoaded(courseId, { enabled = true } = {})`** passes the option
   to all three.
3. **`useSequenceIds(courseId, { enabled = true } = {})`** passes it to
   `useIsCourseLoaded`.
4. **Descendants pass `{ enabled: false }`**; the owner keeps the default:

   | call site | role | change |
   |---|---|---|
   | `CoursewareContainer.tsx:32-33` (direct queries), `:46` (`useSequenceIds`) | owner | none |
   | `redirects.ts:248-250` (called from `CoursewareContainer`) | owner | none |
   | `CourseBreadcrumbs.jsx:20` (`useIsCourseLoaded`) | descendant | `{ enabled: false }` |
   | `sequence-navigation/hooks.js:11` (`useSequenceIds`), `:13` (`useIsCourseLoaded`) | descendant | `{ enabled: false }` |
   | `UnitNavigationEffortEstimate.jsx:32` (`useSequenceIds`) | descendant | `{ enabled: false }` |

   `CourseExit.jsx:73-75` owns its own route (`/course/:courseId/course-end`)
   and is unchanged.

A disabled observer returns the query's current state and re-renders when the
owner's fetch updates it, so `useIsCourseLoaded`'s result is unchanged at every
call site. That matters for the outline query in particular: `TabPage`'s gate
covers `course_metadata` and `/api/courseware/course/` only, so descendants can
mount while `useCoursewareOutline` is still pending — they read `false` and
flip to `true` when `redirects.ts` finishes fetching it, exactly as today.
Invalidation is unaffected too: `useIFrameBehavior.ts:169-171` invalidates all
three keys, and the owner's observers are enabled and mounted, so they refetch.

## Tests

- **`courseware/data/apiHooks.test.tsx`**: a disabled `useIsCourseLoaded` makes
  no request and stays `false` on an empty cache; mounted after an enabled one
  has resolved, it reads `true` and adds no request
  (`axiosMock.history.get.length` unchanged). A matching pass-through case for
  `useSequenceIds`.
- **Suites that render a descendant standalone** relied on it fetching the gate
  queries itself and will need the owner's data seeded instead
  (`seedQueryData`, `setupTest.js:283-286`). Candidates, to confirm by running:
  `CourseBreadcrumbs.test.jsx`, `sequence-navigation/SequenceNavigation.test.jsx`,
  `UnitNavigation.test.jsx`, `Sequence.test.jsx`, `SequenceContent.test.jsx`,
  `Unit/index.test.jsx`, `Course.test.jsx`. `CoursewareContainer.test.jsx`
  renders the owner and should be unaffected.

## Behaviour changes

- On the outline → courseware crossing, each of the three gate endpoints is
  requested once instead of three times, re-measured with the protocol above.
  The one request left per endpoint is the owner's: a cache miss for the two
  courseware queries, and the on-navigation refetch for `course_metadata`.
- Nothing else: every descendant reads the same query state it did before.

## Not in scope

- **`staleTime` on any of these queries** — see above.
- **The progress tab looks like it has the same defect, unmeasured.**
  `useProgressData()` (`progress-tab/hooks.jsx:5-8`) observes
  `useProgressTabData` without `enabled: false`, and 22 files under the
  progress tab's gate use it — the double request layer A fixed for outline and
  dates. `useExamsData` is plugin-facing and reads through it, so the fix has a
  plugin-contract question of its own. Proposed as a separate issue once a count
  of `/api/course_home/progress/` on one progress-tab load confirms it. The
  other course-home tabs have no such readers: outline and dates were fixed in
  #2083, and `useLiveTabData` has one caller.
- **`useSequenceIds`'s model-store read** (`useModel('coursewareMeta')`,
  `useModels('sections')`) converts in D3 (#2089), which must keep the
  `{ enabled }` pass-through this layer adds.

## Knock-on for #2085 / #2086

Their bodies say each site becomes `useCourseHomeMeta(courseId).data ?? {}`.
Per `decisions-2083.md` entry 3, readers under a gate should be
`useCourseHomeMeta(courseId, { enabled: false }).data ?? {}`, and this layer
provides that option. Both bodies need updating before those layers start.
