Part of #1905. Depends on #2197.

**Goal:** a learner in courseware on a frontend-base site opens the auxiliary sidebar (the panel beside the content that holds the registered widgets; `RightSidebarSlot` on `master`) and finds the in-context discussions panel on units that have discussions enabled, as on `master`. The discussions widget is the one registered widget, hard-coded; the framework's handling of several registered widgets (one trigger each, one panel open) ports intact so later widgets slot in. The auxiliary sidebar stubs from #2196 are replaced. Two things wait for the Slot API in #2185 and are looked at again when tabs become widgets in #2186: how a site registers widgets (the `SIDEBAR_WIDGETS` list on `master`; under frontend-base plausibly the slot itself, with a Tutor plugin such as tutor-forum inserting the discussions widget), and the upgrade widget, whose panel is a plugin slot with no default content (since [14c662dc](https://github.com/openedx/frontend-app-learning/commit/14c662dc530c1982d016a2ffd2ffe2af51603303)) and whose default registration #1902 already lists for removal.

## What moves

Files port from the legacy `src/` tree to the same relative path under `frontend-base/src/`, with their tests, and get a line each in `frontend-base/manifest.tsv`.

- The auxiliary sidebar and its trigger: the generic sidebar and trigger shells the framework from #2197 already holds, now rendered through the auxiliary sidebar slot and its trigger slot, which become placeholder slots with those shells as their default content. These two modules move under new names, `AuxiliarySidebarSlot` and `AuxiliarySidebarTriggerSlot` (from `RightSidebarSlot` and `RightSidebarTriggerSlot`), the one rename in the port: "right" describes the left-to-right rendering only (under a right-to-left locale the navigation sidebar renders on the right; both sidebars sit in the same flex row), so the ported tree drops it. The manifest records the mapping; the legacy slot ids are untouched until the Slot API port in #2185 names the frontend-base ids.
- The course component passes the discussions widget config straight to the sidebar provider as its one widget, where `master` passes the list `getEnabledWidgets()` builds. The registry that builds that list ([`defaultWidgets.js`](https://github.com/openedx/frontend-app-learning/blob/master/src/courseware/course/sidebar/defaultWidgets.js): the built-in entries merged with the `SIDEBAR_WIDGETS` config) does not port here. It is a plugin mechanism, so it ports to frontend-base patterns in #2185.
- The discussions widget ([`src/widgets/discussions/`](https://github.com/openedx/frontend-app-learning/tree/master/src/widgets/discussions)): available on a unit with in-context discussions enabled; its sidebar embeds the discussions app for the unit's topic. Its URL comes from the discussions role, resolved through frontend-base's route resolver (an external route a site supplies today, the installed discussions app later), in place of `DISCUSSIONS_MFE_BASE_URL`.

## Testing

The tests of the files that move here, the discussions widget's and the auxiliary sidebar slots', port with them, as do the framework's mock-widget suites (`SidebarTriggers.test.jsx`, `SidebarContext.test.jsx`) that pass two or more widgets to the provider, and reach the page through the exported route array at a unit URL, with the unit, course metadata and discussions-topic queries mocked per the conventions #2189 set.

The role resolution is tested by hand both ways, since the resolver returns an installed app's route path or an external route's URL depending on what the site config holds: once with the real discussions app configured as an external route for the discussions role, and once with a stub app in the dev site config that provides the role on a route, checking the iframe URL the panel builds in each case.

## Acceptance

- [ ] The auxiliary sidebar opens and closes from its trigger; on a unit with in-context discussions enabled the discussions panel loads the discussions app for that unit
- [ ] Manual test of the discussions role resolved both ways: the real discussions app as an external route, and a stub installed app providing the role; the panel's iframe URL recorded for each
- [ ] With a second widget passed to the provider in a test, each available widget has its own trigger, clicking one opens its panel and closes the other, and priority ordering holds (the framework's mock-widget suites)
- [ ] The auxiliary sidebar slot and its trigger slot are placeholder slots rendering their default content
- [ ] Types, lint and tests of the new package pass; the legacy workflow stays green; `npm run dev` from the package serves courseware with the discussions widget
- [ ] Manifest lines added for every file moved; the discussions widget directory's coverage compared against the `master` baseline
