## Summary

A how-to for adding a new version of a slot, `docs/how_tos/add-a-slot-version.md`, with tests that run its examples and a guard that fails when the markdown and the tested code drift apart. **Docs and tests only; the runtime is unchanged.**

[ADR 0009](https://github.com/openedx/frontend-base/blob/main/docs/decisions/0009-slot-naming-and-lifecycle.rst) sets the rules for a slot's contract and lifecycle but not the steps. The how-to walks the new-version path on four invented examples, from a prop rename in full to a slot whose default widget takes widget options, each ending with the old version's removal, and then two renames of a slot: one with its contract unchanged, where the old id is kept as an alias, and one where its props change, where ADR 0009 calls for a new identifier and a new slot wraps the old one. Every version of every example is a fixture the tests render, so the code in the how-to is code that runs. The examples follow the answer on #339 that an app exports the types its slot props are built from ([comment](https://github.com/openedx/frontend-base/issues/339#issuecomment-6581552081)).

Resolves #340.

## What changed

- `docs/how_tos/add-a-slot-version.md`: an overview and six examples. Renaming a prop, in full: `v2` wrapping `v1`, `@deprecated` notes, a README per version, the `feat:` commit, the later `feat!:` removal, and a closing section on moving an operator's widget to `v2`. Changing a prop's type, under the same step headings, showing only what differs. A prop that becomes a list, where the old prop has no direct source in the new one and the list is added to `v1` as well. A slot whose default widget takes options, where the item type gains a required field and the widget serves `v1` and `v2` operators' options at once until `v1` is removed, with the whole slot file shown after the deprecation step and after the removal. Renaming a slot, where nothing in the contract changes: the old id is kept in `idAliases` until a later `feat!:` removes it, and the slot keeps its one README. Renaming a slot when its props change: the new slot wraps the old one under the new-version steps, and the old README is renamed `README.songList.v1.md`, named for the old slot minus what its id shares with the new one, the rule that also names `README.v1.md`. The how-to shows that rule by example only; where it gets written down is #346.
- `runtime/slots/testMocks/`: twenty-six fixtures, each example slot in the three states the how-to shows (`v1` only, `v2` wrapping `v1`, `v2` after removal), plus the two states the rename says not to produce, the operator's widget before and after its move, the list example's state before the list is added to `v1`, and the options example's operator operation and the page that renders the slot before and after the change. The two rename examples hold the slot before, with the alias or the wrapping, and after the removal, plus the id renamed with no alias.
- `runtime/slots/howToExamples.test.tsx`: renders each state the ways an operator can use it (component widgets against either version, replacing the default content, replacing the layout and reading the props through `useSlotContext()`, widgets on both versions at once, a `v1` operation on the `v2`-only state) and checks the reasons the how-to gives: a widget reading a renamed-in-place prop gets `undefined` and the typecheck rejects it, a widget on a bumped-in-place id stops rendering, a `v1` widget gets the first tag or an empty string, a `v1` option reaches the default widget only while `v1` exists, a `v2` option's function never sees a tree a `v1` option added, and `useWidgetOptions()` inside the wrapped `v1` reads `v1`'s options while `useWidgetOptionsForId` on the `v2` id reads `v2`'s.
- `runtime/slots/howToExamples.drift.test.ts`: reads the how-to and asserts that every `ts` or `tsx` block under an example heading, and both sides of every `diff` block, appears in one of that example's fixtures, with every comment line checked verbatim and every code fence tagged with one the guard reads.

## Open question

**How do people find out a slot version is deprecated?** A `feat!:` subject or a `BREAKING CHANGE:` footer is easy to search for, but the `feat:` commit that adds `v2` and deprecates `v1` is not, and the deprecation sits there for at least a named release before the breaking removal. Should deprecations be tracked somewhere findable: a commit convention, a list in the repo, the DEPR ticket alone, or something else? The how-to's step 5 says only what the commit body should say.
