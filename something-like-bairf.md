# Doing something like bairf

For colleagues who use Claude for non-coding work. `what-bairf-is.md` is the reference, checked against the repo; this is the version for the room. Draft; shape first, words second.

## Opening

Stuff Brian uses to make Claude work the way he likes (and a home for "for Claude by Claude" text).

From the talk: "Claude likes to write a lot of text. I've started affectionately calling that 'Claude vomit'. Claude needs that text, and I need a home for it. Hence bairf: it's barf + AI."

## Shape

Each of bairf's five parts, as: what Brian does, what it gets him, and what the equivalent looks like without a terminal or a code repo. The order follows what the cold reader (`cold-read-1.md`) said landed, strongest first.

### 1. A "How I work" document

- Brian: "How Brian works", read by Claude at the start of every session on every project. Pace, how to decide, what not to do, learned the hard way.
- Gets him: no re-explaining; the same Claude on day one of a project as on day ninety.
- For the room: a standing document of your own. "Never say 'leverage'. Posts under 150 words. Lead with a person." Where it goes so Claude reads it every time: to confirm for the browser product.

### 2. Let memory pile up, then curate

- Brian: memory stays on. Every so often he reviews what Claude has remembered, with Claude, and promotes what deserves to be permanent into the "How I work" document. The rest is dropped.
- Gets him: cheap collection, deliberate promotion, at his pace.
- For the room: ask Claude what it remembers about you; keep, rewrite into your document, or drop. The alternative some people take, memory off and everything written up front, and why Brian doesn't.

### 3. A home for the text Claude writes for Claude

- Brian: every piece of work gets a folder for the plans, decisions and context Claude writes so a later Claude can get situated. Separate from the work itself. Searchable after the work is done.
- Gets him: a Claude that picks up where the last one left off, and a record of why things were decided.
- For the room: a folder per project for Claude's notes, that Claude knows to read first and write to. Where that folder can live for a browser user: to confirm.

### 4. "Please don't" versus "cannot"

- Brian: most rules are followed because Claude read them. Two are enforced by code and block the action outright, with a reason.
- Gets him: the rules that matter too much to leave to reading don't depend on reading.
- For the room: which of your rules is a "cannot" ("never post a donor's name without written consent"). Whether a browser user can have one, and what the nearest thing is: to confirm.

### 5. Procedures with stops

- Brian: a written procedure Claude follows the same way every time, with stops where nothing advances until he says so. Draft, create, review, settle.
- Gets him: the stops are built in, not remembered.
- For the room: your newsletter as a procedure. Draft, you approve, it formats, you approve, it schedules. Skills exist in the browser product; how a non-coder writes one: to confirm.

### 6. The same on every computer

- Brian: one checklist, run by Claude, that makes any machine he sits down at behave like the others.
- Gets him: nothing about Claude's behaviour depends on which machine.
- For the room: whether this is even a problem for browser users (the reader said Claude "feels slightly different" on their two machines), and what carries over automatically.
