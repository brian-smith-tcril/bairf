# Plan: #2084 — Take tab identity out of the course-home metadata query

Layer B1 of the model-store dissolution (#1977), stacked on layer A (#2093).
No reader converts here: this layer removes `rootSlug` so that B2 (#2085) and B3
(#2086) can convert 53 `courseHomeMeta` readers without any of them naming a
cache variant.

## Context

`courseHomeQueryKeys.metadata(courseId, rootSlug)` caches one endpoint twice —
under `'outline'` for the five course-home tabs and `CourseAccessErrorPage`, and
under `'courseware'` for `CoursewareContainer`, `CourseExit`, `redirects` and
`useIsCourseLoaded`. `rootSlug` never reaches the request. It changes exactly one
field, in `normalizeCourseHomeCourseMetadata` (`course-home/data/api.js:20`):

```js
// The API uses "courseware" as a slug for both courseware and the outline tab.
slug: tab.tabId === 'courseware' ? rootSlug : tab.tabId,
```

### Why that field exists

The LMS returns **one** tab entry, `tabId: 'courseware'`, for a destination
learning splits into two pages. Both pages render the same nav, and the nav
decides highlighting by string equality (`CourseTabLink.tsx:16`,
`active: slug === activeTabSlug`). Neither fixed value works — `'outline'` fails
to highlight on courseware, `'courseware'` fails on the course-home page — so
something has to know that this one tab is "the current page" in two different
situations. That knowledge can live in the data or in the comparison.

Nobody designed the split; a page name and a tab id collided and the nav broke:

| when | PR | what happened |
|---|---|---|
| 2020-06-15 | [#80](https://github.com/openedx/frontend-app-learning/pull/80) | The outline becomes its own page, routed as `tab="outline"` — a *page* name, not a tab id. |
| 2020-06-25 | [#93](https://github.com/openedx/frontend-app-learning/pull/93) | `course-home/data/api.js` is created emitting plain `slug: tab.tabId`. From here the Course tab is **not highlighted** on the outline page. |
| 2020-12-16 | [#281](https://github.com/openedx/frontend-app-learning/pull/281) | A 31-file feature PR building the anonymous/un-enrolled landing page notices the dead highlight in passing and fixes it in two lines. Its review thread states the bug outright — ["The "Course" tab wasn't active while in course home because our course metadata calls it "courseware""](https://github.com/openedx/frontend-app-learning/pull/281#discussion_r537750859). |
| 2022-03-10 | [#861](https://github.com/openedx/frontend-app-learning/pull/861) | Unifying the tab source means one normalizer serves both pages, so the hardcoded `'outline'` becomes the `rootSlug` parameter, passed `'outline'` by `fetchTab` and `'courseware'` by `fetchCourse`. |
| 2026-08-31 | [#2023](https://github.com/openedx/frontend-app-learning/pull/2023) | Converting the fetch to React Query means the queryFn's output varies by `rootSlug`, so it must go in the key — two cache entries for one response. |

#281's two-line fix was the cheap one, and incidental to that PR's actual subject.
`fetchTab` was a *per-page* thunk, so fetch time and render time were the same
moment and "who is asking" was ambient and free, while fixing the comparison meant
touching the nav component. Every consumer stayed a plain equality check.

It stops fitting because React Query keys on **what was requested** while this
field encodes **who was asking**.

### Why the whole mapping goes, not just the parameter

Removing `rootSlug` alone leaves the normalizer with this:

```js
tabs: data.tabs.map(tab => ({ slug: tab.tabId, title: tab.title, url: tab.url })),
```

`camelCaseObject` has already produced `tabId`, and per the pact contract the
endpoint sends only `tab_id`, `title` and `url` — so nothing is filtered either.
The map's entire remaining effect would be to re-spell one field, which is the
only reason tab identity is a concern of `src/course-home/data/` at all.

The request is `GET /api/course_home/course_metadata/{courseId}?browser_timezone=…`.
No tab is an input, and the response is identical for every page. Tab identity is
*content* in the response body, like `title` or `org` — never a parameter — so the
data layer should have no opinion about it. Leaving the map behind would also leave
the layer's central claim half-stated: the id is the id, and the page asking is not
part of it.

## The change

1. **`course-home/data/api.js`** — `getCourseHomeCourseMetadata(courseId)` and
   `normalizeCourseHomeCourseMetadata(metadata)` drop the parameter, and the
   `tabs` mapping is deleted outright. The normalizer keeps only `isMasquerading`;
   `...data` carries tabs through as the LMS sent them (`tabId`, `title`, `url`).
2. **`course-home/data/queryKeys.ts`** — `metadata: (courseId: string)`.
3. **`course-home/data/apiHooks.ts`** — `useCourseHomeMeta(courseId)`.
4. **Ten call sites** drop their argument: `DatesTab`, `DiscussionTab`,
   `LiveTab`, `OutlineTab`, `ProgressTab`, `CourseAccessErrorPage`,
   `CoursewareContainer`, `CourseExit`, `redirects.ts`, and `useIsCourseLoaded`
   in `courseware/data/apiHooks.ts`.
5. **New `src/course-tabs/utils.ts`** becomes the only module that names an LMS
   tab id. `getTab` stays module-private so no call site passes an id:

   ```ts
   export interface TabMetadata {
     tabId: string;
     title: string;
     url: string;
   }

   const getTab = (tabs: TabMetadata[] | undefined, tabId: string) => tabs?.find(tab => tab.tabId === tabId);

   export const getDatesTabUrl = (tabs?: TabMetadata[]) => getTab(tabs, 'dates')?.url;
   export const getProgressTabUrl = (tabs?: TabMetadata[]) => getTab(tabs, 'progress')?.url;
   export const hasDiscussionTab = (tabs?: TabMetadata[]) => !!getTab(tabs, 'discussion');

   export const getCourseOutlineUrl = (tabs?: TabMetadata[]) => getTab(tabs, 'courseware')?.url;

   export const isActiveTab = (slug: string, activeTabSlug?: string) => {
     if (activeTabSlug === slug) {
       return true;
     }

     // Course content renders at /course/:courseId/:sequenceId/:unitId and carries the slug `courseware`;
     // the course outline renders at /course/:courseId/home and carries `outline`. Users see one "Course" tab.
     if (activeTabSlug === 'outline' && slug === 'courseware') {
       return true;
     }

     return false;
   };

   export const getActiveTabTitle = (tabs?: TabMetadata[], activeTabSlug?: string) => (
     tabs?.find(tab => isActiveTab(tab.tabId, activeTabSlug))?.title
   );
   ```

   A helper per destination rather than a generic `getTab(tabs, id)`:
   plain-versus-quirky is a fact about the implementation, not about the caller,
   and the tab ids are the LMS's vocabulary appearing as bare literals in six
   components. Each returns what callers actually use — a URL, or a boolean —
   because every tab-object caller immediately wrote `tab && tab.url` and
   `widgetConfig.js` only tested truthiness. Even `getActiveTabTitle` returns a
   string, so nothing outside `utils.ts` handles a tab object at all.

   Only four destinations need an accessor, and that is not a coincidence. `tabs`
   is a server-owned nav menu, not a list of this app's pages: `openedx.course_tab`
   is an entry-point namespace and openedx-platform ships nineteen types, most of
   them LMS-hosted (`wiki`, `instructor`, `teams`, `edxnotes`, the textbook tabs)
   or carrying author-chosen URLs (`external_link`, `static_tab`, the `lti_*`
   tabs). The MFE renders `title` → `url` for whatever arrives and inspects ids
   only for the destinations it deep-links to from elsewhere.

   The Course tab gets a URL accessor instead, because three names disagree about
   it and no caller should have to hold that. The LMS's id is `courseware` and its
   title is "Course"; this MFE splits it across the outline route (`/home`) and the
   content routes; and the tab's own `url` points at the outline, which the UI calls
   **Course outline** (the courseware sidebar, the progress tab's related links, its
   detailed-grades alert). Neither `courseware` nor `outline` appears in any URL —
   they are in-app labels carried by `activeTabSlug`. So the constant keeps the LMS's
   name, the comment states the disagreement once, and the export is
   `getCourseOutlineUrl(tabs)` — named for where it goes, which is all either caller
   wanted. `get` rather than `find` follows the repo's own convention
   (`getResponseStatus`, `getErrorDetail`, `getSidebarId`), including for helpers
   that may return `undefined`.

   `isActiveTab` keeps a `slug` parameter because `CourseTabLink` passes it a value
   that may be a plugin's custom tab name rather than an LMS tab id. The optional
   `tabs` parameter matters too: `widgetConfig.js` passes `course?.tabs`, which is
   `undefined` before the model loads.

6. **Seven consumers** move to the helpers — one line each:
   `CourseNonPassing.jsx:28`, `HiddenAfterDue.jsx:15` and
   `CertificateStatusAlert.jsx:118` (`getProgressTabUrl`), `CourseInProgress.jsx:28`
   and `RelatedLinks.jsx:31` (`getDatesTabUrl`), `widgetConfig.js:10`
   (`hasDiscussionTab`), and `LoadedTabPage.tsx:47` (`getActiveTabTitle`).
   `DetailedGrades.jsx:42` and `RelatedLinks.jsx:29` take `getCourseOutlineUrl`,
   which collapses their two-line `tab && tab.url` dance into one.

   `CertificateStatusAlert.jsx:203-207` also documents the tab shape in PropTypes
   as `tab_id`, which is wrong both before and after — the camelCased field is
   `tabId`.

7. **One tab type.** `CourseTabsNavigation.tsx:11-15`,
   `CourseTabLinksList.tsx:5-9` and `CourseTabLinksSlot/index.tsx:5-9` each
   re-declare `{ title, slug, url }`; all three import `TabMetadata` instead. This is
   mandatory rather than tidying — left alone they declare a field that no longer
   exists. `TabMetadata`'s `title`/`url` are required, since `CourseTabLink`
   requires `url: string` and the optional form would not compile once the type is
   actually used; nothing depended on the optional form.

   `CourseTabLinksList` is the one seam: it destructures `tabId` and passes
   `slug={tabId}` to `CourseTabLink`, whose prop is a documented plugin contract
   with a wider domain than LMS tab ids.

8. **Faithful fixtures.** `shared/data/__factories__/tab.factory.js` emits `slug`
   *and* a derived `tab_id`, plus `priority`/`type` that this endpoint never sends;
   the mapping is what hides them today. It emits `tab_id`, `title` and `url` only,
   and the six `Factory.build('tab', …)` calls in
   `courseHomeMetadata.factory.js:38-123` pass `tab_id`.

   This is the change's safety net, not cleanup: `useModel('courseHomeMeta')`
   returns `any` (`generic/model-store/hooks.js` is JavaScript) and
   `useCourseHomeMeta` is typed as only `{ courseAccess }`, so **`tsc` cannot catch
   a missed reader**. Left alone, a consumer that still reads `slug` would keep
   passing tests and break only in production. Rosie silently accepts a stray
   `slug` override *and* falls back to its default `tab_id`, so all six convert in
   one edit with the built array's ids asserted once.

## Tests

- **`course-home/data/apiHooks.test.tsx`** has three tests pinning what this layer
  removes, added by #2023 when the convention was introduced: *labels the shared
  tab "courseware"*, *labels it "outline"*, and *keys the query by rootSlug so the
  two contexts do not share a cache entry*. The first two are **deleted** — they
  assert a data-layer opinion about tab ids, which is exactly what this layer
  removes, and only compile through a `data as { tabs: … }` cast. The third
  **inverts**: both contexts now share one cache entry, which is the improvement
  this layer makes, so it is worth pinning in that direction.
- **New unit tests for the helpers** (`course-tabs/utils.test.ts`): the courseware
  tab is active under both `'outline'` and `'courseware'`; an ordinary tab matches
  only its own id; each named helper finds its entry; all of them tolerate absent
  tabs.
- **New unit test for `discussionsPrefetch`** (`widgets/discussions/`). Nothing
  exercises it today — every test calls `prefetchDiscussionTopics` directly, and
  the only test that renders the provider supplies `{ tabs: [] }`. With no type
  coverage on that path either, a mistake there is invisible: CI green,
  discussion-topic prefetching silently dead.
- **`course-tabs/CourseTabsNavigation.test.jsx:65`** passes
  `activeTabSlug: tabs[0].slug`, which becomes `tabs[0].tabId`. It still derives
  the page from a tab, but the fixture's ids (`test1`, `test2`) are neither route
  names nor LMS tab ids, so nothing real is conflated; a literal `'test1'` would
  behave identically and can land whenever the test is next touched.
- **`pact-tests/lmsPact.test.jsx:126-131`** expects the normalized `slug: 'outline'`
  and becomes `tabId: 'courseware'`. The API-side `tab_id: 'courseware'` at line 85
  is the contract with the LMS and does not move.

## Behaviour changes

- **One cache entry per course instead of two**, verified by the inverted test in
  `apiHooks.test.tsx`: both contexts return the same object and one controlled
  render makes one request.

  **This does not reduce requests in the browser, and the layer should not claim
  it does.** Measured in tutor dev on the outline → courseware crossing (clear the
  network log once the outline settles, click a sequence title, wait for idle,
  count `course_metadata`): **exactly 3, five runs each, on this layer and on
  #2093** — no variance either side. An earlier draft claimed "two requests become
  one"; that was reasoning from the key alone, and it is wrong.

  The reason is `staleTime`. `useCourseHomeMeta` sets none, so the entry is stale
  the moment it lands and `refetchOnMount` fires for each observer that mounts on
  it — the courseware side mounts three (`CoursewareContainer`, `useIsCourseLoaded`,
  `redirects`) across a route that remounts as the redirect resolves. Collapsing two
  keys into one turns a cache *miss* into a stale *hit*; it does not remove a fetch.
  Whether that changes what blocks `useIsCourseLoaded` was not measured.

  The tab bar is not a client-side path at all: `CourseTabLink` renders a plain
  `<a href>`, so every tab click is a full page load that discards the cache. The
  only crossings that reuse it are a sequence title on the outline (`SequenceTitle`
  renders a router `Link` into courseware) and the home breadcrumb in courseware
  (`CourseBreadcrumbs` links to `/home`).

  Reducing the count is a `staleTime` question rather than a key question, and this
  layer makes it tractable by leaving one key to tune instead of two.
- **Tabs carry the ids the LMS sent**, wherever the payload is read, including the
  `courseHomeMeta` model the bridge still writes. The bridge itself is a
  passthrough (`model: { id: courseId, ...data }`) and needs no change.
- **No re-render change.** `camelCaseObject` already deep-clones per fetch and
  `useModel` compares `tabs` by reference, so that reference was new on every fetch
  with or without the mapping. Deleting it removes one array allocation.

Plugins are unaffected: `CourseTabsNavigationSlot` passes no `pluginProps`, and
`CourseTabLinksSlot` passes only `activeTabSlug` — the tabs array never reaches
plugin code. The slot README's example renders its own
`<CourseTabLink slug="custom-link" activeTabSlug={…} />`, which is untouched.

## Not in scope

- **`CourseTabLink`'s `slug` prop and the slot README** — that identity is a
  route comparison whose domain includes plugin-supplied names, not an LMS tab id.
- **`generic/tabs/Tabs.jsx`** drops `className`/`style` when cloning
  `CourseTabLink`, so tab overflow does not work. Pre-existing since the slot was
  added; its own issue.
- **The stale `tabs` block in the generated `src/pacts/frontend-app-learning-lms.json`**
  under the courseware interaction, unasserted since #861.
