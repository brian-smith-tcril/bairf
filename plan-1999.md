# Plan: #1999 — source the access-expiration masquerade banner from the tab queries, not `useModel(tab)`

Layer E of the model-store dissolution (`plan-1977.md`), the last reader
layer. Goes on the running stack #2141 above #2150 (`bsmith/course-home-api-types`,
#2130), which already rewrites two of the files this layer touches
(`course-home/data/apiHooks.ts`, `course-home/data/api.ts`). After it, no
`useModel` reader and no bridge producer is left in `src`, so F (#1977) is
pure deletion.

## How it works today

`LoadedTabPage` renders `InstructorToolbar` when `originalUserIsStaff`, passing
`tab={activeTabSlug}`. The toolbar calls two sibling hooks with the same
`(courseId, tab)` signature and spreads both into one
`<AlertList topic="instructor-toolbar-alerts">`:

```js
const accessExpirationMasqueradeBanner = useAccessExpirationMasqueradeBanner(courseId, tab);
const courseStartDateMasqueradeBanner = useCourseStartMasqueradeBanner(courseId, tab);
```

`useAccessExpirationMasqueradeBanner` (`alerts/access-expiration-alert/hooks.js`)
reads `userTimezone` from the metadata query already (#2109) and
`accessExpiration` from the model store, keyed by whatever tab is asking:

```js
const userTimezone = useCourseHomeMeta(courseId, { enabled: false }).data?.userTimezone;
const { accessExpiration } = useModel(tab, courseId);
const isVisible = accessExpiration && accessExpiration.masqueradingExpiredCourse;
```

`useModel` returns `{}` when `state.models[tab]` or `[tab][courseId]` is
missing, so `accessExpiration` is `undefined` and the banner is hidden on any
tab whose model nobody writes.

**Who writes a tab model.** Three bridge `meta` entries in
`course-home/data/apiHooks.ts`, the last `{ modelType, courseId }` producers
in `src` (the courseware mirrors left in #2134/#2140/#2144):

| Hook | `meta` |
|---|---|
| `useDatesTabData` | `{ modelType: 'dates', courseId }` + `Transitional (#1999)` comment |
| `useOutlineTabData` | `{ modelType: 'outline', courseId }` + `Transitional (#1999)` comment |
| `useProgressTabData` | `{ modelType: 'progress', courseId, logStatusAs: { 404: 'silent' } }` |

**Who renders a tab page, and what the banner sees there.** Seven
`TabPage` / `TabWithTimer` producers:

| Page | `activeTabSlug` | `courseStatus` tab data | model under that slug | banner today |
|---|---|---|---|---|
| `OutlineTab.jsx` | `outline` | `useOutlineTabData` | written | can show |
| `ProgressTab.jsx` | `progress` | `useProgressTabData(courseId, targetUserId)` | written | can show |
| `DatesTab.jsx` | `dates` | `useDatesTabData` | written, **has no `accessExpiration`** (below) | never |
| `DiscussionTab.jsx` | `discussion` | none | none | never |
| `LiveTab.jsx` | `lti_live` | `useLiveTabData` | none | never |
| `CoursewareContainer.tsx` | `courseware` | `useCoursewareMetadata` | none | never |
| `CourseExit.jsx` | `courseware` | `[coursewareMetadata, outline]` | none | never |

**Which payloads carry `access_expiration`** (openedx-platform `master`):

| Endpoint | `access_expiration` |
|---|---|
| `course_home_api/outline` | `OutlineTabSerializer.access_expiration = DictField()`; `views.py` fills it from `get_access_expiration_data` |
| `course_home_api/progress` | `ProgressTabSerializer.access_expiration = DictField()`; same source |
| `course_home_api/dates` | **absent** — `DatesTabSerializer` is `course_date_blocks`, `has_ended`, `learner_is_full_access`, `user_timezone` plus `DatesBannerSerializer`'s `dates_banner_info` |
| `courseware_api` (courseware metadata) | `CoursewareMeta.access_expiration` property → **the same `get_access_expiration_data`** |
| `course_home_api/course_metadata` | absent (`verified_mode.access_expiration_date` is the upgrade deadline, a different thing) |

`get_access_expiration_data` (`openedx/features/course_duration_limits/access.py`)
returns `{ expiration_date, masquerading_expired_course, upgrade_deadline, upgrade_url }`
or `None`, with
`masquerading_expired_course = is_masquerading_as_specific_student(user, course.id) and expiration_date < now`.

So today the banner can appear on exactly two pages, outline and progress.
That has been so since PR #606 (2021-08, AA-877) introduced it: that version
read `useModel(tab, courseId)` the same way, `CoursewareContainer` passed
`activeTabSlug="courseware"` then too, and no `'courseware'` model type has
ever existed (the courseware page's model is `coursewareMeta`).

**The progress key.** `useProgressTabData` keys on `(courseId, targetUserId)`;
`ProgressTab.jsx` takes both from `useParams()`. The banner hook has only
`(courseId, tab)`.

**Types.** `CourseHomeOutline.accessExpiration: CourseHomeAccessExpiration | null`
is declared (`courseHomeOutline.ts`, four fields + index signature).
`CourseHomeProgress` (`api.ts`, #2130) does not name `accessExpiration`; it
falls under the `[key: string]: unknown` index signature.

**Tests.** The positive path is already under the owners, through the real
query path (axios mocks → query → bridge → model):
`OutlineTab.test.jsx` › *Access Expiration Alert* › *renders page banner on
masquerade* / *does not render banner when not masquerading*, and
`ProgressTab.test.jsx` › *Access expiration masquerade banner* (same two).
`InstructorToolbar.test.jsx` renders the toolbar bare on `initializeTestStore`
and asserts only *does not display alerts by default*. `LoadedTabPage.test.jsx`
mocks the toolbar. There is no hook-level test. Both owners' *request count*
suites render a non-staff user, so the toolbar (and anything it reads) is
not mounted there.

## Findings beyond the issue body

1. **The `dates` bridge entry feeds nothing.** The dates endpoint has no
   `access_expiration`, so `useModel('dates', courseId).accessExpiration` has
   always been `undefined`. The issue and the `Transitional (#1999)` comment
   on `useDatesTabData` describe a reader that cannot fire. Dropping that
   `meta` is a no-op for the banner.

2. **A uniform read would turn the banner on where it has never shown.** The
   courseware metadata carries the same `masquerading_expired_course` flag,
   so "read `accessExpiration` from whatever `courseStatus` tab-data query the
   page passes" would start rendering the banner on the courseware page and
   `CourseExit` (and would have to pick between `CourseExit`'s two queries).
   That may be a reasonable product change, but it is not this conversion;
   the faithful target is outline and progress only. Worth a line in the
   decisions doc; a product follow-up is the user's call, not this layer's.

3. **The hook's file is two-thirds dead.** `hooks.js`'s default export
   `useAccessExpirationAlert` and the `AccessExpirationAlert.jsx` it lazily
   loads (135 lines, plus `messages.ts`) have had no caller since
   `28d359e7` (2021-07-14, REV-2132 "remove first purchase discount banner
   from courseware"); `index.js` still re-exports the default, and
   `generic/user-messages/hooks.js:18` cites `useAccessExpirationAlert` as
   the payload-memoisation example. `git grep` for either name outside the
   folder finds only that comment.

4. **The recommended shape touches fewer files than the issue lists.** The
   issue scopes four files (`hooks.js`, `InstructorToolbar.jsx`,
   `LoadedTabPage.tsx`, `TabPage.tsx`) because it assumed the data would be
   threaded down. Reading the owner queries from the hook leaves the three
   components untouched.

5. **After this layer, F is deletion only.** `git grep useModel src` (non-test)
   returns nothing; `git grep "modelType:" src` (non-test) returns nothing;
   the bridge's remaining callers are `queryClient.ts` (wiring) and
   `queryClient.test.ts` (one `'widget'` case), both F's. The three `meta`
   entries on the courseware hooks that survive are `logStatusAs` only.

6. **Precedents this conversion continues.**
   - A shared hook reading an owner's query without fetching:
     `useEnrollmentAlert` / `useLogistrationAlert` read
     `useOutlineTabData(courseId, { enabled: false })` from every tab (#2083).
   - A toolbar banner that behaves per tab: `useCourseStartMasqueradeBanner`
     gates on `tab === 'progress'`.
   - A shared hook reading route params: `useContextId` is
     `useParams().courseId` (`src/data/hooks.ts`, #1976).

## Decisions (settled with the user 2026-10-02)

Four independent axes; the chosen shape first in each.

### D1. Where the hook gets `accessExpiration` — settled

**(B) The hook reads the two owner queries without fetching, selected by
tab — settled.**

```ts
const outline = useOutlineTabData(courseId, { enabled: false }).data;
const progress = useProgressTabData(courseId, targetUserId, { enabled: false }).data;
// Only the outline and progress payloads carry access_expiration (openedx-platform
// course_home_api serializers); the dates payload does not, and the banner has never
// rendered on the courseware page.
const accessExpirationByTab: Partial<Record<string, CourseHomeAccessExpiration | null>> = {
  outline: outline?.accessExpiration,
  progress: progress?.accessExpiration,
};
const accessExpiration = accessExpirationByTab[tab];
```

Same visibility as today on every page: on outline and progress the owner has
fetched, the `enabled: false` observer sees the cached result; on every other
tab the lookup yields `undefined` exactly where `useModel` yielded `{}`. No
component changes. Two more observers mount with the toolbar; both are on
keys the page either owns (fetched once) or never fetches (no request).
Continues #2083's reader pattern and the sibling hook's per-tab gating.

(A) Thread it from `courseStatus`: `TabPage` derives
`courseStatus.tabDataQuery?.data?.accessExpiration`, passes it through
`LoadedTabPage` → `InstructorToolbar` → the hook. Changes three components,
turns a hook named for the data it sources into one that takes it in (the
issue's own objection), has no single answer for `CourseExit`'s two queries,
and either changes behaviour on the courseware page (finding 2) or needs a
per-page opt-out to avoid it.

(C) A context from `TabPage` carrying the tab's data: new bridging paradigm
for one reader. Rejected.

(D) Move `access_expiration` onto the course metadata endpoint: backend change,
out of Stage 1. Rejected here; noted in the decisions doc as the "north star"
the issue mentioned.

### D2. Where `targetUserId` comes from for the progress key — settled

**Read it with `useParams()` in the hook — settled.** `ProgressTab.jsx`
takes it from the same place; `useContextId` already reads a route param from a
shared data hook. react-router 6's `useParams` returns `{}` when no route
matched (it reads `RouteContext` without an invariant), so the bare
`InstructorToolbar.test.jsx` renders keep working. On any page but
`/progress/:targetUserId` it is `undefined`, which is the key the progress tab
itself uses there.

Alternative: thread `targetUserId` as a prop from `ProgressTab` through
`TabPage` / `LoadedTabPage` / `InstructorToolbar`. Three component edits to
carry one route param the hook can read itself.

### D3. `hooks.js` → TypeScript — settled: a peel layer below this one

Rename `hooks.js` / `index.js` to `.ts`, type `courseId` and `tab`, annotate
the `useModel` destructure as it is today. No runtime change, existing tests
untouched: the #2125 shape. This layer then shows only the read swap and the
`meta` removals on a typed file. Converting inside this layer (the #2111
shape) was passed over because the rename would show the whole file as new
and bury the one behavioural change, under a `refactor!:` footer about model
types. Issue body: `issue-body-access-expiration-alert-ts.md`. Stack order:
#2150 ← peel ← #1999.

### D4. The learner-facing `useAccessExpirationAlert` — settled: it stays

No in-repo caller since #499 (2021-06) and REV-2132 (2021-07); #606 left it
behind. Deleting it in the peel was proposed and rejected: the folder's
`index` exports it, plugins reach host modules through `@src`, and the only
remedy for a plugin that imported it would be to copy the hook, the component
and four message ids into itself. Earlier removal footers (#2134, #2140,
#2144) asked for a one-line read swap; this is a different order of ask and
not the migration's to make. The peel types its six parameters;
`AccessExpirationAlert.jsx` stays `.jsx` like the banner component. Removal,
if wanted, is a standalone proposal outside #1946.

## The change

**Peel** (#2151, `issue-body-access-expiration-alert-ts.md`, decisions in
`decisions-2151.md`; committed 2026-10-02 as `b0c318c3` (PR #2152, draft) on

  `useAccessExpirationMasqueradeBanner(courseId, tab)` per D1/D2; drop the
  `useModel` import (the last one in `src`). Comment on the lookup names the

- Untouched: `InstructorToolbar.jsx`, `LoadedTabPage.tsx`, `TabPage.tsx`,
  `modelStoreBridge.ts`, `queryClient.ts`, `store.ts` (all F).

## Tests

- **Owners' positive tests stay as they are.** The four cases in
  `OutlineTab.test.jsx` and `ProgressTab.test.jsx` go axios → query → hook
  now with no bridge in between; they are the proof the real path works.
- **Progress under `targetUserId`** (`ProgressTab.test.jsx`, beside *Viewing
  progress page of other students by changing url*): masquerade flag set, route
  `/progress/:targetUserId`, banner renders — proves the hook's key matches the
  owner's when the param is present.
- **Request count with a staff user** (per owner page, per the
  once-per-load convention): `original_user_is_staff: true` so the toolbar and
  its two `enabled: false` observers mount; outline data requested once on the
  outline page, progress once on the progress page, and the other tab's
  endpoint not at all.
- **Hidden where it has always been hidden** (`InstructorToolbar.test.jsx`,
  moving its render onto a seeded `QueryClientProvider`): seed the courseware
  metadata with `accessExpiration.masqueradingExpiredCourse: true` and render
  with `tab="courseware"` — no banner (guards finding 2); seed the outline with
  the flag and render `tab="outline"` — banner, with the date in the seeded
  `userTimezone`. Two cases, one per direction.
- `queryClient.test.ts`'s bridge case stays until F.
