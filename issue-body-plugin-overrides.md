Part of #2185.

**What:** `master` carries a plugin override registry, [`src/generic/plugin-overrides/`](https://github.com/openedx/frontend-app-learning/tree/master/src/generic/plugin-overrides) (#2082, formerly the Redux `plugin-store` slice): a widget rendered inside Learning's tree calls `registerOverrideMethod({ pluginName, methodName, method })`, and a host component folds the registered overrides over its default with `usePluginsCallback(methodName, defaultMethod)`. One method exists, `getIFrameUrl`: the unit content iframe URL built by [`Unit/urls.ts`](https://github.com/openedx/frontend-app-learning/blob/master/src/courseware/course/sequence/Unit/urls.ts) and folded in [`Unit/index.tsx`](https://github.com/openedx/frontend-app-learning/blob/master/src/courseware/course/sequence/Unit/index.tsx). The one known registrar is the published `@edx/unit-translation-selector-plugin`, which adds `src_lang`/`dest_lang` to the URL from a language the learner picks in the unit title slot.

**Why it does not survive the port as it is.** On `master` a plugin reaches the hook by importing `@src/generic/plugin-overrides` from an `env.config.jsx` widget compiled in the same build as Learning. On a frontend-base site a plugin is another app in `site.config` whose `slots` operations mount a widget in a Learning slot, and it imports from the Learning package's public exports (`learningApp`, `learningRoutes`), which do not include the hook; and until this epic restores the slots there is no slot to mount in. The epic 1 port (#1905) therefore drops the module: the unit computes its URL from `getIFrameUrl` directly, and the override surface is reshaped here, on the Slot API, as #2017 anticipated ("the *later* reshaping of the override API onto the frontend-base `Slot` system").

**Design direction, from the #2082 review.** frontend-base has no value-filter pipeline, and [ADR 0011](https://github.com/openedx/frontend-base/blob/main/docs/decisions/0011-no-slot-wrapping-operation.rst) declines the nearest thing to one: "We will **not** implement a slot wrapping operation in `frontend-base`. The use cases previously served by wrapping are better addressed by improving the existing layout system." The sketch from that review, as the candidate:

- A unit content slot whose default widget is `ContentIFrame`, with the default `iframeUrl` (and what builds it) passed as the slot's contract, and `ContentIFrame` and `getIFrameUrl` exported from the package so a plugin composes rather than reimplements.
- The translations plugin replaces that widget with its own composition of the two, adding `src_lang`/`dest_lang` from state it owns. Its selector stays a unit-title-slot widget, gated on its config fetch; the selection lives in a provider the plugin registers through `App.providers`, so the content widget has the value on its first render and the "no cleanup on unmount" workaround from #2082 is not needed. Because a replace is declared at config time and `condition` is synchronous, the plugin's widget self-gates, rendering the plain default when the feature is off or no language differs.

**Before fixing the shape:** the registry is a public extension surface and operator `env.config.jsx` files are unsearchable, so the known plugin is a pattern setter, not the whole population. Ask on the forums and in the Frontend Working Group whether other plugins register overrides (and for which `methodName`), and fold any answers into the slot contract. If none surface, the slot above is the replacement and the `getIFrameUrl` method name goes with the registry.

**Done when:** a plugin on a frontend-base site can change the unit content iframe URL the way the translations plugin needs (hidden until its config fetch, learner-selected language mid-session, applied on the first render of every unit), through slots and exports documented in the slot's README; the registry's README migration note is superseded by that README.
