# Decisions — reviewing other people's PRs (2026-10-30)

Settled while working out how a long-running review of someone else's PR is tracked: what was understood, what was checked and needed no comment, what changed under the review since the last pass. Entries are in the order they were decided.

1. **A fourth effort kind, `review`, branch `review/<repo>-<n>`.** A review ends in a verdict, so it is not a sidequest, and it is against a PR Brian does not own, so it is not a task. The close-to-tag lifecycle is what keeps the live set small; a single long-lived reviews branch was rejected because it only grows.

2. **The review's record is one file, `review-<n>.md`: a state section, a passes table and a question ledger.** State is free text, rewritten rather than appended: Brian's current read of the PR, whatever that is at the time ("not sure we want this at all", "approach is fine, reading the tests", "waiting on the author's answer about X"). A fixed ladder of gates was tried and dropped; the state means whatever it needs to mean. The passes table records base and head SHA, scope and outcome per pass. The ledger has one entry per question with a status (open, resolved with no comment, posted with the thread link, parked, stale) and a "rests on" anchor naming the files and the head SHA the answer was reached at. The next pass flips entries whose anchored files changed to stale and leaves the rest, so a question dug into once is not dug into again.

3. **A comment on the PR is what the author should act on or answer.** Everything else is a ledger entry: a question that resolved itself on digging, a check that came back fine, a finding held until something larger settles.

4. **Reviews live under `<bairf parent>/reviews`, one directory per review.** `reviews/<repo>-<n>/code` is the PR checkout and `reviews/<repo>-<n>/bairf` the effort worktree, so `ls reviews` is the list of open reviews. A flat layout with two entries per review was rejected once several open reviews on one repo became the normal case.

5. **One hub clone per repo at `reviews/.repos/<repo>`, never worked in and never pushed from.** A blobless clone of upstream itself, not the fork: reviews never push, and with origin being upstream `gh` resolves PR numbers without fork-versus-upstream ambiguity. Its push URL is disabled so the property holds mechanically. It exists to own worktrees. The project clone was rejected as the hub because its worktrees would die with the project and its branch list would fill with other people's branches.

6. **The PR checkout is a worktree whose branch is named by number.** `gh pr checkout <n> --branch pr-<n> --worktree <dir>/code` from the hub, so the hub's branch list reads as the open reviews. A pass re-syncs with `gh pr checkout <n> --force`, which survives the author's rebases and force-pushes. The code worktree's own `CLAUDE.local.md` names the review branch, so the one-checkout-one-branch link holds unchanged. Each worktree carries its own `npm ci`; that is the accepted cost of several open reviews on one frontend repo.

7. **`bin/review open|sync|close` wraps the steps, and close takes a reason.** Open ensures the hub, creates both worktrees, writes `CLAUDE.local.md`, prefills `prs:` in TAG.md and writes the review file with its first passes row. Sync force-resets the checkout and appends the passes row with the new head, scope and outcome left for the pass to fill. Close takes one of `merged`, `closed` (without landing) or `abandoned`, writes it as the final line of the state section, removes the code worktree and its branch in the hub, then runs `bin/effort close`. TAG.md stays refs only.
