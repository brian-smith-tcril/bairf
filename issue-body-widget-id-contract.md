**Goal:** decide, and write down, what an app promises about the widgets it registers by default: whether their ids are public surface, whether their order is, and what a change to each is called. Today two ADRs answer the first question in opposite directions and nothing answers the second.

**Why:** the two ADRs contradict each other on the same plugin.

- [ADR 0009](https://github.com/openedx/frontend-base/blob/main/docs/decisions/0009-slot-naming-and-lifecycle.rst) (Accepted), section 2, lists what a slot's contract is comprised of and adds: "though this does not include the presence, absence, shape, or implementation of child widgets: a given slot's content, default or otherwise, is explicitly *not* part of the slot's contract, and may change at any time".
- [ADR 0016](https://github.com/openedx/frontend-base/blob/main/docs/decisions/0016-shell-layout-replacement-seams.rst) (Proposed): "All existing inner slot ids and default widget ids are preserved. Plugins that target ``desktopCenterLinks.v1``, [...] continue to work without modification", and later: "The public surface gains one new slot id [...] and one new widget id".

Read literally, ADR 0009 says a default widget may be removed, renamed or moved at any time, so a plugin whose `relatedId` names one is outside any contract. ADR 0016 says plugins that target default widget ids keep working, and counts a new default widget id as public surface. Practice follows ADR 0016: five of the seven `WidgetOperationTypes` take a `relatedId` (`INSERT_AFTER`, `INSERT_BEFORE`, `REPLACE`, `REMOVE`, `OPTIONS`), a miss in `findRelatedWidgetIndex` is a silent no-op, and apps already target the shell's defaults (frontend-app-learner-dashboard inserts its order-history link with `INSERT_BEFORE` on `org.openedx.frontend.widget.header.desktopAuthenticatedMenuLogout.v1`, a default widget registered in `shell/header/app.tsx`). So the ADR 0009 clause is already not what anyone relies on, and ADR 0016 wrote the practice down for one change without reconciling it.

Order is the same question one step further, and neither ADR reaches it. Given a slot whose defaults are widgets A, B, C, a plugin meaning "at the end" writes `INSERT_AFTER` C, because `APPEND` from another app is ordered by `siteConfig.apps` and cannot say "last" on its own. If the app reorders its defaults to C, B, A, every id is preserved and the plugin renders, in the middle. "Continue to work without modification" has two readings, still renders and still renders where the author put it, and ADR 0016 never had to pick because its change moved JSX verbatim and kept the order.

Concrete case: openedx/frontend-app-learner-dashboard#878 keeps the three header link widget ids and changes their order from Courses, Programs, Discover to Explore, My Learning, Programs. Whether that is a `feat` or a `feat!` for the package depends on the answer here. openedx/frontend-base#334 (widget id aliases) is the deprecation mechanism for ids once ids are decided to be public; it does not touch order.

Written 2026-10-31 against `ae5ec93` on `main`. Three independent decisions, then where they are written.

### 1. Are an app's default widget ids part of its public surface?

Practice and ADR 0016 say yes. If yes: renaming or removing a default widget id is a breaking change of the app that registers it, versioned by that app's package, not by the slot's `.vN`; the deprecation path is `idAliases` on the widget (#334) kept for at least one release, the mirror of slot aliases (#178). If no, ADR 0016's preservation promise and the practice above are unsupported, and relative operations against defaults are documented as best-effort.

### 2. Is the order of an app's default widgets part of its public surface?

Separate from 1, because preserving an id keeps `REPLACE`, `REMOVE` and `OPTIONS` whole but only keeps `INSERT_AFTER` and `INSERT_BEFORE` placing against the right widget, not in the right place.

- (a) Order is not promised. A relative operation places against the target's current position; an app may reorder its defaults in a minor release. "First" and "last" are expressed with `PREPEND` and `APPEND`, and a plugin that needs "last" regardless of `siteConfig.apps` order has no way to say it. Cheapest for apps, and the reading closest to ADR 0009's clause.
- (b) Order is promised. A reorder of default widgets is a breaking change of the app, disclosed like a rename. Plugins can rely on `INSERT_AFTER` the last default; apps carry a major bump for navigation reorders.

Either way the TSDoc on `INSERT_AFTER` and `INSERT_BEFORE` in `runtime/slots/widget/types.ts` states the rule, since that comment is where a plugin author reads what the operation promises.

### 3. Where it is written

The ADR 0009 clause stays true for its own purpose (what bumps a slot's version) and is amended to say what it does not cover: the registering app's contract over its default widgets, which is the outcome of 1 and 2. Either an amendment to ADR 0009 section 2 with ADR 0016 updated to cite it, or a short new ADR that both reference. ADR 0016 is still Proposed, so its wording can change in the same pass.

Not here: the alias mechanism itself (#334); dependency ordering between relative operations.
